پیاده‌سازی کامل و قابل اجرای ربات معاملاتی هوشمند بر اساس **Data Contract &
Schema Specification** (`docs/data-contract.md`) — با داشبورد وب فارسی.

## شروع سریع (ویندوز)

**روی `start.bat` دابل‌کلیک کنید.** تمام!

اسکریپت پایتون را پیدا می‌کند، پورت را از `config.json` می‌خواند
(`engine.server_port` — روی این نصب **۹۹۹۹**)، مرورگر را روی داشبورد باز
می‌کند و ربات **کم‌مصرف و بدون هیچ چاپ اضافه‌ای** در همان پنجره اجرا می‌شود.
داده را در داشبورد ببین؛ پنجره فقط بنر و خطوط `[web]` را نشان می‌دهد:

```text
[i] Starting bot on port 9999 ...

==============================================================
 Nobitex Smart Trading Bot v1.0.0
 mode: nobitex | data: data
 dashboard: http://127.0.0.1:9999
==============================================================
[web] dashboard on http://0.0.0.0:9999
[web] password gate: ON | max 3 wrong tries | session 12.0 h
```

(اگر برای یک نشست عیب‌یابی می‌خواهی خودِ پنجره هم داده را زنده چاپ کند،
`run.py --live` را از داخل آن پنجره اجرا کن — بخش «نمای زنده (اختیاری)».)

**توقف ربات — دو راه، هیچ فایل جداگانه‌ای لازم نیست:**

1. **`Ctrl+C`** در همین پنجره. خط
   `stopped - engine thread joined, dashboard port released` را می‌بینی و
   پورت آزاد می‌شود. اگر cmd بعدش پرسید `Terminate batch job (Y/N)?` حرف
   `Y` را بزن — آن پرامپت خودِ cmd است و ربات همان لحظهٔ Ctrl+C خاموش شده.
2. **بستن کامل پنجره (X).** هندلر کنسول **قبل از** مرگ پروسه
   `engine.stop()` را صدا می‌زند، پس موتور وسط نوشتن دیتابیس رها نمی‌شود
   (بخش «Update Note» شمارهٔ ۵۹).

پورت دلخواه:

```bat
set NOBOT_PORT=9000
start.bat
```

## شروع سریع (لینوکس / مک)

```bash
python run.py                # داشبورد روی پورت config.json (این نصب: 9999) — کم‌مصرف
python run.py --live         # فقط برای عیب‌یابی: نمای زندهٔ رویدادها + خط حساب
python run.py --port 9000    # پورت دلخواه
python run.py --once         # فقط یک چرخه و خروج
python run.py --no-server    # بدون داشبورد
```

### نمای زنده (اختیاری، پیش‌فرض خاموش)

`run.py --live` هر رویداد مهم و هر چرخه یک خط حساب چاپ می‌کند (یادداشت ۵۹).
اما هر چرخه یک `status()` کامل می‌خواهد و روی یک VPS کوچک که باید هفته‌ها
بچرخد، هزینهٔ بی‌دلیل است — پس **پیش‌فرض خاموش است** و `start.bat` هم صدایش
نمی‌زند. اندازه‌گیری روی همین سرور (دو پنجرهٔ ۱۲۰ ثانیه‌ای، هر دو دقیقاً ۴
چرخه): بدون `--live` **۱۸.۰s** CPU و با `--live` **۱۹.۸s** CPU — یعنی نمای
زنده حدود **۱.۸ ثانیه در هر ۱۲۰ ثانیه (≈۱.۵٪ یک هسته)** اضافه می‌کرد، علاوه بر
کشیدن و رندر مداومِ کنسولِ ویندوز.

نیازمندی‌ها: **فقط Python 3.10+** — هیچ وابستگی خارجی وجود ندارد
(همه‌چیز stdlib است).

## داشبورد

آدرس: `http://127.0.0.1:9999` (`engine.server_port` در config.json) — فارسی و راست‌به‌چپ، با این تب‌ها:

| تب | محتوا |
|---|---|
| نمای کلی | KPIها، نمودار قیمت، ارزش پرتفوی زنده، «دارایی‌های من» در دو بخش تتری/تومانی (هر سکه زیر بخش بازار خودش، با خرید/فروش و حد ضرر/حد سود قابل ویرایش)، سفارش‌های در جریان، آخرین تصمیم‌ها |
| بازارها | همه بازارها: قیمت، اسپرد، نقدینگی، نوسان، RSI، روند، رژیم، کیفیت داده |
| تصمیم‌های AI | تاریخچه کامل تصمیم‌ها با ورود/حد ضرر/حد سود |
| ریسک و اجرا | تصمیم‌های موتور ریسک (تأیید/رد + دلیل) و اجراها |
| پرتفوی | موقعیت‌های باز، دارایی‌ها، معاملات انجام‌شده |
| رویدادها | جریان رویدادهای سیستم (SS53) |
| تنظیمات | ویرایش همه پارامترها از داخل مرورگر + ذخیره در config.json |

دکمه‌های بالای صفحه: شروع/توقف موتور، اجرای یک چرخه، معامله خودکار روشن/خاموش،
حالت امن، ریست پرتفوی آزمایشی.

اگر `web.password` تنظیم شده باشد، **قبل از دیدن داشبورد** یک صفحهٔ ورود می‌آید
(جزئیات: بخش «امنیت داشبورد و اجرا روی VPS»).

## امنیت داشبورد و اجرا روی VPS (پسورد ورود)

داشبورد می‌تواند موتور را روشن کند و **سفارش واقعی** بفرستد؛ پس هر بار که روی
آدرسی جز `127.0.0.1` گوش می‌دهد، باید پشت پسورد باشد.

**تنظیم پسورد (دو راه):**

1. از خود داشبورد: تب «تنظیمات» → کارت **🔒 امنیت داشبورد** — پسورد جدید،
   تعداد تلاش مجاز، مدت اعتبار هر ورود و تأخیر هر پسورد اشتباه. (برای تغییر
   پسورد لازم است همین حالا وارد شده باشید.)
2. در `config.json` بخش `web`:

```json
"web": {
  "password": "پسورد-دلخواه",
  "max_attempts": 3,
  "lockout_seconds": 0,
  "session_hours": 12,
  "failure_delay_s": 0.8,
  "allow_remote_without_password": false
}
```

- `password` هم متن ساده قبول می‌کند و هم هش یک‌طرفه. ساده‌ترین راه (بدون ویرایش دستی JSON):
  `python -m nobitex_bot.webauth --set "پسورد-دلخواه"` — پسورد را **هش‌شده** در
  `web.password` می‌نویسد و بقیهٔ فایل را دست نمی‌زند (متن ساده در هیچ‌جا ذخیره یا
  چاپ نمی‌شود). یا خروجی `python -m nobitex_bot.webauth --hash "پسورد-دلخواه"` را
  دستی در config.json بگذارید. بررسی مقدار فعلی:
  `python -m nobitex_bot.webauth --check "پسورد"` و وضعیت قفل/پسورد:
  `python -m nobitex_bot.webauth --show-status` (با `--config PATH` روی فایل دیگری
  هم قابل اجرا است).
- `max_attempts` — چند پسورد اشتباه تا قفل شدن (پیش‌فرض ۳).
- `lockout_seconds` — `0` یعنی قفل فقط با **تغییر پسورد در config.json** باز می‌شود؛
  عدد بزرگ‌تر یعنی بعد از آن مدت خودش هم باز می‌شود.
- `session_hours` — هر ورود موفق چند ساعت معتبر بماند.
- `allow_remote_without_password` — تا وقتی یک لایهٔ دیگر (مثلاً reverse proxy با
  احراز هویت) جلوی داشبورد نیست، `false` بماند.

**رفتار قفل:** پسورد اشتباه → پیام با تعداد تلاش باقی‌مانده؛ تلاش سوم → پیام
قفل و غیرفعال شدن فرم. قفل در `data/web_auth.json` ذخیره می‌شود، پس
**ری‌استارت کردن ربات هم قفل را دور نمی‌زند**. تنها راه باز کردن (وقتی
`lockout_seconds = 0` است): مقدار `web.password` را در `config.json` به یک
پسورد جدید تغییر دهید — قفل و همهٔ سشن‌های باز **فوراً** باطل می‌شوند و
نیازی به ری‌استارت نیست.

**چه چیزی به بازدیدکننده نشان داده نمی‌شود:** صفحهٔ ورود و پیام‌های عمومی قفل
(JSON پاسخ `/api/auth/login`) هیچ اشاره‌ای به نام فایل یا فیلد بازنشانی ندارند —
هیچ راهنمایی برای باز کردن قفل در سمت وب نیست. مسیر بازیابی فقط در **کنسول
سرور** (هنگام بالا آمدن) و **کارت «🔒 امنیت داشبورد» پس از ورود** نشان داده
می‌شود.

**نکات امنیتی پیاده‌سازی:** سشن‌ها سمت سرور و توکنشان تصادفی ۲۵۶ بیتی است
(تصمیم از پسورد مشتق نمی‌شود)؛ کوکی `HttpOnly; SameSite=Strict` است (پشت
HTTPS با هدر `X-Forwarded-Proto: https`، `Secure` هم اضافه می‌شود)؛
مقایسهٔ پسورد constant-time است؛ هر پسورد اشتباه `failure_delay_s` تأخیر
دارد؛ درخواست‌های POST با Origin غیرهم‌مبدأ رد می‌شوند (CSRF) و هدرهای
`X-Frame-Options: DENY` و `X-Content-Type-Options: nosniff` روی همهٔ پاسخ‌ها
ست می‌شوند. هیچ جا پسورد لاگ یا برگردانده نمی‌شود؛ فقط شمارش تلاش‌ها ذخیره
می‌شود و رویدادهای `AUTH_OK` / `AUTH_BAD_PASSWORD` / `AUTH_LOCKED` در تب
«رویدادها» دیده می‌شوند.

**اجرا روی VPS:**

```json
"engine": { "server_host": "0.0.0.0", "server_port": 9999 }
```

اگر پسورد تنظیم نشده باشد، سرور **عمداً بالا نمی‌آید** و پیامی می‌دهد که
`web.password` را تنظیم کنید (یا `allow_remote_without_password = true` را
فقط وقتی پشت یک پروکسی احراز‌هویت‌کننده هستید). پیشنهاد امن: درایور را روی
`127.0.0.1` نگه دارید و با nginx/آپاچی + TLS یا تونل SSH در معرض بگذارید.

**قبل از هر بار انتقال روی سرور جدید، این را اجرا کنید:**

```bash
python run.py --doctor        # یا: python -m nobitex_bot.doctor
```

گزارش، همین ماشین را می‌سنجد (بدون دست زدن به حساب): مخزن گواهی‌ها، یک
دست‌دادن واقعی HTTPS با صرافی، اختلاف ساعت میزبان با ساعت صرافی، IP خروجی و
کشورش، یافتن فایل توکن حساب، تنظیم bind و آزاد بودن پورت، و در پایان «حکم».
هر چک `FAIL` کد خروج **۲** برمی‌گرداند، پس در اسکریپت راه‌اندازی قابل استفاده
است. یک خط `report_json` هم در خروجی هست تا ماشینی خوانده شود.

دو خطایی که **فقط** روی سرور پیش می‌آید و الان خودِ گزارش علتش را می‌گوید:

1. **صفحه باز نمی‌شود** (در مرورگر `ERR_EMPTY_RESPONSE` / «هیچ داده‌ای
   نفرستاد»): علت `engine.server_host` روی `127.0.0.1` است — پورت فقط روی
   loopback گوش می‌دهد، پس `http://IP:8787` از سیستم شما هیچ جوابی ندارد
   (از بیرون، پورت فعالانه refused می‌شود). دو راه:
   - `"server_host": "0.0.0.0"` **همراه با** پسورد داشبورد:
     `python -m nobitex_bot.webauth --set "پسورد-دلخواه"` — بدون پسورد سرور
     بالا نمی‌آید. پورت را در فایروال هاست/پروایدر هم باز کنید
     (`ufw allow 8787/tcp`).
   - امن‌تر: `127.0.0.1` را نگه دارید و از سیستم خودتان تونل بزنید:
     `ssh -L 8787:127.0.0.1:8787 user@IP` و بعد `http://127.0.0.1:8787` را باز
     کنید (هیچ پورتی در دنیا باز نمی‌شود).
2. **ورود به صرافی:** `CERTIFICATE_VERIFY_FAILED ... unable to get local issuer
   certificate` — تصویر مینیمال لینوکس بستهٔ `ca-certificates` را ندارد و
   پایتون روی ویندوز از مخزن ROOT خود ویندوز می‌خواند (پس محلی سالم است).
   روی سرور: `sudo apt update && sudo apt install -y ca-certificates && sudo
   update-ca-certificates` (یا `pip install certifi`) و ربات را ری‌استارت کنید.
   در کد، همهٔ تماس‌های HTTPS از یک verifier مشترک می‌گذرند
   ([tls.py](nobitex_bot/tls.py)): اول مخزن سیستم‌عامل، و اگر خالی بود مخزن
   certifi؛ **اعتبارسنجی گواهی هیچ‌وقت خاموش نمی‌شود** و خطا با کد
   `TLS_CA_MISSING` همین دستور ترمیم را می‌گوید.
3. اگر IP خروجی سرور ایرانی نباشد، ورود و ثبت سفارش نوبیتکس معمولاً
   `429/403` می‌دهد؛ گزارش `--doctor` کشور IP خروجی را چاپ می‌کند.
4. اگر با nginx/آپاچی/Caddy جلوی داشبورد می‌گذارید، `Host` و
   `X-Forwarded-Proto` را پاس بدهید: گارد CSRF مقدار `Origin` مرورگر را با
   هدر `Host` مقایسه می‌کند و بدون آن، GETها کار می‌کنند ولی **همهٔ POSTها**
   (ورود، ذخیرهٔ تنظیمات، شروع/توقف) با `403` رد می‌شوند؛ و کوکی سشن فقط با
   `X-Forwarded-Proto: https` علامت `Secure` می‌گیرد. فایل‌های آمادهٔ
   این کار (Caddy، nginx، پسورد پروکسی، و unit systemd) در
   [deploy/](deploy/README.md) هستند: داشبورد روی `127.0.0.1` می‌ماند و
   Caddy فقط روی IP عمومی — روی همان پورت ۸۷۸۷ — گوش می‌دهد، با گواهی
   داخلی خودش (`tls internal`) چون پورت ۸۰/۴۴۳ ممکن است مال سرویس دیگری
   باشد.

## معماری (SS100)

```
Exchange (demo | nobitex REST)
   ↓
Snapshot Collector  (atomic write, SHA-256, SS56/57)
   ↓
Feature Engine      (EMA/RSI/MACD/Bollinger/ATR/..., SS12/15-19)
   ↓
Quality Gate        (SS93)
   ↓
Quant Scanner       (ranking, top-N, SS30)
   ↓
AI Layer            (heuristic | LLM — فقط پیشنهاد، SS31/32)
   ↓
AI Output Validation (SS73/74)
   ↓
Risk Engine         (SS33-35, fail-closed)
   ↓
Exit Manager        (stop-loss / take-profit, SS36/37)
   ↓
Execution Engine    (paper broker, idempotent fills, SS38-44)
   ↓
Portfolio / PnL     (SS21/22/45) → Performance (SS46)
```

اصل طلایی: **AI هرگز مستقیم به صرافی سفارش نمی‌زند و نمی‌تواند ریسک را دور بزند.**

## تنظیمات

همه‌چیز در `config.json` (یا از تب تنظیمات داشبورد):

- `engine.cycle_seconds` — فاصله چرخه‌ها (دمو: ۶۰ ثانیه)
- `exchange.mode` — `demo` یا `nobitex`
- `fee.*` — کارمزد (قرارداد: هیچ‌گاه hardcode نشود، SS27)
- `risk.*` — حداکثر ریسک هر معامله، exposure، drawdown، ...
- `ai.engine` — `heuristic` (بدون نیاز به اینترنت) یا `llm`
  (endpoint سازگار با OpenAI؛ خروجی LLM هم مثل همیشه validate می‌شود)
- `ai.buy_best` — وقتی چرخه هیچ خریدی پیشنهاد نکند، ربات بهترین بازار
  رتبه‌بندی‌شده را برای خرید انتخاب می‌کند (سایز و ریسک همچنان توسط موتور
  ریسک کنترل می‌شود)؛ از داشبورد هم با دکمه «بهترین گزینه» قابل تغییر است
- زمان‌های داشبورد (تصمیم‌ها، معاملات، رویدادها) به **ساعت تهران** نمایش
  داده می‌شوند
- `paper.*` — موجودی اولیه حساب آزمایشی (USDT و IRT)
- `exchange.live_trading` — ثبت سفارش واقعی (پیش‌فرض: روشن؛ پس از ورود مستقیم معامله واقعی انجام می‌شود)
- `exchange.live_by_default` — بعد از لاگین، معامله واقعی خودکار فعال شود
- `exchange.prefer_usdt_markets` / `exchange.include_irt_markets` — انتخاب بازارهای USDT و IRT
- `exchange.min_quote_volume_usdt` — حداقل حجم ۲۴ساعته (دلار) برای ورود بازار به چرخه
- `engine.max_markets` — حداکثر تعداد بازارهای پایش‌شده (برتر بر اساس حجم)
- `exchange.wallet_sync` — آینه‌کردن موجودی واقعی در موتور ریسک
- `exchange.rls_to_irt_divisor` — تبدیل ریال به تومان (پیش‌فرض ۱۰)

## ورود به حساب واقعی نوبیتکس (خرید/فروش و موجودی اسپات)

از تب «حساب نوبیتکس» در داشبورد:

1. **ایمیل و رمز عبور** نوبیتکس را وارد کنید.
2. **کد دو مرحله‌ای** (Google Authenticator) را بزنید — یا رمز مخفی 2FA
   (Base32) را ذخیره کنید تا ورودهای بعدی خودکار باشند. ربات طبق مستندات
   رسمی خودِ نوبیتکس، کد TOTP را با هدر `X-TOTP` می‌فرستد.
3. پس از ورود موفق، توکن (۴ ساعته یا ۳۰ روزه) در `data/credentials.json`
   ذخیره می‌شود و **ربات خودکار به حساب واقعی وصل می‌شود** — حتی اگر از
   حالت دمو شروع کرده باشید (hot-attach، بدون ری‌استارت).
4. **موجودی اسپات واقعی** (تمام رمزارزهای لیست‌شده در کیف پول) از
   `/users/wallets/list` خوانده، همگام و در داشبورد نمایش داده می‌شود؛
   موتور ریسک از همان موجودی واقعی برای اندازه‌ی معامله استفاده می‌کند.
5. بعد از ورود، ربات **مستقیم روی حساب واقعی** معامله می‌کند (بدون توقف در
   حالت آزمایشی): سفارش‌های لیمیت واقعی از طریق `/market/orders/add` ثبت

   واقعی هر چرخه reconcile می‌شوند. برای توقف معامله واقعی، دکمه‌ی
   **«معامله واقعی»** را خاموش کنید (فقط ناظر).
6. **جهت‌گیری سرمایه‌گذاری:** ربات همه بازارهای واقعی نوبیتکس (USDT و IRT)
   را می‌کاود، بازارهای بی‌نقدش را حذف می‌کند و برترین‌ها را بر اساس حجم
   و سیگنال‌های کمّی انتخاب می‌کند — سپس تصمیم‌های خرید/فروش را روی همان‌ها
   اجرا می‌کند.
7. دکمه‌ی سبز **«⚡ اجرای فوری چرخه»** در بالای داشبورد، همان لحظه یک چرخه
   کامل (داده → تحلیل → ریسک → سفارش واقعی) را اجرا می‌کند؛ دکمه‌ی ساده
   «اجرای چرخه» هم موجود است.

نکته‌ها:

همهٔ کوین‌های نوبیتکس داشته باشد».

**ریشهٔ هر دو مشکل یکی بود: اسنپ‌شاتِ دیسک.** *اسنپ‌شات* فقط سبد همان چرخه
را دارد (`engine.max_markets` بازارِ برترِ تتری که در «بازار معاملات» روشن
هستند) — پس سکه‌ای که در کیف پول داری ولی بیرون آن سبد است:

- در `_manage_exits` **قیمتی نداشت**، پس مقایسه‌ای هم با حد ضرر انجام نمی‌شد
  و تصمیمِ خروج هرگز ساخته نمی‌شد (ATOM با حد ضرر ۱٫۸۸۳۷۴ و قیمت ۱٫۷۶۳
  نمونهٔ زندهٔ همین بود)؛
- تصمیم‌هایی که ساخته می‌شدند (۲۴ تصمیم `EXIT_STOP` روی UNIUSDT) در
  اعتبارسنجی با `UNKNOWN_MARKET` **دور ریخته** می‌شدند، چون فهرست مجاز فقط
  بازارهای اسنپ‌شات بود؛
- «فروش» و «خرید» دستی با پیام «بازار در اسنپ‌شات فعلی نیست» رد می‌شدند.

**۱) کاتالوگ زندهٔ صرافی — [nobitex_bot/universe.py](nobitex_bot/universe.py) (جدید).**
ماژول `MarketUniverse`: **یک** فراخوانی عمومی `GET /market/stats` تمام بازارهای
نوبیتکس را می‌آورد (روی این نصب: **۴۵۷ بازار**) و ۲۰ ثانیه کش می‌شود — قیمت،
تغییر ۲۴ساعت، اسپرد، حجم، `tradable` و ارز پایه/مظنه برای همهٔ سکه‌ها، **بدون
اسنپ‌شات، بدون چرخه و بدون درخواست جدا برای هر بازار**. یک کپی دیسکی
(`data/markets/market_universe.json`) فقط warm-start است تا پروسهٔ تازه‌ری‌استارت
قبل از اولین فراخوانی شبکه هم قیمت داشته باشد؛ هرگز مبنای حقیقت نیست.

**۲) حد ضرر/حد سود و فروشِ دستی دیگر به اسنپ‌شات نگاه نمی‌کنند.**

- `_manage_exits` قیمت را با `prices.get(market) or _exit_price(...)` می‌گیرد
  (`_exit_price` = اسنپ‌شات → کاتالوگ زنده → تیکر با کش). سکهٔ نگه‌داشته‌شده
  همیشه قیمت دارد، پس **حد ضرر همیشه سنجیده و اجرا می‌شود**.
- `_market_row()` (کالای راهبردی «فروش/خرید دستی»): اول ردیف اسنپ‌شات، وگرنه
  یک ردیف ساخته‌شده از کاتالوگ زنده (`source=live_universe`,
  `data_quality=WARNING` با ایراد `LIVE_UNIVERSE_ROW`). دیگر «فروش» بی‌جواب
  نمی‌ماند؛ تصمیم از همان مسیر عادی (validation → risk → execution) می‌رود و
  ریسک همهٔ سقف‌ها را چک می‌کند.
- `_allowed_symbols()` = اسنپ‌شات **+** کاتالوگ زنده **+** رجیستری **+** هر
  بازارِ در اختیار: دیگر تصمیمِ خروج روی سکهٔ خودت `UNKNOWN_MARKET` نمی‌گیرد.
- قیمت درآمدنی‌های کیف پول هم از کاتالوگ زنده می‌آید (`_augment_prices_with_holdings`).

**۳) دو دلیلِ باقی‌ماندهٔ «حد ضرر نخورد» هم بسته شد.**

- **کارگزار سفارش را رد می‌کرد:** نوبیتکس سفارش زیر **۰٫۵ دلار** را با
  `SmallOrder` و فروشِ بیشتر از موجودیِ آزاد را با `OverValueOrder` رد می‌کند.
  حالا مقدار فروش از `_free_sell_amount` (کیف پول واقعی) گرفته می‌شود و سفارش‌های
  فروشِ بازِ خودمان برای همان بازار کنسل می‌شوند تا سکهٔ قفل‌شده آزاد شود؛ و
  موقعیتِ زیر کمینه از بازارِ **تبدیل** صرافی بسته می‌شود (بدون کمینه؛ تسویه
  به تومان) — به‌جای ۳۰ دقیقه پارکِ بی‌پایان. خاموش کردن:
  `risk.exit_convert_below_min=false`.
- **۵۰ خطای نویزی:** اگر کیف پول واقعی سکه را ندارد، ردیفِ کهنهٔ دفتر صفر و
  پلن پاک می‌شود (`EXIT_STALE_POSITION_CLEARED`) به‌جای تلاش هر چرخه.

**۴) تب جدید داشبورد «🌐 همهٔ بازارهای نوبیتکس».** کل کاتالوگ با جست‌وجو،
مرتب‌سازی (حجم/بیشترین رشد/بیشترین ریزش/تغییر/قیمت/کم‌ترین اسپرد/نماد) و

هر بازار — همه بدون اسنپ‌شات.

**۵) قفل امنیتی `NOBITEX_READ_ONLY` — و افشای یک حادثهٔ واقعی.** در جریان
عیب‌یابی همین باگ، یک پروسهٔ عیب‌یابیِ **فقط‌خواندنی** با توکنِ ذخیره‌شده
آداپترِ واقعی را hot-attach کرد (`live_by_default`) و مسیر «تبدیلِ زیر کمینه»
**۷ تبدیلِ واقعی** روی حساب انجام داد (جمعاً ≈۰٫۷۱ دلار از موقعیت‌های خرد که
قیمتشان زیر حد ضرر بود؛ خروجی به تومان در کیف پول است).

- `_convert_exit_below_min` حالا مثل هر سفارش واقعی دیگری به گیتِ
  `exchange.live_trading` پایبند است؛
- **قفلِ سخت روی خودِ آداپتور:** `NobitexAPI.is_read_only()` (متغیر محیطی

  `cancel_order`، `convert_wallet_balance`) را با `NobitexError(code="READ_ONLY")`
  رد می‌کند — هر مسیری از موتور که به آن‌ها برسد. خواندن (تیکر/اوردر‌بوک/
  کیف پول/کندل) دست‌نخورده است. اسکریپت‌های `scripts/dbg_*` خودشان این متغیر را
  ست می‌کنند و دیگر نمی‌توانند پول جابه‌جا کنند.

**۶) ابزار تازه: `python scripts/dbg_exits_live.py`** — پیش‌نمایشِ تصمیم خروج
روی **موقعیت‌های واقعی**، سه‌لایه فقط‌خواندنی: `NOBITEX_READ_ONLY=1` (سطح

برای هر بازار چاپ می‌کند: قیمت زنده، حد ضرر، فاصله، و اینکه موتور چه می‌کند
(سفارش/تبدیل/پارک/بی‌تریگر) و آیا از اعتبارسنجی رد می‌شود. نمونهٔ اجرای واقعی

### ۱۴۰۵-۰۷-۲۱ (۶۱) — «بازار معاملات: فقط تتری» حالا واقعاً همه‌جا حاکم است + کنسول دیگر با اسکنرها پر نمی‌شود

درخواست: «بعد از یک مدت این error را می‌دهد (ConnectionResetError از یک IP
خارجی) و با اینکه بازار معاملات روی فقط تتر ست شده، ربات هنوز خرید و فروش
IRT می‌کند — این بخش هم مشکل دارد.»

**یافتهٔ اول — آن traceback، خرابی ربات نیست، صدای اینترنت است.**

- پورت داشبورد روی `0.0.0.0:9999` با IP عمومی سرو می‌شود؛ `netstat` چند
  اتصال `ESTABLISHED` از IPهای خارجی نشان می‌داد و هر کلاینتی که وسط
  درخواست قطع می‌شد، `socketserver` یک traceback کامل روی کنسول چاپ می‌کرد
  («Exception occurred during processing of request from …» /
  «ConnectionResetError … forcibly closed by the remote host»). همین پنجره‌ای
  که در پیام آمده بود، از همان ابتدا پر از این بلوک‌ها بود.
- [nobitex_bot/web.py](nobitex_bot/web.py): `BotHTTPServer.handle_error` فقط
  خطاهای سطح اتصال (`ConnectionResetError`، `ConnectionAbortedError`،
  `BrokenPipeError`، `TimeoutError`) را بی‌صدا می‌کند؛ یک باگ واقعی داخل
  هندلر همان traceback قبلی را می‌گیرد (تست شده).
- همان فایل: `Handler.timeout = 30` — اتصال بیکار/رهاشده (اسکنر وصل می‌شود و
  هیچ نمی‌فرستد) بعد از ۳۰ ثانیه بسته می‌شود، به‌جای اینکه تا هر‌وقت باز
  بماند و نخ کارگر بگیرد.

### ۱۴۰۵-۰۷-۲۰ (۵۷) — رفع شکست گواهی حتی وقتی مخزن سیستم‌عامل «خالی نیست» (union با certifi)

درخواست: همان گزارش ورودی دوباره (باز نشدن `IP:8787` بعد از انتقال کد به VPS و
`CERTIFICATE_VERIFY_FAILED` هنگام ورود نوبیتکس) — با این تأکید کاربر که «روی
سیستم محلی اصلاً مشکلی نیست».

**یافتهٔ تازه (اندازه‌گیری‌شده): ادعای «سیستم محلی سالم» دیگر درست نبود.**

- `python run.py --doctor` روی همین ماشین: `[FAIL] exchange https … unable to
  get local issuer certificate` — در حالی که `trust store` می‌گفت **23 گواهی**
  از مخزن سیستم‌عامل بار شده؛ یعنی مخزن «خالی نیست» ولی کافی هم نیست.
- فهرست همان 23 ریشه فقط DigiCert/Microsoft/GlobalSign/ISRG/Starfield/
  SSL.com/USERTrust است — نه TrustAsia نه Certum.
- زنجیرهٔ فعلی سرور: `*.nobitex.ir ← LiteSSL Pro RSA CA 2025 ← TrustAsia TLS
  RSA Root CA ← (cross-sign) Certum Trusted Network CA`؛ `openssl s_client` روی
  همان اتصال `Verify return code: 0 (ok)` می‌دهد و همان دست‌داده با
  `cafile=certifi` هم TLSv1.3 و **HTTP 200**. پس نه شبکه خراب است نه سرور، فقط
  همان دو ریشه در مخزنی که پایتون بار می‌کند نیست.
- خودِ ربات هم از `2026-10-11T23:01Z` (۰۲:۰۱ بامداد امروز به‌وقت تهران) در
  [events.jsonl](data/events/events.jsonl) انبوه `MARKET_DISCOVERY_FAILED` /
  `MARKET_COLLECTION_FAILED` با همین متن ثبت کرده (100 خطا در 72 ثانیه) و
  ساعت ۰۲:۳۲ خاموش شد — یعنی جمع‌آوری داده روی همین سرور هم شکسته بود، نه فقط
  ورود.

**ریشهٔ منطقی در کد:** [tls.py](nobitex_bot/tls.py) فقط وقتی certifi را اضافه
می‌کرد که مخزن OS **کاملاً خالی** باشد؛ فرض «non-empty == working» با یک
مخزن 23تایی ناقص باطل شد و پناهگاه certifi هرگز فعال نمی‌شد.

**پیاده‌سازی:**

- [tls.py](nobitex_bot/tls.py): اگر certifi نصب باشد حالا **همیشه** با مخزن
  OS ادغام می‌شود (union دو مخزن ریشهٔ معتبر). `CERT_REQUIRED` و بررسی
  hostname دست‌نخورده‌اند؛ فقط مجموع ریشه‌ها widen می‌شود. اگر OS خالی باشد و
  certifi هم نباشد، هشدار بلند + `FIX_HINT` قبلی سر جایش است (همان دستور
  VPS: `apt install ca-certificates`).
- [test_doctor.py](tests/test_doctor.py): دو تست جدید — (1) ادغام certifi وقتی
  مخزن OS خالی **نیست**، (2) خالی‌ماندنِ بدون certifi باید هشدار بدهد و هرگز
  ساکت نماند (رفتار VPS تازه بدون هیچ بسته‌ای).

**تأیید:** `python run.py --doctor` بعد از تغییر → `0 FAIL, 3 WARN, 7 OK` با
`exchange https verified | TLS TLSv1.3 | cert CN=*.nobitex.ir by TrustAsia
Technologies, Inc. | HTTP 200` و `trust store: 131 CA certificates from
operating-system trust store + certifi`؛ مجموعهٔ کامل تست‌ها → ۲۳۷ تست سبز.

**وضعیت مشکل اول (ERR_EMPTY_RESPONSE) — ریشه روی همین سرور پیدا شد: پورت
۸۷۸۷ را IIS گرفته، نه ربات.**

- `netstat`: `0.0.0.0:8787` (و `:9742`) مال **PID 4 یعنی http.sys** است؛
  `appcmd list sites`: سایت IIS به نام `v42ir` با بایند
  `http/*:8787:v42.ir` + `https/*:9742:v42.ir` حالت Started دارد و 8787 در
  `excludedportrange` (administered) هم آمده است.
- `netsh http show sslcert`: گواهی TLS فقط روی `v42.ir:9742` ثبت است، نه
  روی 8787.
- پس رفتار مرورگر از خانه: `http://<IP>:8787` → **400 Invalid Hostname**
  (اندازه‌گیری‌شده از همین سرور)، `http://v42.ir:8787` → **403.4 از IIS**، و
  `https://v42.ir:8787` → هیچ TLS‌ای روی پورت نیست پس اتصال بی‌پاسخ بسته
  می‌شود — **همان ERR_EMPTY_RESPONSE مرورگر**.
- خود ربات هم مستأصل است: `run.py --doctor` → `WinError 10013` روی بایند
  `127.0.0.1:8787`. برخلاف لینوکس، http.sys سوکت را wildcard می‌گیرد و بایند
  لوپ‌بک هم نمی‌شکند؛ پس «دو سوکت روی یک پورت» (معماری (۵۵)/(۵۶)) با IIS روی
  این ویندوز ممکن نیست و [deploy/](deploy/README.md) هم تا وقتی بایند 8787 از
  سایت IIS برنداشته نشده بالا نمی‌آید.

**انتخاب کاربر: گزینهٔ ۱ (انتشار مستقیم روی `0.0.0.0:8787` + پسورد) — اعمال شد و
اندازه‌گیری شد.**

1. حذف بایند از IIS: `Remove-WebBinding -Name v42ir -Protocol http
   -BindingInformation '*:8787:v42.ir'` → سایت `v42ir` با `https/*:9742` سالم و
   Started ماند (9742/80/443 دست‌نخورده).
2. پسورد داشبورد: `python -m nobitex_bot.webauth --set` (فقط هش PBKDF2 در
   config.json ذخیره می‌شود) + `"server_host": "0.0.0.0"` +
   `allow_remote_without_password: false`.
3. فایروال ویندوز: قانون ورودی TCP روی پورت 8787 برای همهٔ پروفایل‌ها
   (`netsh advfirewall firewall add rule name="nobitex dashboard 8787" ...
   localport=8787 profile=any`).
4. ری‌استارت کامل ربات (موتور + داشبورد) با کد جدید TLS.

**تأیید روی همین سرور:**

- `netstat` → `0.0.0.0:8787` LISTENING با PID پایتون (نه PID 4 = http.sys)؛
  `GET` روی هر سه آدرس (loopback، IP عمومی، نام دامنه) → **200 + text/html**
  صفحهٔ ورود فارسی؛ `POST /api/auth/login` با Origin منطبق →
  `{"ok": true, "message": "ورود موفق"}` + کوکی `HttpOnly; SameSite=Strict`.
- **باز بودن از اینترنت (نه فقط از خود سرور):** پورت از سه نود مستقل بیرونی
  پرسیده شد (check-host.net → ایران/تهران، UK/لندن، USA/دالاس) و هر سه به
  `185.165.30.181:8787` **وصل شدند** (3.5ms / 93ms / 204ms) — یعنی علت
  `ERR_EMPTY_RESPONSE` (مالکیت http.sys روی 8787) رفع شده و نه فایروال ویندوز و
  نه پروایدر جلوی 8787 را نمی‌گیرند.
- جمع‌آوری داده بعد از ری‌استارت: در ۲۰۰ رویداد آخر **صفر** خطای گواهی (قبل از آن
  ۱۰۰ تا `MARKET_COLLECTION_FAILED` در ۷۲ ثانیه).
- `python run.py --doctor` → **0 FAIL**، `trust store: 131 CA certificates from
  operating-system trust store + certifi`، و `dashboard port 8787 … already
  served by this bot's dashboard`.

**دو نقص در ابزار تشخیص که همین بررسی رو کرد (رفع شد):**

- «dashboard port» می‌گفت پورت **آزاد** است در حالی که IIS آن را داشت: پروب با
  `SO_REUSEADDR` روی wildcard بایند می‌کرد و در ویندوز دو سوکت wildcard
  می‌توانند همزمان روی یک پورت بنشینند (باگ واقعی، چون همین پیام مسیر عیب‌یابی
  کاربر را گمراه می‌کرد). الان اول `/api/auth/status` را می‌پرسد (داشبورد خودمان →
  OK) و بعد با `SO_EXCLUSIVEADDRUSE` بایند می‌کند تا مالک غریبه لو برود؛ سه تست
  جدید همین را قفل می‌کند.
- متن «remote reachability» بر اساس `server_host` شاخه‌شده: حالت مستقیم (`0.0.0.0`،
   بدون TLS + دستور `netsh`) در برابر حالت پشت پروکسی (loopback، با هشدارِ «با
   `0.0.0.0` پورت پروکسی را ندزد»). قبلاً یک متن عمومی برای هر دو معماری بود.

**یافتهٔ جانبی (خارج از دو مشکل گزارش‌شده، تصمیم با صاحب ربات):** در همین اجرا
**۲۱** رویداد `SYSTEM_ERROR` از `EXECUTION_ENGINE` ثبت شده که متن‌شان رد شدن سفارش
توسط نوبیتکس است (`SmallOrder: Order value is limited to above 0.5`؛ آخرین مورد
`2026-10-12T01:00Z`) — چون `risk.min_order_usdt` روی **0.44** است و از حداقل
نوبیتکس (۰٫۵) کمتر است، یعنی سفارش‌های کوچک هیچ‌وقت پر نمی‌شوند.

**محدودیت صریح:** «از خانه باز شد؟» را نمی‌توان از داخل خود سرور جواب داد؛ همان
تست سه‌نودی بالا جانشین قابل‌قبول آن است (اتصال TCP واقعی از اینترنت)، ولی خودِ
رندر صفحه در مرورگر سیستم شما فقط با امتحان‌کردن تأیید می‌شود. این چیدمان HTTPS
ندارد؛ اگر لایهٔ TLS و پسورد پروکسی (خواستهٔ (۵۵)/(۵۶)) را هم می‌خواهید، همان
Caddy ویندوز را می‌شود بعداً اضافه کرد، ولی اول باید `engine.server_host` را به
`127.0.0.1` برگرداند (پروکسی نمی‌تواند روی پورتی که ربات با `0.0.0.0` گرفته
بنشیند).

### ۱۴۰۵-۰۷-۱۹ (۵۶) — داشبورد روی HTTPS با همان پورت ۸۷۸۷ (بدون دست زدن به ۸۰/۴۴۳)

خواستهٔ کاربر (پس از دیدن یافتهٔ پایین): «می‌خواهم پورت ۸۷۸۷ بماند» + «Caddy».

**راه‌حل: دو سوکت روی یک شماره پورت.** ربات روی `127.0.0.1:8787` می‌ماند و
Caddy فقط روی **IP عمومی** همان پورت گوش می‌دهد. چون بایند روی سوکت‌های
متفاوت است، تعارضی نیست: درخواست از اینترنت به Caddy می‌رسد و درخواست
داخلیِ خود سرور مستقیم به ربات. (تنها چیزی که این توازن را می‌شکند
`server_host: 0.0.0.0` است؛ آن‌وقت Caddy با «address already in use» بالا
نمی‌آید.)

**در Caddyfile:**

- `bind 185.165.30.181` — دستور `bind` طبق مستندات فقط *هاست* می‌گیرد و پورت
  از آدرس سایت (`v42.ir:8787`) می‌آید، پس ربات دست‌نخورده می‌ماند.
- `auto_https disable_redirects` — وگرنه Caddy برای ریدایرکت HTTP→HTTPS
  پورت ۸۰ را می‌خواهد که مال سرویس دیگر است و **بالا نمی‌آید**.
- `tls internal` — ACME به ۸۰ یا ۴۴۳ نیاز دارد و هر دو اشغالند، پس گواهی را
  CA داخلی Caddy صادر می‌کند؛ ریشه‌اش یک‌بار روی سیستم کاربر نصب می‌شود تا
  هشدار مرورگر برود (مسیر `root.crt` زیر `/var/lib/caddy/.../pki/authorities/local/`).
- جایگزین: اگر بعداً ۸۰/۴۴۳ آزاد شد یا گواهی واقعی داشت، همان دو خط
  `tls fullchain.pem privkey.pem` جای `tls internal`.

**تست رانش (drift) اضافه شد:** [test_deploy_configs.py](tests/test_deploy_configs.py)
کانفیگ‌های مستقر را ساختاری می‌سنجد چون نه روی این ماشین `caddy`/`nginx` هست
و نه داکر: پورت بالادست هر دو فایل یکی و برابر پورت پیش‌فرض ربات باشد؛ لیسنر
عمومی IP مشخص بگیرد (نه `0.0.0.0`، وگرنه با سوکت ربات تعارض می‌کند)؛ هیچ
کانفیگی پورت ۸۰/۴۴۳ را نگیرد؛ هر دو لایهٔ احراز هویت حاضر باشد و رمز
پروکسی **فقط هش** باشد؛ nginx همان دو هدر الزامی را داشته باشد و از تلهٔ
`Host $proxy_host` پرهیز کند.

> یک باگ در **خود تست** پیدا و رفع شد: `assertNotRegex` با `^` روی یک رشتهٔ
> چندخطی هرگز match نمی‌کند و آن تست **توخالی** بود (همیشه سبز). الان
> خط‌به‌خط چک می‌شود، و صحتش را با یک نسخهٔ عمداً خرابِ کانفیگ سنجیدم:
> **۹ تست، ۸ شکست** در حالت خراب و **۹ سبز** روی فایل‌های واقعی.

**تأیید:** اجرای واقعی `python run.py --doctor` روی همین ماشین با متن
راهنمای جدید (سه گزینه: پروکسی TLS / تونل SSH / بازکردن مستقیم) → `0 FAIL`
و ASCII؛ کل مجموعه → **۲۳۵ تست سبز، exit 0**.

**محدودیت صریح:** سینتکس Caddyfile/nginx روی این ماشین قابل اعتبارسنجی
نبود (نه caddy نه nginx نه داکر)؛ روی سرور `caddy validate --config` و
`nginx -t` را بزن. مصرف پورت ۸۷۸۷ روی VPS و بازبودنش در فایروال پروایدر هم
از اینجا قابل آزمایش نبود (قبلاً پورت ۸۷۸۷ آن سرور فعالانه refused می‌شد).

### ۱۴۰۵-۰۷-۱۹ (۵۵) — چیدمان امن روی سرور: HTTPS + پسورد پروکسی، داشبورد روی loopback

درخواست: «داشبورد را روی `v42.ir` با HTTPS و یک reverse proxy
احراز‌هویت‌کننده سرو کن، ولی خود ربات روی `127.0.0.1` بماند.»

**یافتهٔ مهم قبل از هر تغییر (اندازه‌گیری‌شده):** `v42.ir` روی
`185.165.30.181` الانه روی ۸۰ و ۴۴۳ به یک سایت فارسی «فرم ثبت شکایت /
دادخواست» ریدایرکت می‌کند (`302 → /Shekayat`) و گواهی‌اش هم برای این نام
معتبر نیست، مستقل از هدر `Host` — یعنی این نام به خودِ سرویس داشبورد وصل
نیست و همان سرویس پورت‌های ۸۰/۴۴۳ را گرفته است. تا این نکته حل نشود،
Caddy/nginx نمی‌تواند بایند کند؛ راه‌حل‌ها (ساب‌دامین، vhost جدا، پورت
اختصاصی + DNS‑01) در [deploy/README.md](deploy/README.md) آمده است.

**تحویل:** جعبه‌ابزار استقرار در [deploy/](deploy/README.md):

- [Caddyfile](deploy/Caddyfile) — گزینهٔ پیشنهادی: گواهی خودکار
  Let’s Encrypt + `basic_auth` (bcrypt؛ نام دستور از Caddy 2.8 به بعد
  `basic_auth` است، قبلاً `basicauth` بود) و `reverse_proxy 127.0.0.1:8787`.
  مستندات رسمی تأیید می‌کند Caddy **هدر اصلی `Host` را رد می‌کند** و
  `X-Forwarded-Proto` را خودش ست می‌کند، پس اضافه‌ای لازم نیست.
- [nginx-v42.ir.conf](deploy/nginx-v42.ir.conf) — گزینهٔ دوم با certbot و
  `auth_basic`؛ برخلاف Caddy، این دو خط **الزامی** است:
  `proxy_set_header Host $http_host;` (پیش‌فرض nginx مقدار `$proxy_host`
  یعنی `127.0.0.1:8787` است → همهٔ POSTها 403) و
  `proxy_set_header X-Forwarded-Proto $scheme;` (→ کوکی `Secure`).
- [nobitex-bot.service](deploy/nobitex-bot.service) — `Restart=always`،
  sandbox ملایم، و خط اختیاری `ExecStartPre=... run.py --doctor`.
- [deploy/README.md](deploy/README.md) — گام‌به‌گام فارسی + عیب‌یابی
  (۵۰۲ = ربات بالا نیست، ۴۰۳ روی POST = هدر `Host`، شکست صدور گواهی = پورت
  ۸۰ اشغال، و اینکه WARN داشبوردِ loopback در `--doctor` با این معماری
  **طبیعی** است و نباید با `0.0.0.0` «حل» شود).

**قرارداد پروکسی تست‌پذیر شد:** [test_proxy_contract.py](tests/test_proxy_contract.py)
یک reverse proxy واقعی (پسورد Basic + بازنویسی هدر) را جلوی **همان سرور
داشبورد** می‌گذارد و ادعاهای مستندات را اجرا می‌کند: ۴۰۱ بدون پسورد پروکسی؛
ورود موفق با کوکی `HttpOnly; SameSite=Strict; Secure`؛ **۴۰۳ شدن همهٔ
POSTها وقتی هدر `Host` بازنویسی نشود** (همان تلهٔ رایج)؛ افتادن `Secure`
وقتی `X-Forwarded-Proto` نباشد؛ ماندن گارد CSRF مقابل Origin بیگانه حتی با
سشن معتبر؛ و اینکه دسترسی مستقیم روی لوپ‌بک هم بدون پسورد خود داشبورد فقط
صفحهٔ ورود می‌دهد.

**تأیید:** `python -m unittest discover -s tests` → **۲۲۶ تست سبز** (۸ تست
جدید پروکسی). `python run.py --doctor` هم متن راهنمای bind را به سه گزینهٔ
(پروکسی TLS / تونل SSH / باز کردن مستقیم) به‌روز کرد.

**محدودیت صریح:** روی این ماشین نه `caddy` نصب است نه `nginx` (و نه
داکر)، پس **سینتکس Caddyfile/nginx محلی اعتبارسنجی نشد**؛ روی سرور قبل از
ری‌استارت `caddy validate --config /etc/caddy/Caddyfile` و `sudo nginx -t`
را حتماً اجرا کنید. صدور گواهی و بایند ۸۰/۴۴۳ هم به وضعیت DNS و اشغال
پورت‌ها روی سرور بستگی دارد که از اینجا قابل آزمون نیست.

### ۱۴۰۵-۰۷-۱۹ (۵۴) — اجرا روی VPS: چک پیش از راه‌اندازی + رفع خطای گواهی و پورت

درخواست: «وقتی کد را به VPS منتقل می‌کنم، دیگر با IP و پورت 8787 از سیستم خودم
باز نمی‌شود (`ERR_EMPTY_RESPONSE`) و هنگام ورود به نوبیتکس خطای
`NETWORK: <urlopen error [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify
failed: unable to get local issuer certificate>` می‌دهد؛ روی سیستم محلی هیچ
مشکلی نیست.»

**ریشهٔ دو مشکل (اندازه‌گیری‌شده، نه حدس):**

1. `engine.server_host = 127.0.0.1` در `config.json` (پیش‌فرض) — داشبورد فقط
   روی loopback گوش می‌دهد؛ از همین سیستم `185.165.30.181:8787` و `:8080`
   فعالانه `refused` شدند، یعنی **هیچ چیزی روی اینترفیس عمومی گوش نمی‌دهد**.
   پس مرورگر شما «داده‌ای» نمی‌گیرد، صرف‌نظر از نوع پیام مرورگر. (روی پورت ۸۰
   همان میزبان یک وب‌سرور/WAF جواب می‌دهد، پس میزبان زنده است.)
2. ماژول `ssl` روی ویندوز گواهی‌ها را از مخزن ROOT ویندوز می‌خواند، ولی
   تصویر مینیمال لینوکس بدون بستهٔ `ca-certificates` می‌آید؛ آن‌وقت هر
   `urlopen` روی HTTPS با `unable to get local issuer certificate` شکست
   می‌خورد. این یک مشکل **هاست** است، نه شبکه.

**پیاده‌سازی:**

- [tls.py](nobitex_bot/tls.py): یک verifier مشترک برای همهٔ تماس‌های خروجی —
  اول مخزن سیستم‌عامل (override محیطی `SSL_CERT_FILE`/`SSL_CERT_DIR` هم
  به‌صورت بومی رعایت می‌شود)، و اگر مخزن خالی بود مخزن `certifi`. اعتبارسنجی
  هرگز خاموش نمی‌شود؛ `ca_report()` وضعیت را برای گزارش و پیام خطا آماده
  می‌کند و `error_hint()` متن ترمیم را می‌سازد.
- [nobitex_api.py](nobitex_bot/nobitex_api.py): هر دو مسیر HTTPS (تماس احراز‌شدهٔ
  سشن و `_public_get` بازار) از همان context استفاده می‌کنند و شکست گواهی
  به‌جای `NETWORK` با کد مشخص `TLS_CA_MISSING` و دستور ترمیم برگردانده
  می‌شود؛ خطاهای غیرگواهی مثل قبل رفتار می‌کنند (`_public_get` همان استثنا را
  دوباره بالا می‌دهد). [ai.py](nobitex_bot/ai.py) هم context مشترک می‌گیرد.
- [doctor.py](nobitex_bot/doctor.py) + `python run.py --doctor`: چک پیش از
  راه‌اندازی — مخزن گواهی، دست‌دادن واقعی TLS با `apiv2.nobitex.ir`
  (نسخهٔ TLS، CN/صادرکنندهٔ گواهی، انقضا، اختلاف ساعت از هدر `Date`)، IP
  خروجی و کشورش (روی HTTP ساده تا وقتی مخزن گواهی خراب است هم کار کند)،
  پیدا کردن فایل توکن حساب (`data/real/credentials.json`)، تشخیص اینکه
  bind روی loopback است یا عمومی و آیا پسورد هست، آزاد بودن پورت (اگر ربات
  از قبل روشن باشد می‌گوید نسخهٔ دوم را بالا نیاورید) و راهنمای فایروال.
  هر `FAIL` کد خروج ۲ می‌دهد و یک `report_json` ماشین‌خوان هم چاپ می‌شود.

**تأیید:** `python -m unittest discover -s tests` → **۲۱۷ تست سبز** (۲۰ تست
جدید در [test_doctor.py](tests/test_doctor.py): استحکام verifier، تشخیص
زنجیرهٔ خطای گواهی در `URLError.reason`، نگاشت `TLS_CA_MISSING`، عبور هر
تماس HTTPS از context مشترک، fail شدن bind عمومی بدون پسورد، هشدار bind
loopback با هر دو راه‌حل، پورت اشغال‌شده، پیدا کردن فایل توکن، و ASCII بودن
گزارش برای کنسول ویندوز). اجرای واقعی روی همین ماشین:
`python run.py --doctor` → `0 FAIL, 3 WARN, 7 OK` با
«`https://apiv2.nobitex.ir verified | TLS TLSv1.3 | cert CN=*.nobitex.ir by
TrustAsia | clock +0 s`».

**محدودیت صریح:** گزارش از بیرون نمی‌تواند ثابت کند پورت روی VPS باز است؛
فقط می‌گوید روی این ماشین آزاد است و باید در فایروال پروایدر باز شود. و
برداشت/تراکنش ارزی همچنان با نرخ لحظه‌ای ارزگذاری می‌شود.

### ۱۴۰۵-۰۷-۱۹ (۵۳) — برداشت از حساب دیگر «سود سرمایه» را منفی نمی‌کند

درخواست: «وقتی از کل سرمایه واریزی برداشت می‌کنم، درست است که از کل سرمایه
واریزی کم می‌شود ولی حسابش غلط است — چون میزان سود سرمایه هم منفی می‌خورد»
(صفحهٔ `/panel/turnover/withdraw`).

**ریشهٔ باگ (با دادهٔ خام صرافی اثبات شد):** برداشت بانکی همان لحظهٔ ثبت
از کیف پول **کم می‌شود**، ولی وضعیتش ساعت‌ها روی `Bank processing` می‌ماند و
کد قبلی فقط `Done/Sent/Paid` را می‌شمرد. پس در فاصلهٔ تسویه: ارزش حساب
`−۲٬۴۳۴٬۷۲۰` تومان افتاده بود (تاریخچهٔ زنده: `08:16:35 → 08:17:35`)
ولی «کل سرمایه واریزی» روی `۵٬۴۶۴٬۶۰۵` ثابت مانده بود → «میزان سود سرمایه»
`−۱٬۸۲۰٬۱۶۳` (‎−۳۳٪) نشان می‌داد در حالی که با شمردن همان برداشت
**`+۶۰۰٬۸۹۳` (‎+۱۹٫۷۳٪)** بود. یک برداشت `Failed` (۲۸٬۹۰۷٬۲۴۱ ریال، پول
برگشته) درست بیرون می‌ماند.

**پیاده‌سازی:**
- **قاعدهٔ تعهد در `_net_deposited_from_exchange()` (`engine.py`):** هر برداشت
  به‌محض پذیرش صرافی شمرده می‌شود (کیف پول همان لحظه بدهکار شده) و فقط
  `failed/rejected/canceled/returned/refunded/expired` بیرون می‌ماند؛ واریزی
  تنها وقتی شمرده می‌شود که **رسیده** باشد (`Succeed/executed/…` — `Pending`
  نه، چون پولش روی کیف پول نیست). ثبت‌های بدون status سطح بالا
  (واریزی کارت‌به‌کارت کوین‌باکس) از `statement.status` خوانده می‌شوند.
- **`pending_withdraws_irt` + `audit`:** هر آیتم با ارز/مبلغ/معادل تومانی/وضعیت
  و `counted` در payload می‌آید (آخرین ۶۰ مورد) تا عدد قابل حسابرسی باشد.
- **تازگی کش:** سینک کیف پول هر جابه‌جایی خارجی تومان را می‌بیند (`flow_dirty`
  در `portfolio.overwrite_balances` — هر فیل خودش دفتر را آپدیت می‌کند، پس
  اختلاف با کیف پول یعنی انتقال بیرونی) و کش «کل سرمایه واریزی» فوراً
  بازخوانی می‌شود؛ قبلاً تا یک ساعت (`net_deposit_refresh_s`) عدد قدیمی
  سرو می‌شد و همان فاصله به‌اندازهٔ کل برداشت ضرر جعلی می‌ساخت.
- **خالص منفی هم معتبر است:** `net_irt` منفی دیگر با عدد دستی/دفتری جایگزین
  نمی‌شود (بیشتر برداشت‌کردن از واریزی، «سود سرمایه = ارزش حساب − سرمایه»
  را با خودش درست نگه می‌دارد).
- **هم‌خوانی دو کارت:** `holdings_pnl` قبل از ساخت payload حساب می‌شود و
  «سود ۲۴ساعت» همان اعداد را مقایسه می‌کند (قبلاً دو ارزش‌گذاری مستقل در یک
  payload، یک سنت اختلاف می‌ساخت)؛ در کارت «سود کل» هم «جمع» = جمع همان دو
  عددِ چاپ‌شده (سنت در حالت دلاری، تومان در حالت تومانی) و «ارزش کل حساب»
  از همان ارزش تومانی به دلار تبدیل می‌شود.
- **UI:** خط «برداشت در جریان (از حساب رفته، بانک در حال تسویه): X — از
  سرمایه واریزی کم شده تا سود سرمایه اشتباه منفی نشود» زیر سه خط کارت
  «سود کل» چاپ می‌شود.

**تأیید زنده (موتور ری‌استارت‌شده، حساب واقعی وصل، `live_trading=true`):**
برداشت در جریان `۲٬۴۱۹٬۳۸۱` تومان؛ کارت «سود کل» → `+۱۹٫۹۶٪`،
«میزان سود سرمایه: $2.3 | کل سرمایه واریزی: $11.5 | جمع: $13.8» و
`$2.3 + $11.5 = $13.8` ✓؛ «ارزش کل حساب» `$13.8` (همان `۳٬۶۵۳٬۱۷۶ تومان`)؛
«سود ۲۴ساعت» `+$1.83` با خط «واریز/برداشت خارجی این بازه: $-9.14» — یعنی
برداشت به‌عنوان انتقال، نه ضرر. `node --check` پاک و
`python -m unittest discover -s tests` → **۱۹۷ تست، exit 0** (سه تست جدید در
`TestNetDeposited` از [test_profit_lock.py](tests/test_profit_lock.py): برداشتِ
`Bank processing` شمرده می‌شود و `Failed` نه؛ واریزی `Pending` سرمایه نیست؛
افتِ کیف پول کش را بی‌اعتبار می‌کند).

**محدودیت (صریح):** کارمزد برداشت در پاسخ صرافی فیلد ندارد، پس فقط مبلغ
برداشت حساب می‌شود؛ برداشت‌های ارزی هم با نرخ لحظه‌ای به تومان ارزگذاری
می‌شوند (نه نرخ روزِ خودِ تراکنش).

### ۱۴۰۵-۰۷-۱۸ (۵۲) — «سود و زیان این بازار» = Σ(ارزش − مبلغ خرید) با دقتِ نمایشِ همان بخش

درخواست: در سرِ هر بخش (تتری/تومانی)، «ارزش − مبلغ خرید» برای هر توکن حساب و
جمعشان داخل «سود و زیان این بازار» گذاشته شود.

**ریشهٔ اختلاف:** جمعِ خام گرد می‌شد، نه ردیف‌ها. تتریِ زنده: ردیف‌ها
`$0.61 / $6.38 / $3.89 / $3.24 / $0.01` (ارزش) و `$0.59 / $5.99 / $3.04 /
$3.24 / $0.01` بودند و (ارزش − مبلغ خرید)شان **$1.26** می‌شد، ولی سرِ بخش
**$1.25** می‌گفت (`14.1255 − 12.8739 → 1.2516 → $1.25`). بخش تومانی هم یک
تومان فرق داشت (`۶۸۰٬۲۹۱٫۵۸۶ → ۶۸۰٬۲۹۲` در حالی که ردیف‌ها
`۳۳۲٬۲۲۲ + ۳۴۸٬۰۶۹ = ۶۸۰٬۲۹۱` چاپ می‌کردند).

**پیاده‌سازی:**
- `_display_step(quote)` (`engine.py`): دقتِ نمایشِ پول هر بازار — دلار ۲ رقم
  اعشار، تومان بدون اعشار (`ROUND_HALF_UP`).
- `_position_row()`: هر ردیف علاوه بر اعداد خام، `value_disp` و
  `invested_disp` (همان اعدادی که روی صفحه چاپ می‌شوند) و `pnl_money` =
  `value_disp − invested_disp` می‌دهد. اعداد خام (`value_irt`/`invested_irt`)
  برای محاسبات داخلی دست‌نخورده مانده‌اند.
- `_holdings_pnl()`: `by_market` از همین اعداد نمایشی ساخته می‌شود، پس
  `pnl == value − invested == Σ pnl_money` ردیف‌ها **دقیقاً** برقرار است
  (`display_step` هم در payload می‌آید). ردیفی که «مبلغ خرید»ش نامعلوم
  باشد در جمع هیچ‌یک از سه عدد نمی‌آید (ارزشش تنها جمع نمی‌شود؛ وگرنه
  دوباره همان سودِ جعلی زاده می‌شد).
- UI (`index.html`): سلول‌های «مبلغ خرید»/«ارزش»/سود پولی هر ردیف و
  سرِ بخش همه از همین اعداد خوانده می‌شوند (`rowVal`/`rowCost`/`rowMoney`)،
  پس سرِ بخش عیناً جمعِ ردیف‌های روی صفحه است و tooltip سرِ بخش هم همین
  قاعده را می‌گوید.

تأیید زنده (موتور ری‌استارت‌شده، PID 31676): تتری «5 سکه — ارزش: `$14.14` —
مبلغ خرید: `$12.87` — سود و زیان این بازار: `+$1.27`» = `0.34+0.92−0.01+0.02+0`
و `14.14 − 12.87 = 1.27`؛ تومانی «2 سکه — ارزش: `680,219 ت` — مبلغ خرید:
`243,257 ت` — سود و زیان این بازار: `+436,962 ت`» = `224,858 + 212,104`.
`node --check` پاک و `python -m unittest discover -s tests` → **۱۹۴ تست، exit 0**
(تست جدیدِ [test_market_sections.py](tests/test_market_sections.py): سرِ بخش =
جمع اعداد نمایشی ردیف‌ها، با همان پنج ردیف واقعی).

### ۱۴۰۵-۰۷-۱۸ (۵۱) — باکس «سود ۲۴ساعت»: مبلغ سود سرمایه در ۲۴ ساعت + دیتیل ریز زیرش

درخواست: باکس «سود ۲۴ساعت» فقط و فقط مبلغ سود سرمایه را — آن هم در ۲۴ ساعت —
نشان بدهد و زیرش یک دیتیل ریز هم از همین «میزان سود سرمایه در ۲۴ ساعت» بنویسد.

بدنهٔ کارت حالا **عدد بزرگ = فقط همان مبلغ** است (به واحد نمایش داشبورد:
`$-0.13` یا `-۳۵٬۱۰۳ تومان`) و زیرش یک **دیتیل ریز از خود «میزان سود سرمایه»**
می‌آید: «میزان سود سرمایه الان»، «میزان سود سرمایه ۲۴ ساعت پیش» و
«تغییر ۲۴ساعته» با درصد، و در آخر یک ردیف ۱۱px برای «مبنا» (همین ساعت،
۲۴ ساعت پیش + حساب واقعی/آزمایشی). همان متن کامل در **tooltip کارت** هم هست،
پس با یک hover همه‌چیز در دسترس است. عدد همان `pnl_irt` سرور است (محاسبهٔ سمت
مرورگر نیست) و برای این tooltip، `kpi()` یک پارامتر اختیاری `o.title` گرفت؛
کارت «سود کل» همان راهنمای کلیک خود را نگه داشته است. حالت «در انتظار»
(نبود نقطهٔ ۲۴ ساعت پیش) مثل قبل با متن توضیح می‌آید، چون آن‌جا عددی وجود ندارد.

تأیید زنده: `سود ۲۴ساعت` = `$-0.13` و ریزِ زیرش `$-0.13 = $0.45 − $0.58`
(هم‌خوان با «میزان سود سرمایه» کارت «سود کل»: `$0.45`)، با `basis: capital` و
`coverage: exact`. `node --check` روی اسکریپت داشبورد پاک و
`python -m unittest discover -s tests` → **۱۹۳ تست، exit 0**.

### ۱۴۰۵-۰۷-۱۸ (۵۰) — «سود و زیان این بازار» = جمع «ارزش − مبلغ خرید» ردیف‌ها + باکس ۲۴ساعت فقط از تغییر «سود سرمایه»

درخواست: در هر بخش (تتری/تومانی) برای هر سکه «ارزش» منهای «مبلغ خرید» همان
ردیف جدا نوشته شود و جمع نهایی آن‌ها همان «سود و زیان این بازار» بالای بخش
باشد؛ و باکس «سود ۲۴ساعت» فقط از میزان سود سرمایه در ۲۴ ساعت حساب شود.

**ریشهٔ باگ ‎-۲۳۳٫۵۹$:** ردیف SUSDT در دفتر با «میانگین خرید» ۱۶٫۵۱۲۰۹…$
ذخیره شده بود در حالی که همهٔ فیل‌های همان سکه ‎~۰٫۰۴$ بودند (خرید ۵۶٫۷۹ عدد
@۰٫۰۴۰۶۱ و ۶۳٫۱۵ عدد @۰٫۰۴۲۳۴). پس «مبلغ خرید» ‎$۲۳۵ برای ۱۴٫۲۵ سکهٔ ‎$۰٫۶۱
می‌شد و سود بخش تتری ‎-۲۳۳٫۵۷$ — درست کنار ردیفی که «سود از خرید: +۱٫۰۹٪»
می‌گفت. همان عدد خراب در فروش، `realized = فروش − میانگین×تعداد` را هم جعلی
می‌کرد (زیان محقق‌شدهٔ ساختگی). پس نمایش عوض نشد؛ **خودِ دفتر تعمیر شد**.

**پیاده‌سازی:**
- `_repair_position_entry()` (`engine.py`): میانگین خریدِ ذخیره‌شده با میانگین
  فیل‌های خود ربات مقایسه می‌شود و فقط اگر بیش از ۵ برابر (یا کمتر از یک‌پنجم)
  فرق داشته باشد بازنویسی می‌شود — به‌همراه `total_buys_irt`ی که همان‌قدر
  بیگانه است. `amount`، `last_buy_price`، تایمر نگه‌داری، `realized_pnl` و
  **نقشهٔ خروج/حد ضرر/پلهٔ کاربر** دست‌نخورده می‌مانند (رویداد
  `POSITION_ENTRY_REPAIRED`). میانگین سالم (اختلاف کارمزد/تاپ‌آپ) هرگز لمس
  نمی‌شود. این تعمیر در `_seed_positions_from_wallet` (هر `sync_real_wallet`)
  صدا زده می‌شود، پس با هر ری‌استارت/همگام‌سازی خودکار اجرا می‌شود.
- `_reconstruct_entry()`: تطبیق فیل‌ها از «پیشوندِ LIKE» به **برابری (سکه،
  واحد پول)** با `split_symbol(canonical_symbol(...))` تغییر کرد. برای بازار
  یک‌حرفی مثل SUSDT، `base="S"` بود و `LIKE 'S%'` خرید‌های SOLUSDT/STRKUSDT/…
  را هم وارد میانگین می‌کرد (خودش یک منبع خرابی و مانع تعمیر درست).
- `_position_row()`: «مبلغ خرید» باز هم هزینهٔ واقعی است (`amount × avg_entry`،
  اگر میانگین نبود قیمت آخرین خرید) و «سود از خرید»/«قیمت خرید» طبق SS100d
  همان آخرین خرید. خروجی `pnl_money` (ارزش − مبلغ خرید) هم مثل قبل می‌آید.

### ۱۴۰۵-۰۷-۱۷ (۴۸) — «سود ۲۴ساعت» = تغییر «میزان سود سرمایه» + جدا شدن حساب دمو از کیف پول واقعی

### ۱۴۰۵-۰۷-۱۷ (۴۷) — باکس «سود ۲۴ساعت»: مبنای سود سرمایه در آخرین ۲۴ ساعت، و افتادن روی «شروع» وقتی دیتا کامل نیست

**ریشهٔ رفتار قبلی:** `_profit_24h` وقتی تاریخچه از ۲۴ ساعت کوتاه‌تر بود،
نقطه‌های جوان‌تر از **۳۰ دقیقه** را نادیده می‌گرفت و کارت «در انتظار تاریخچهٔ
۲۴ ساعت قبل…» می‌شد — یعنی بعد از هر ری‌استارت تا نیم ساعت عدد نداشتیم و روی
حساب تازه/دمو بیشتر هم طول می‌کشید.

**قاعدهٔ جدید:** در حالت `partial` **قدیمی‌ترین نقطهٔ موجود** (همان لحظهٔ شروع)

۲۴ ساعت هم در حالت `exact` تضمین شده: از میان نقطه‌های قدیمی‌تر از ۲۴ ساعت،

همان بازه از گردش واقعی صرافی؛ اگر دیتای واریز روی یکی از دو سر بازه موجود
نباشد، جریان صفر فرض می‌شود و هرگز به‌عنوان سود جعل نمی‌شود. `waiting` فقط وقتی
است که هنوز **هیچ** نقطه‌ای ثبت نشده باشد (پیامش هم دیگر «۲۴ ساعت دیگر»
نمی‌گوید).

### ۱۴۰۵-۰۷-۱۷ (۴۵) — یک سکه فقط در یک بخش: پایان «duplicate با قیمت USDT»

درخواست: در بخش تومانی یک ردیف تکراری از بخش تتری (با همان دارایی/قیمت) دیده
می‌شود؛ نباید این‌طور باشد.

**ریشهٔ دقیق (از دیتای واقعی حساب):** در دیتابیس واقعی، `FILIRT` و `FILUSDT`
هر دو مقدار کامل `5.57969425`، `STRKIRT`/`STRKUSDT` هر دو `55.067636` و
`ATOMIRT`/`ATOMUSDT` هر دو `1.278464` داشتند — یعنی **یک موجودی کیف پول دو بار
روی دو بازار کاشته شده بود**. `_seed_positions_from_wallet` همیشه **تمام**
موجودی کیف پول را روی بازار هدف می‌گذاشت و `_refile_misplaced_positions`
ردیف بازار دیگر را دست نمی‌زد چون آن سمت هم «خرید واقعی» قدیمی داشت — پس
مجموع دو ردیف دو برابر کیف پول می‌شد و یک سکه در هر دو بخش (و در سود و زیان
هر دو) شمرده می‌شد.

**قاعدهٔ جدید — جمع ردیف‌های یک سکه ≤ موجودی کیف پول:** تابع جدید
`TradingEngine._reconcile_wallet_totals(balances, targets)` (در [engine.py](nobitex_bot/engine.py#L2475))
اول با `_market_for_base` بازارِ برنده را انتخاب می‌کند (اول خریدهای واقعی
خودمان، بعد ردیف موجود، آخر تنظیمات)، سهم آن بازار از کیف پول برداشته
می‌شود و بقیهٔ موجودی بین ردیف‌های بازار دیگر تقسیم می‌شود. اگر فقط همین
کافی نبود، ردیف اضافه **کلَمپ** می‌شود و اگر سهمش صفر شد، صفر و پلن حدش
حذف می‌شود (رویداد `POSITION_MARKET_REFILED` با مبلغ و `wallet_total`).
اگر جمع ردیف‌ها **داخل** موجودی کیف پول جا شود (نگهداری واقعی در هر دو
بازار)، هیچ‌چیز دست‌نخورده می‌ماند — دارایی واقعی نابود نمی‌شود.

**دو محل اجرا:** در پایان `_seed_positions_from_wallet` (کیف پول واقعی) و
همین‌طور هر چرخه در `run_cycle` روی موجودی دفتر (حالت واقعی: آینهٔ کیف پول
صرافی، دمو: کیف پول کاغذی) — چون `sync_real_wallet` در حالت دمو اجرا
نمی‌شود، داشبورد دمو هم خودش تمیز می‌شود.

**دو باقی‌ماندهٔ همان باگ:** (۱) ردیف صفرشده `total_buys_irt` و
`last_buy_price` را پاک نگه نمی‌داشت، پس `market_sections` آن بازار را
تا ابد «سرمایه‌گذاری‌شده» می‌دید؛ الان صفر می‌شوند. (۲) شرط
`opened_at` از `_market_activity` حذف شد — ردیفی که نه سکه دارد و نه پولی
خرج شده، بخش را فعال نمی‌کند.

**تست‌ها:** `tests/test_market_sections.py` → کلاس
`TestOneWalletBalanceNeverFillsTwoMarkets` (۶ تست): ردیف‌های برابرِ کل کیف
پول دی‌دوپ می‌شوند، خریدهای واقعی تومانی ردیف تومانی را نگه می‌دارند،
تقسیم واقعی دست‌نخورده می‌ماند، ردیف‌های بزرگ‌تر از کیف پول کلَمپ می‌شوند،
پلن ردیف صفرشده می‌رود، و یک چرخه در حالت دمو هم تکرار را تمیز می‌کند.
کل مجموعه: **۱۷۵ تست OK**.

**تأیید روی دیتای واقعی حساب (کپی جداگانه، بدون دست‌زدن به دیتای زنده):**
قبل از اصلاح: `ATOMIRT/ATOMUSDT`, `FILIRT/FILUSDT`, `STRKIRT/STRKUSDT` هر
کدام با مقدار کامل؛ بعد از یک بار `_reconcile_wallet_totals` با کیف پول
همان دفتر (`ATOM 1.278464`، `FIL 5.57969425`، `STRK 55.067636`):
`deduped = 3` و فقط `ATOMUSDT`/`FILUSDT`/`STRKUSDT` ماندند — با پلن‌های
صفرشده حذف‌شده؛ باکس دارایی‌ها دقیقاً سه ردیف تتری شد و `by_market` سمت
تومانی را صفر نگه داشت.

⚠️ **هشدار وضعیت کانفیگ (خارج از باگ ربات):** `config.json` خودتان
`exchange.mode = "demo"` و `engine.data_dir` روی پوشهٔ موقت آزمون
(`%TEMP%\ladder_preview_jf5k8lpk\data`) ست شده است — یعنی داشبورد ۸۷۸۷ در

پوشهٔ `data` تنها با تأیید کاربر انجام می‌شود.

### ۱۴۰۵-۰۷-۱۷ (۴۴) — تفکیک کامل موجودی، ارزش و سود و زیان هر بازار (IRT و USDT)

درخواست: موجودی، ارزش دارایی‌ها، قیمت خرید، قیمت فعلی و سود و زیان هر بازار
کاملاً مستقل محاسبه و نمایش داده شود؛ خرید در یک بازار هرگز در بخش دیگر
دیده نشود؛ سود و زیان هر بازار فقط از معاملات همان بازار بیاید؛ و مجموع
سود و زیان هر بخش در واحد پول خودش باشد.

**۱) هیچ‌وقت دو پول با هم جمع نمی‌شود:** `_holdings_pnl()` قبلاً
`invested`/`value` همهٔ ردیف‌ها را بدون توجه به بازارشان جمع می‌کرد —
یعنی `$` یک ردیف تتری (مبلغ خرید = تعداد × قیمت خرید) با تومان یک ردیف
تومانی در یک عدد می‌نشست و همان عددِ بی‌معنا زیر نام `_irt` گزارش می‌شد.
الان خروجی کلید `by_market` دارد: `{"IRT": {...}, "USDT": {...}}` با
`invested`/`value`/`pnl`/`pnl_pct`/`rows` هر بازار **در واحد پول خودش**
(تومان برای بازارهای `*IRT`، دلار برای `*USDT`). عددهای سطح بالای
`invested_irt`/`value_irt`/`pnl_irt`/`pnl_pct` فقط بازار تومانی‌اند و
`usdt_*` هم آینهٔ دلاری سمت تتری است. «کل سرمایه واریزی» هم فقط از سمت
تومانی بذر می‌شود.

**۲) سود و زیان پولی هر سکه:** `_position_row()` حالا `quote` (واحد پول
همین ردیف) و `pnl_money` (ارزش − مبلغ خرید، به پول همان بازار) هم
برمی‌گرداند. در باکس دارایی‌ها ستون جدید «سود/زیان» آمد: هر ردیف عددش را
در واحد بازار خودش می‌نویسد و زیر سرتیتر هر بخش هم مجموع همان بخش در
همان واحد می‌آید — «سود و زیان این بازار: +$1,042.81» زیر بخش تتری و
«+388 ت» زیر بخش تومانی. مجموع هر بخش فقط از ردیف‌های همان بخش ساخته
می‌شود (تومانی تومان، تتری دلار).

**۳) دو مبنای سود، هر دو صریح:** «سود/زیان» = ارزش − **مبلغ خرید**
(میانگین خرید) و هم‌خوان با دو ستون کنارش؛ «سود از خرید» درصدی جداست و
مبنایش **آخرین خرید** است (بعد از هر خرید ریست می‌شود) — توضیح هر دو در
tooltip همان عدد هست تا این دو با هم قاطی نشوند.

**۴) بخشی که خرید ندارد، عدد نمی‌سازد:** بخش تومانی بدون هیچ فعالیت
واقعی تومانی همچنان فقط سرتیتر «غیرفعال» است؛ بدون سکه، بدون ردیف موجودی
تومان و بدون سود و زیان.

**تست‌ها:** `tests/test_market_sections.py` → کلاس `TestMarketPnlSplit`
(۴ تست): جمع‌نشدن دلار و تومان در یک عدد، تومان‌نبودن عددهای سطح بالا در
حساب تتری‌فقط، پول‌نبودن سود و زیان در بازار دست‌نخورده، و `pnl_money`
هر ردیف در واحد بازار خودش. کل مجموعه: **۱۶۹ تست OK**.

**تأیید زنده (سرور دموی ‎`127.0.0.1:8801`):** payload موتور
`by_market.IRT = {invested: 55,998.65, value: 56,386.69, pnl: +388.03,
pnl_pct: 0.69}` و `by_market.USDT = {invested: $4,064.09, value: $5,106.89,
pnl: +$1,042.81, pnl_pct: 25.66}` داد و سطح بالا هم فقط 
`invested_irt = 55,998.65` بود (عدد دلاری داخلش نرفت). داشبورد همان دو
عدد را جدا نوشت: «ارزش: $5,106.89 — سود و زیان این بازار: +$1,042.81» و
«ارزش: 56,387 ت — سود و زیان این بازار: +388 ت»؛ ردیف `BTCUSDT`
«سود/زیان: +$940.74» و ردیف `BTCIRT` «سود/زیان: +388 ت» (دقیقاً
`4,245.23 − 3,304.49` و `56,387 − 55,999`). باpayload تتری‌فقط
(`market_sections.IRT.active = false`) رشتهٔ رندر شده نه ردیف موجودی
تومان داشت، نه سکهٔ تومانی، نه سود و زیان — فقط همان سرتیتر غیرفعال.

### ۱۴۰۵-۰۷-۱۷ (۴۳) — بخش تومانی فقط با خرید واقعی تومانی + هر بخش فقط با واحد پول خودش

درخواست: (۱) بخش تومانی (IRT) صرفاً وقتی فعال باشد که کاربر واقعاً در بازار
IRT با تومان خریده باشد؛ بدون آن هیچ ارزی در این بخش نمایش داده نشود؛
(۲) همهٔ قیمت‌ها/مبالغ بخش IRT تومانی باشد؛ (۳) همهٔ مبالغ بخش USDT دلاری
باشد و به تومان وابسته نباشد؛ (۴) ارزی که با تتر خریده شده در بخش تومانی
نیاید — نمایش بر اساس بازار واقعی خرید و سفارش ثبت‌شده؛ (۵) همهٔ محاسبات
(قیمت خرید، قیمت فعلی، ارزش، سود/زیان) در هر بخش با پول همان بخش.

**ریشهٔ مشکل (فایل‌های واقعی حساب):** `_seed_positions_from_wallet` روی
«همهٔ بازارهای همان سکه» حلقه می‌زد و هر کدام را با **همان موجودی کیف پول**
پر می‌کرد — پس یک سکهٔ واحد هم به‌عنوان `BTCUSDT` و هم `BTCIRT` ثبت می‌شد و
همان دارایی در هر دو بخش (و در exposure موتور ریسک) دیده می‌شد؛ حتی اگر
کاربر فقط با تتر خریده بود، ردیف تومانی هم ساخته می‌شد.

**۱) بازار واقعی خرید تعیین‌کننده است:** تابع‌های جدید `quote_of_market`
(در `utils.py`)، `_real_buy_activity(base)` و `_market_for_base(base, markets)`
هر کیف پول را به **یک** بازار می‌نشانند: اول خریدهای واقعی خودمان
(`fills` با شناسهٔ `live_…` و سفارش‌های دارای `exchange_order_id` — رکوردهای
کاغذی/دمو مدرکِ خرج‌کردن پول واقعی نیستند)، بعد ردیف موجودِ همان بازار، بعد
هر چیزی که درصد را می‌شکند («بازار معاملات» تنظیمات). `_refile_misplaced_positions`
هم ردیف قدیمی که در بازار اشتباه نشسته (هیچ خرید واقعی در آن سمت ندارد)
را صفر می‌کند و سکه زیر بازار واقعی‌اش می‌ماند — با رویداد
`POSITION_MARKET_REFILED`. اگر واقعاً در هر دو بازار خرید کرده باشد، هر دو
ردیف دست‌نخورده می‌مانند (ولی یک موجودی کیف پول هرگز دو بار کاشته نمی‌شود).

**۲) فعال‌سازی بخش تومانی:** `status()` کلید `market_sections` را برمی‌گرداند
(به تفکیک IRT/USDT: تعداد دارایی، سرمایه‌گذاری، سفارش، معامله و پلن +
`active`). داشبورد بخش «تومانی (IRT)» را فقط با `rowsIrt.length` یا
`market_sections.IRT.active` می‌کشد؛ بدون آن، همان سرتیتر با برچسب
«غیرفعال — هنوز خرید/سفارشی در بازار تومانی (IRT) ثبت نشده» دیده می‌شود و
**هیچ سکه و هیچ ردیف موجودی تومانی** داخلش نیست.

**۳) واحد پول هر بخش، خودِ آن بخش است:** در باکس دارایی‌ها، مبالغ و قیمت‌های
سطح تومانی (خرید، ارزش، «قیمت حد»، حد ضرر/سود، مبلغ قفل سود/ریسک، پلهٔ بعد)
همیشه با «ت» و ردیف‌های تتری همیشه با «$» نشان داده می‌شوند — حتی وقتی
«بازار معاملات» = both/usdt است و بقیهٔ داشبورد دلاری است (منبع قبلیِ
قاطی‌شدن دو واحد). معادل «≈ … تومان» از ردیف موجودی تتر حذف شد و ویرایشگر
حد ضرر/حد سود و پنجرهٔ خرید هر ردیف در واحد پول همان بازار باز می‌شود
(تومانی → تومان، تتری → $). هر ردیف نماد بازار خودش را هم کنار نام سکه
می‌نویسد (`BTC BTCIRT`).

**تست‌ها:** `tests/test_market_sections.py` (۱۵ تست) — `quote_of_market`،
فعال‌نشدن بخش تومانی با معاملهٔ کاغذی، فعال‌شدنش با معامله/سفارش/پلن واقعی
تومانی، کاشته‌شدن هر سکه در یک بازار، بازنشانی ردیف بازار اشتباه، و برنده‌شدن
بازار واقعی خرید بر تنظیمات. کل مجموعه: **۱۶۵ تست OK**.

**تأیید زنده (سرور دموی ‎`127.0.0.1:8801`):** با
`PREVIEW_SECTIONS=usdt` (فقط خرید تتری + یک معاملهٔ کاغذی تومانی) بخش تومانی
غیرفعال و خالی ماند و payload موتور `IRT: {fills: 0, active: false}` داد؛ با
ردیف تومانی، پلن و دارایی تومانی همان بخش فعال شد و در حالت دلاریِ کل
داشبورد همهٔ اعدادش تومانی ماند (`قیمت: 9,090,068,159 ت`)، ویرایشگر حد ضرر
با درصد ‎-5 دقیقاً `9,027,513,454.676802 × 0.95` را در موتور نوشت و با مبلغ
۲۰۰ تومان هم `stop_money = 200` و `stop = entry + 200 ÷ 0.000005` ثبت شد.

### ۱۴۰۵-۰۷-۱۷ (۴۲) — درصد حد ضرر از «قیمت حد» + ویرایش مبلغ قفل سود/ریسک + کلیک خرید/فروش در بازار «بازار معاملات» + دو بخش تتری/تومانی

درخواست: (۱) حد ضرر از «قیمت حد» محاسبه شود؛ (۲) با کلیک روی حد ضرر هم
درصد و هم مبلغ قابل تنظیم باشد؛ (۳) وقتی «بازار معاملات» روی تتری است،
کلیک خرید/فروش در تتر حساب شود و وقتی روی تومانی است در تومان؛ (۴) هر خرید
زیر بخش بازار خودش بنشیند — تتری زیر بخش موجودی تتر، تومانی زیر بخش موجودی
و جزئیات تومان — با همان دکمه‌های خرید/فروش و جزئیات، هر کدام در بخش خودش.

**۱) مبنای درصد = «قیمت حد» (نه قیمت خرید):** `set_stop_loss` حالت
`base_mode="hadd"` گرفت و ردیف‌های دارایی‌ها درصد هر دو حد را نسبت به همان
عددی می‌خوانند که به‌عنوان «قیمت حد (n)» نشان داده می‌شود
(`hadd_stop_pct` / `hadd_tp_pct`). پس تنها باز کردن ویرایشگر و تأیید، سطح را
جابه‌جا نمی‌کند. «مبلغ» (قفل سود/ریسک) همچنان نسبت به **قیمت خرید** است —
همان پولی که برای سکه‌ها داده شده — چون «چقدر سود قفل شد / چقدر در ریسک
است» یعنی همین. ویرایشگر سه فیلد دارد (قیمت، درصد، مبلغ) با همگام‌سازی زنده:
فیلد آخری که تایپ کرده‌اید تصمیم می‌گیرد چه چیزی ثبت شود (درصد با
`base="hadd"`، یا مبلغ → قیمت = قیمت خرید + مبلغ÷تعداد سکه). «حد ضرر همه»
و «حد سود همه» هم با `base="hadd"` اعمال می‌شوند.

**۲) کلیک خرید/فروش تبغ بازار انتخاب‌شده:** `TradingEngine._click_market_for`
نماد کلیک‌شده را با انتخاب «بازار معاملات» تنظیمات (`both|usdt|irt`) می‌سنجد:
در حالت «فقط تتری» کلیک «خرید» روی ردیف تومانی همان سکه را در بازار تتری
می‌خرد (و برعکس) و یادداشت فارسی می‌دهد که در کدام بازار ثبت شد — به‌جای
ردکردن کلیک. `suggest_buy` هم از همان مسیر می‌گذرد، پس مبلغ پیشنهادی و
موجودی نقد به تتر/تومانِ همان بازار می‌آید. در فروش، اولویت با بازار خودِ
ردیف است (سکه‌ها همان‌جا هستند) و فقط اگر آن بازار سکه نداشت، همان سکه در
بازار انتخاب‌شده فروخته می‌شود.

**۳) باکس «دارایی‌های من» در دو بخش:** «بخش تتری (USDT)» با ردیف موجودی
تتر و «بخش تومانی (IRT)» با ردیف موجودی/جزئیات تومان؛ سکه‌های هر بازار زیر
بخش خودشان (ارزش هر بخش هم در واحد همان بخش). دکمه‌های «خرید»/«فروش» و

### ۱۴۰۵-۰۷-۱۷ (۴۱) — نردبان پله‌ها: حد ضرر با هر strike بالا می‌رود + سرمایهٔ افزوده روی همان سکه

درخواست: (۱) درصد و مبلغ حد ضرر با هر strike (پلهٔ قیمت حد) به‌روز شود؛
(۲) هرچه پله‌ها بالاتر می‌روند سرمایهٔ بیشتری روی همان سکه بنشیند؛
(۳) حد ضرر هیچ‌جا پایین‌تر از «قیمت حد» نماند.

**ریشهٔ واقعی مشکل (از دیتای واقعی حساب):** `STRKIRT` در پله ۴ با قیمت حد
۱۸۳۶۴ (‎+۷۵٪ بالای خرید ۱۰۵۰۰) بود ولی `stop` هنوز ۱۰۱۸۵ مانده بود — یعنی ۳٪
زیر **قیمت خرید**، پس تمام سود پله‌ها بی‌محافظت و درصد/مبلغ حد ضرر هم ثابت و
بی‌ربط به پله‌ها. همین حالت در ردیف `SIRT` هم دیده می‌شد: `stop`=۱۰۲۱۷
(۳٪ زیر میانگین ورود) در حالی که «قیمت خرید» ردیف ۴۶۵۰۰ نشان می‌داد و ردیف
مثل «‎-۷۸٪» خوانده می‌شد.

**قاعدهٔ جدید (حد ضرر روی «پلهٔ قبلی» — انتخاب کاربر):** پله ۱ ← قیمت خرید
(سربه‌سر)، پله ۲ ← پله ۱، پله ۳ ← پله ۲ … و **هرگز پایین نمی‌آید**. یک پلهٔ کامل
فضای نفس می‌ماند؛ حد تنگ (مثلاً ۳٪ زیر پلهٔ تازه) روی تکان معمولی بازار می‌فروخت
و سود را قبل از ادامهٔ روند می‌بست. پله‌های واقعیِ ردشده در `ladder_rungs` ذخیره
می‌شوند تا حتی وقتی گام پله‌ها بین پله‌ها عوض می‌شود «پلهٔ قبلی» دقیق باشد؛
پلن‌های قدیمی (بدون این لیست) از لنگر خرید و گام خودشان بازسازی می‌شوند.

**سرمایهٔ هر پله:** با هر strike مقدار `ladder_add_stage` ثبت می‌شود و
`TradingEngine._ladder_topup_decisions` در **همان چرخه** با پول نقد آزاد
`risk.ladder_add_pct` درصد (پیش‌فرض ۵۰٪) از ارزش فعلی موقعیت را روی همان سکه
می‌خرد — مبلغ هم کف و هم سقف اندازه است، یعنی خرید دقیقاً همان بودجهٔ پله
(حداقل سفارش صرافی می‌تواند کمی بالا ببرد و سقف سهم/نقد پایین). تصمیم از خط
لولهٔ کامل SS100 می‌گذرد (validation → risk → execution)؛ هر پله حداکثر یک
خرید دارد و اگر پول نقد/سقف اجازه نداد همان پله می‌سوزد (رویداد
`LADDER_TOPUP_BLOCKED` دلیلش را ثبت می‌کند).

**خرید پله‌ای نردبان را ریست نمی‌کند:** `ladder_buy_pending` باعث می‌شود
`_auto_stop_for_buy` بعد از پر شدن سفارش پله، پله/قیمت حد/حد ضرر را از صفر
شروع نکند — خرید دستی یا خرید عادی AI مثل قبل نردبان را از قیمت جدید شروع
می‌کند. ویرایش دستی پله (کلیک روی زوج `(n)`) هم حد ضرر را روی پلهٔ قبلی
می‌برد، ولی خودش خرید پله‌ای نمی‌کند.

**پلن‌های عقب‌مانده:** هر چرخه، پلن‌هایی که حد ضررشان زیر پلهٔ قبلی جا مانده
هر چرخه یک‌بار بالا کشیده می‌شوند (`LADDER_STOP_RAISED`) — پس همان بعد از این
آپدیت، حد ضرر `STRKIRT`/`STRKUSDT`/`USDTIRT` روی پلهٔ قبلی می‌نشیند. اگر قیمت
همین حالا زیر آن پله باشد، همان چرخه با حد ضرر فروخته می‌شود (این خواستهٔ صریح
«حد ضرر پایین‌تر از پله نماند» است).

**ردیف دارایی‌ها:** درصد حد ضرر روی همان لنگر «قیمت خرید» و **مبلغ** آن هم کنارش
می‌آید — «قفل سود: X» وقتی حد بالای خرید نشسته، «ریسک: X» وقتی هنوز زیر خرید
است؛ «· پله بعد: X» هم بودجهٔ سرمایهٔ پلهٔ بعد را نشان می‌دهد. هر دو با
`dispPrice` (واحد همان بازار: تومان برای IRT، تتر برای USDT) نمایش داده می‌شوند،
نه با `usd()` که مبنای تومان دارد.

**کلیدهای جدید:** `risk.ladder_enabled` (پیش‌فرض true)، `risk.ladder_add_pct`
(۵۰) و `risk.ladder_topup_enabled` (خرید خودکار پله). با
`ladder_enabled = false` رفتار قبلی برمی‌گردد (حد ضرر با strike تکون نمی‌خورد).

**دو باگ واحدی که سر راه پیدا و بسته شد:** (۱) در `risk.py` مبلغ درخواستی
(تومان/تتر) با یک مقدار «تعداد سکه» مقایسه می‌شد و برای بازارهای IRT اشتباه
تقسیم می‌شد، پس مبلغ درخواستی خرید دستی/پله‌ای هیچ‌وقت واقعاً اعمال نمی‌شد —
الان با قیمت زنده به تعداد سکه تبدیل می‌شود؛ (۲) `manual_buy` مبلغ تومانی را در
فیلد واحد-تتری می‌گذاشت، یعنی برای بازارهای USDT درخواست کاربر حدوداً ۲۶۷٬۰۰۰
برابر اشتباه بود.

**تست‌ها:** `tests/test_profit_lock.py` → کلاس `TestLadder` (۸ تست: بالا کشیدن
حد عقب‌مانده روی پله، هرگز پایین نیامدن، درصد/مبلغ قفل‌شدهٔ ردیف، ریست نشدن
نردبان با خرید پله، پلهٔ دستی، بودجهٔ یک‌بار-در-هر-پله، خاموش‌بودن نردبان) +
به‌روزرسانی دو تست قبلی که «حد ضرر با strike تکون نمی‌خورد» را چک می‌کردند.
کل مجموعه: **۱۴۵ تست OK**.

### ۱۴۰۵-۰۷-۱۷ (۴۰) — کارت «سفارش‌های در جریان» جای باکس «برترین بازارها (Quant Scanner)»

درخواست: باکس «برترین بازارها (Quant Scanner)» از نمای کلی حذف شود و به‌جایش
باکس «سفارش‌های در جریان» بیاید که **جزئیات کامل آیتم‌های داخل هر سفارش** را
نشان دهد.

- **منبع حقیقت (سمت سرور):** متد جدید `TradingEngine.in_flight_orders()` و فیلد
  `open_orders` در `/api/status`. تا وقتی حساب واقعی وصل است، لیست سفارش‌های باز
  **خود صرافی** مبناست (دفتر محلی ممکن است بعد از لغو/پر شدن بیرونی، ردیف را OPEN
  نگه دارد) و برای اینکه هر ۲٫۵ ثانیه به API نزنیم این خواندن ۱۰ ثانیه کش می‌شود.
  در حالت دمو که لیست صرافی وجود ندارد، همان دفتر محلی استفاده می‌شود.
- **فقط سفارش‌های در جریان:** وضعیت‌های پایانی (FILLED/CANCELLED/REJECTED/…) از
  کارت بیرون می‌مانند؛ سفارشی که همین حالا ثبت شده و هنوز در لیست صرافی نیست هم
  فوراً دیده می‌شود.
- **جزئیات هر آیتم:** نماد، سمت (خرید/فروش)، نوع (LIMIT)، قیمت سفارش (با واحد
  نمایش $/تومان)، حجم درخواستی، مقدار پرشده + درصد، باقی‌مانده، ارزش سفارش،
  وضعیت، **سن سفارش** و فاصلهٔ قیمت سفارش تا قیمت بازار؛ به‌علاوهٔ «ثبت‌کننده»
  (ربات یا دستی) و شناسهٔ سفارش/تصمیم در tooltip. سفارش‌های ربات اول فهرست می‌آیند.
- **دو باگ واقعی که تست‌ها لو دادند و بسته شد:** (۱) باقی‌ماندهٔ نامعتبر/خالی کل
  سفارش را از کارت حذف می‌کرد — الان به «حجم − پرشده» برمی‌گردد؛ (۲) دو ردیف دفتر
  با شناسهٔ صرافی تکراری باعث می‌شدند یک سفارش واقعی ناپدید شود.
- تست‌ها: `tests/test_risk_mode.py` → `TestInFlightOrders` (۷ تست) — جزئیات سفارش،
  حذف وضعیت‌های پایانی، برچسب ربات/دستی، fallback باقی‌مانده، ترتیب ربات‌ها،
  قیمت زنده و حضور `open_orders` در `status()`.

### ۱۴۰۵-۰۷-۱۶ (۳۹) — «سود ۲۴ساعت» حالا مبلغ است، بر پایهٔ کل سرمایهٔ واریزی + سود، از دیتای واقعی نوبیتکس

درخواست: باکس «سود ۲۴ساعت» بر مبنای **کل سرمایهٔ واریزی + سود سرمایه** باشد،
مقدار سود را از ۲۴ ساعت گذشته حساب کند و برای مبلغ دقیق از **دیتای داخل نوبیتکس**
استفاده شود.

- **مبلغ + درصد:** تا قبل از این، کارت فقط یک درصد نشان می‌داد. الان سرصفحهٔ کارت
  عیناً **مبلغ سود ۲۴ساعت** است (تومان یا $ بر اساس حالت نمایش) و زیرش درصد از
  «ارزش حساب ۲۴ ساعت قبل» می‌آید.
- **سه ردیف مبنا (واریزی + سود):** «ارزش حساب ۲۴ ساعت پیش»، «ارزش حساب الان» و
  (وقتی عددی وجود دارد) «واریز/برداشت خالص این بازه» — دقیقاً همان ساختاری که
  کارت «سود کل» دارد، پس هر دو کارت یک زبان دارند.
- **واریز ≠ سود:** Σdeposits − Σwithdraws صرافی (همان دیتای turnover که KPI «سود کل»
  استفاده می‌کند) در هر نمونهٔ تاریخچه ذخیره می‌شود؛ در محاسبهٔ ۲۴ساعت، جریان خالص
  پولِ داخل بازه از تغییر ارزش کم می‌شود. پس واریز/برداشت جدید سود جعلی نمی‌سازد.
  اگر یکی از دو سر بازه معلوم نباشد، هیچ جریانی فرض نمی‌شود (تعداد اشتباه بهتر از
  عدد جعلی نیست).
- **واحدها:** تاریخچهٔ ارزش حساب حالا **تومانی** ذخیره می‌شود (`u:"irt"`) و
  نمونه‌ها از کیف پول واقعی گرفته می‌شوند (هر چرخه `sync_real_wallet`). نمونه‌های
  قدیمی که در واحد USDT بودند یک‌بار با نرخ زندهٔ USDTIRT به تومان تبدیل می‌شوند
  (و اگر نرخ در دسترس نباشد حذف می‌شوند تا هرگز دو واحد با هم مقایسه نشوند) —
  برای همین تاریخچهٔ قبلی کاربر از دست نمی‌رود.
- فیلد دلخواه: `real` (نمونه از حساب واقعی است یا آزمایشی) و `coverage`
  (exact/partial) در `/api/status` → کارت زیرش می‌نویسد مبنا «دیتای واقعی
  نوبیتکس» است یا «حساب آزمایشی»، و اگر تاریخچه کمتر از ۲۴ ساعت باشد سن واقعی
  مبنا را صادقانه نشان می‌دهد.
- تست‌ها: `tests/test_risk_mode.py` (۳۷ تست) — مبلغ + کم کردن واریز، برگرداندن
  برداشت، نبودِ دادهٔ واریز (بدون جعل)، و مهاجرت نمونه‌های قدیمی USDT→تومان.

### ۱۴۰۵-۰۷-۱۶ (۳۸) — یک سوئیچ واحد «حالت امن ⇄ حالت ریسک» و حذف کنترل «توقف ایمنی» از هدر

درخواست: (۱) وقتی حالت ریسک خاموش است، «حالت امن» شناخته و نمایش داده شود و
کلیک روی آن حالت ریسک را روشن کند، (۲) این دو کاملاً در هم ادغام شوند و

- **حالت امن = حالت ریسک خاموش.** در `status` فیلدهای `profile` (`safe|risk`) و
  `safe_profile` اضافه شد؛ یعنی همان یک فلگ ریسک، دو نمایش. بج سبز «حالت امن»
  دقیقاً وقتی نشان داده می‌شود که حالت ریسک خاموش است (قبلاً این بج فقط بابت
  safe_mode دیده می‌شد و عملاً پنهان بود).
- **یک دکمه، یک سوئیچ:** دو دکمهٔ جداگانهٔ «حالت امن» و «حالت ریسک» در هدر با یک
  دکمهٔ واحد `#btnProfile` جایگزین شدند: متن دکمه وضعیت فعلی را می‌گوید
  («🛡 حالت امن — روشن (کلیک: حالت ریسک)» یا «⚡ حالت ریسک — روشن (کلیک: حالت
  امن)») و رنگش با وضعیت عوض می‌شود؛ کلیک، سوئیچ را به حالت دیگر می‌برد، هرچند

  مثل قبل «ذخیره تنظیمات» را بزنید.
- **«توقف ایمنی» از رابط کاربری حذف شد.** دکمه و بج آن برداشته شدند تا تنها
  سوئیچ امن/ریسک در هدر بماند. نکتهٔ مهم و مستندشده: `safe_mode` در این نسخه
  **هیچ‌جا خودکار روشن نمی‌شود** (تنها راه، اندپوینت دستی
  `POST /api/control/safe_mode` است؛ پیش‌فرض خاموش، در config.json ذخیره نمی‌شود و
  با ری‌استارت پاک می‌شود)، پس حذف دکمه هیچ محافظت خودکاری را از بین نبرد. اگر
  روزی از API روشن شود، تنها نشانهٔ آن در tooltip همان دکمهٔ سوئیچ می‌آید.
- تست‌ها: `tests/test_risk_mode.py` (۳۳ تست) — تطابق `profile`/`safe_profile` با
  فلگ ریسک و استقلال «توقف ایمنی» از پروفایل (`test_halt_is_independent_of_the_profile`).

- `jget/jpost` روی ۴۰۱ خودکار به صفحهٔ ورود می‌روند (سشنِ باطل‌شده/منقضی).

**۲) قفل پسورد داشبورد (فایل جدید `nobitex_bot/webauth.py` + صفحهٔ `web/login.html`):**
- پسورد **هر بار از خود `config.json`** خوانده می‌شود (`web.password`)؛ هم متن ساده
  هم هش `pbkdf2_sha256$...` (ساخت: `python -m nobitex_bot.webauth --hash`).
- `max_attempts` (پیش‌فرض ۳) پسورد اشتباه ⇒ قفل. شمارش و زمان قفل در
  `data/web_auth.json` ذخیره می‌شود تا **ری‌استارت، قفل را دور نزند**.
- باز کردن قفل = تغییر مقدار `web.password` در `config.json`؛ تغییر پسورد، قفل و
  همهٔ سشن‌ها را فوراً باطل می‌کند (بدون ری‌استارت). با `lockout_seconds > 0`
  قفل بعد از آن مدت خودش هم باز می‌شود.
- سشن سمت سرور با توکن تصادفی ۲۵۶ بیتی، کوکی `HttpOnly; SameSite=Strict`،
  مقایسهٔ constant-time، تأخیر `failure_delay_s` روی هر پسورد اشتباه، رد POSTهای
  غیرهم‌مبدأ (CSRF) و هدرهای `X-Frame-Options: DENY` + `nosniff`.
- گیت روی همهٔ مسیرها: `/` و هر `/api/*` بدون سشن، پاسخ ۴۰۱ (یا صفحهٔ ورود) می‌دهند؛
  `/api/control/*` بدون ورود کاملاً بسته است. بدون پسورد، داشبورد مثل قبل فقط محلی کار م‌کند.
- **گارد امنیتی:** اگر `server_host` غیرلوکال باشد و پسوردی تنظیم نشده باشد، سرور
  بالا نمی‌آید و می‌گوید `web.password` را بگذارید (مگر
  `allow_remote_without_password = true`).
- کارت **🔒 امنیت داشبورد** در تب تنظیمات: تعیین/تغییر پسورد، تلاش مجاز، مدت
  اعتبار ورود و تأخیر — و دکمهٔ «🔒 خروج» در هدر.
- **بدون راهنمای باز کردن قفل در وب:** پیام‌های عمومی (صفحهٔ ورود و JSON قفل)
  هیچ نام فایل/فیلدی را لو نمی‌دهند؛ مسیر بازیابی فقط در کنسول سرور و کارت امنیت
  پس از ورود دیده می‌شود (تست `test_login_page_leaks_no_internal_paths`).
- `save_config` حالا **merge** می‌کند (قبلاً فایل را با بدنهٔ ارسالی بازنویسی
  می‌کرد و یک ذخیرهٔ جزئی می‌توانست پسورد/اطلاعات صرافی را پاک کند).
- تست‌های جدید: `tests/test_web_auth.py` (۳۱ تست) — هش/متن ساده، قفل بعد از ۳
  تلاش، رد پسورد درست در حالت قفل، باز شدن قفل با تغییر config.json، ماندگاری
  قفل بعد از ری‌استارت، انقضای سشن، باطل شدن سشن با تغییر پسورد، صحت گیت روی
  HTTP واقعی (۴۰۱ قبل از ورود، کوکی امن، خروج، رد Origin غیرمجاز) و گارد bind غیرلوکال.

### ۱۴۰۵-۰۶-۲۹ (۳۶) — نمایش دلاری در حالت تتری/هر دو + ردیف تتر در دارایی‌ها + دراپ‌داون سادهٔ بازار معاملات

درخواست: (۱) وقتی «بازار معاملات» روی «هر دو» یا «فقط تتری» است، در باکس «دارایی‌های من» علاوه بر IRT ردیف **USDT (تتر)** هم دیده شود (موجودی/آزاد/قفل)، (۲) همهٔ اعداد — کارت‌ها، دارایی‌ها، تصمیم‌ها، قیمت پله‌ها، حد ضرر/سود، خرید/فروش — در این حالت **به دلار ($)** نمایش داده شوند و فقط در حالت «فقط تومانی» تومان بمانند، (۳) در Settings فیلد «بازار معاملات» فقط دراپ‌داون ساده باشد و دو checkbox تیک‌خور زیرش حذف شوند.

### ۱۴۰۵-۰۶-۲۹ (۳۵) — بج اتصال نوبیتکس در هدر + اصلاح «سود ۲۴ساعت» + حذف «سود باز» و «جمع ساده» + تنظیمات کاربرپسندتر

درخواست: (۱) معلوم نبود به نوبیتکس وصل هستیم یا نه، (۲) Settings باید کاربرپسندتر شود، (۳) «سود باز» و «جمع سادهٔ سودهای باز» حذف شوند — فقط سه ردیف کارت «سود کل» کافی است، (۴) «سود ۲۴ساعت» واقعاً درست کار نمی‌کرد.

**۱) بج اتصال نوبیتکس (همیشه در هدر، همهٔ تب‌ها):**
- بج جدید «نوبیتکس: متصل ✓» (سبز) / «نوبیتکس: وصل نیست ✕ — وارد شوید» (قرمز) کنار بج حالت
- منبع حقیقت: `nobitex_connected` در `/api/status` = توکن موجود **و** موتور به آداپتور واقعی وصل — دیگر نباید حدس زد؛ کلیک بج → تب «حساب نوبیتکس»

**۲) «سود ۲۴ساعت» واقعی شد (باگ واقعی رفع شد):**
- باگ قدیمی: مبنا در سمت کلاینت وقتی تاریخچهٔ ۲۴ساعته نبود بی‌صدا به نزدیک‌ترین نقطهٔ قدیمی (چند روز قبل) یا اولین نقطه برمی‌گشت و عدد غلط را به‌نام ۲۴ساعت نشان می‌داد
- حالا سرور-محور: `_profit_24h` در engine مبنا را از نقطهٔ equity دقیقاً ۲۴ ساعت قبل می‌گیرد؛ تاریخچهٔ equity حالا **زمانی** هرس می‌شود (فقط ۲۶ ساعت آخر، نه صرفاً شمار نقاط) تا نقطهٔ چندروزه هرگز مبنا نشود
- پوشش صادقانه (`coverage`): `exact` = مبنای واقعی ۲۴ساعته؛ `partial` = تاریخچه هنوز ۲۴ ساعت نیست — پیرترین نقطهٔ ≥۳۰دقیقه مبنا می‌شود و «تاریخچه کامل نیست — مبنا: ارزش حساب N ساعت پیش» صریح نمایش داده می‌شود؛ `waiting` = هنوز تاریخچهٔ قابل‌استفاده نیست (با تخمین «حدود N ساعت دیگر»)

**۳) کارت‌های سود طبق درخواست ساده شدند:**
- کارت «سود باز» از نمای کلی حذف شد (اعداد سودِ هر سکه در باکس دارایی‌ها همان‌جا دیده می‌شود)
- کارت «سود کل» فقط ۳ ردیف: میزان سود سرمایه / کل سرمایه واریزی / جمع — «جمع سادهٔ سودهای باز» حذف شد
- نمای کلی الان: ارزش کل حساب (دلار) → ارزش کل (تومان) → موجودی نقد → سود ۲۴ساعت → سود کل → وضعیت ریسک → کیفیت داده → چرخه‌ها

**۴) Settings کاربرپسندتر:**
- عنوان فارسی واضح بخش‌ها: «صرافی و اتصال»، «ریسک و مدیریت سرمایه»، … + یک خط راهنمای هر گروه (این گروه چه می‌کند)

**تأیید:** ۶۹/۶۹ تست سبز (۵ تست جدید `TestProfit24h`: مبنای دقیق ۲۴ساعته، partial با سن صریح، waiting، نقطهٔ چندروزه هرگز مبنا نمی‌شود، پنجرهٔ ۲۶ساعته). سرور ری‌استارت و از UI زنده تأیید شد: بج قرمز «وصل نیست» هدر، کارت ۲۴ساعت با پوشش partial و سن مبنا، حذف «سود باز» و «جمع ساده»، عناوین/راهنماهای جدید تنظیمات.

### ۱۴۰۵-۰۶-۲۹ (۳۴) — انتخاب بازار معاملات در تنظیمات: تتری (USDT) / تومانی (IRT) / هر دو

درخواست: گزینه‌ای در Settings که تعیین کند خرید با تتر انجام شود یا تومان یا هر دو — به‌صورت tick.

**پیاده‌سازی:**
- فیلد جدید `exchange.trade_quote_markets` در `config.py` — سه‌حالته: `"both"` (هر دو)، `"usdt"` (فقط تتری)، `"irt"` (فقط تومانی)
- **تب تنظیمات:** یک دراپ‌داون + جفت checkbox («تتری (USDT)» / «تومانی (IRT)») زیر آن که با هم هم‌گام‌اند — از دراپ‌داون استفاده کنی تیک‌ها تنظیم می‌شوند، تیک بزنی دراپ‌داون به‌روز می‌شود؛ هر دو تیک روشن = «هر دو»، هر دو خاموش = برگشت به «هر دو» (هیچ‌وقت ربات بی‌بازار نمی‌ماند). برچسب فارسی: «بازار معاملات (خرید با تتر یا تومان)»
- **فیلتر در `_apply_trading_universe` در engine.py:** بازارهای USDT/IRT طبق همین انتخاب از universe معاملاتی حذف/اضافه می‌شوند (بدون ری‌استارت — hot-apply)
- **سازگاری با تنظیمات قدیمی:** مقدار خالی/نامعتبر → fallback به دو checkbox قدیمی «بازارهای تتری/تومانی» (`prefer_usdt_markets`/`include_irt_markets`)؛ اگر هر دو قدیمی هم خاموش بودند → fail-safe: هر دو گروه روشن + رویداد `QUOTE_MARKETS_BOTH_OFF`
- انتخاب معتبر همیشه بر فلگ‌های قدیمی اولویت دارد؛ تغییر انتخاب در همان چرخهٔ بعد اعمال می‌شود (رجیستری فلگ `tradable` را لحظه‌ای به‌روز می‌کند)
- تا وقتی پوزیشن باز روی بازار حذف‌شده وجود دارد، **فروش‌های حد ضرر/سود همان بازار ادامه دارند** (خروج‌ها هرگز بلاک نمی‌شوند) — فقط خریدهای جدید متوقف می‌شوند
- دکمهٔ دستی «خرید» در باکس دارایی‌ها هم طبق همین انتخاب محدود شد (`manual_buy`): خرید دستی از سوی خاموش‌شده با پیام فارسی رد می‌شود (مثلاً «بازار تتری خاموش است — «بازار معاملات» در تنظیمات روی تومانی (IRT) است»)
- config.json فعلی: `"trade_quote_markets": "irt"` (همان رفتار قبلی کاربر: فقط تومانی)

**تأیید:** ۶۴/۶۴ تست سبز (۹ تست جدید `TestQuoteMarketSelection`: هر دو/فقط تتر/فقط تومان، fallback به فلگ‌های قدیمی، fail-safe هر دو خاموش، اولویت انتخاب معتبر، اعمال فوری تغییر). سرور روی 8787 ری‌استارت شد؛ UI زنده تأیید شد (دراپ‌داون+تیک‌ها، ذخیرهٔ هر دو مقدار، برگشت بدون خطا) و universe زنده با انتخاب «irt» دقیقاً ۲۲۵ بازار تومانی و ۰ تتری شد.

### ۱۴۰۵-۰۶-۲۹ (۳۳) — لایهٔ تشخیص رژیم بازار + حد ضرر ATR-محور (معماری چندلایه)

درخواست: طراحی «مهم‌ترین الگوریتم» برای ربات معامله‌گر — پاسخ معیار: سیستم چندلایه‌ای که اولویت‌اش ریسک/سایز/رژیم است، نه پیش‌بینی قیمت. بررسی کد موجود نشان داد بخش بزرگی از معماری از قبل هست؛ این نوت لایه‌های غایب را اضافه می‌کند.

**نقشهٔ تطبیق معماری با کد موجود:**
- ✅ سایز بر اساس ریسک (`equity×risk%÷فاصلهٔ حد ضرر`) — از قبل در `risk.py` (SS35) با محدودهای نقد، حداقل سفارش و exposure
- ✅ کنترل هزینهٔ خالص — SS28 (`expected_net_return` = ناخالص منهای کارمزد دوطرفه + لغزش) با ردِ معاملهٔ بدون ادژ
- ✅ سقف exposure/drawdown/تعداد موقعیت — SS22/SS41 + bootstrap حساب‌های کوچک
- ✅ رتبه‌بندی momentum (حالت ریسک) — SS30 + فیلتر پامپ بی‌حجم (Note ۳۲)
- ⛔ **تشخیص رژیم بازار** — غایب بود (features.py فقط رژیم نوسان داشت) → این نوت
- ⛔ **حد ضرر ATR-محور در حالت ریسک** — حد ثابت بود → این نوت

**۱) ماژول جدید `nobitex_bot/regime.py` — تشخیص رژیم از داده‌های موجود:**
- ۶ رژیم: `STRONG_UPTREND / WEAK_UPTREND / SIDEWAYS / WEAK_DOWNTREND / STRONG_DOWNTREND / HIGH_VOLATILITY`
- ورودی: ساختار EMA 9/20/50، ROC (پراکسی قدرت ADX)، برچسب ساختار، RSI، breakout و `atr_percent` (کسری — 0.08 = ۸٪)
- امتیاز روند در ‎[-1,+1]‎: چیدمان EMA ±۰٫۴۵، ROC تا ±۰٫۳، برچسب ساختار ±۰٫۱۵، RSI تا ±۰٫۱۵، breakout ±۰٫۱ — آستانه‌ها ±۰٫۴۵/±۰٫۱۵
- گیت کرش: `atr_percent ≥ risk_mode_regime_atr_crash_pct` (پیش‌فرض ۸٪) → `HIGH_VOLATILITY` بدون توجه به جهت — هیچ خانواده استراتژی این‌جا قابل معامله نیست
- **گیت خرید:** حالت ریسک (چرخش پرسودترین‌ها) فقط در رژیم صعودی قوی/ضعیف خرید می‌کند — خرید برنده‌های روز در رنج/نزول یعنی خرید سقف؛ حالت امن بازتر است (فقط نزول/کرش بلاک). هرگز خروج‌ها را بلاک نمی‌کند. خاموشی با `risk_mode_require_uptrend=false`.
- در `run_cycle` بعد از رتبه‌بندی (مرحلهٔ ۴٫۵) اعمال می‌شود؛ بلوکه‌ها رویداد `RISK_MODE_REGIME_BLOCKED` + فیلد `status.regime_blocked` + بج «رژیم‌بلاک» روی کارت وضعیت ریسک با برچسب فارسی (صعودی قوی ⬆ … نوسان شدید ⚡)؛ تصمیم‌های خرید reason code `REGIME_<نام>` می‌گیرند

**۲) حد ضرر ATR-محور حالت ریسک در `_auto_stop_for_buy`:**
- فرمول: `فاصله = max(‎|کف ثابت|، 1.5×ATR٪)` با سقف مطلق ‎-8٪ — یعنی کوین پرنوسان حد عریض‌تر می‌گیرد (نویز نمی‌خورد) و هیچ معامله‌ای ریسک بی‌مهار ندارد
- پیش‌فرض‌ها: `risk_mode_atr_stop_floor_pct=-3`، `risk_mode_atr_stop_mult=1.5`، `risk_mode_atr_stop_cap_pct=-8`؛ حالت امن همان حد ثابت خودش
- هم‌راستا با منابع Note ۳۲ (Wilder/chartwhisperer: حد باید تابع نوسان باشد، نه ثابت)

**تأیید:** ۵۵/۵۵ تست سبز (۴ تست جدید: تشخیص رژیم‌ها، گیت کاندیدها در دو حالت، گیت سیکل موتور، سه‌حالتهٔ حد ATR: کف/ATR/سقف + حالت امن)؛ سرور ری‌استارت شد و فیلد `regime_blocked`/برچسب‌ها زنده تأیید شد. مثال عددی: ATR٪=4 → حد ‎-6٪ (به‌جای ‎-3٪ ثابت)؛ ATR٪=9 → سقف ‎-8٪.

### ۱۴۰۵-۰۶-۲۹ (۳۲) — دقیق‌سازی «سود کل» و «سود باز» + تنظیم پارامترهای حالت ریسک بر پایهٔ پژوهش‌های مستند

درخواست: «سود کل و سود باز دقیق نیستند» + «تنظیمات کد بر اساس دانش مستند سرمایه‌گذاری از منابع معتبر تنظیم شود تا سوددهی بالا برود».

**۱) کارت «سود باز» — واحد و مسیر محاسبه درست شد:**
- قبلاً `portfolio.risk.unrealized_pnl` را با زیرنویس «unrealized USDT» نشان می‌داد؛ آن عدد در واقع تومان بود (فرمول `(price−avg_entry)×amount` در بازارهای تومانی) و مسیرِ موازی محاسبه (avg_entry، ردکردن پوزیشن‌های بدون قیمت در snapshot) با ردیف‌های «دارایی‌های من» نمی‌خواند.
- حالا کارت «سود باز» **همان اعداد ردیف‌ها** را نشان می‌دهد: جمع (value−invested) باکس دارایی‌ها = `holdings_pnl.pnl_irt` برحسب تومان — یک مسیر واحد، خط‌به‌خط سازگار با ستون «سود از خرید».

**۲) کارت «سود کل» — تیتر درصدی که با تومان‌ها نمی‌خواند اصلاح شد:**
- نمونهٔ واقعی زنده: تیتر +31.27% (جمعِ سادهٔ درصد «سود از خرید» ردیف‌ها) ولی «میزان سود سرمایه» فقط +28,203 تومان روی 3,680,605 تومان واریزی = +0.77%. جمعِ درصدها وزن‌دار نیست و ضرر/کارمزد تحقق‌یافته را نمی‌بیند (آن‌ها فقط در ارزش کل حساب زنده‌اند).
- حالا تیتر = **رشد واقعی سرمایه** = (ارزش کل حساب − کل سرمایه واریزی) ÷ کل سرمایه واریزی (`holdings_pnl.growth_pct`) — همیشه هم‌خوان با خطوط زیر کارت: growth% × سرمایه واریزی = میزان سود سرمایه، و «جمع» = ارزش کل حساب.
- خط چهارم شفافیت اضافه شد: «جمع سادهٔ سودهای باز (بدون کارمزد/ضرر تحقیق‌یافته)» = `pnl_irt`؛ فیلد قبلی `pnl_pct` (جمع درصدهای باز) هم در API برای مقایسه ماند. tooltip کاشی هم اصلاح شد.

**۳) پارامترهای حالت ریسک بر پایهٔ پژوهش‌های حد ضرر (به‌جای اعداد سرانگشتی):**
- **حد ضرر ‎-1.5٪ → ‎-3٪:** حد ثابت خیلی تنگ روی برترین‌های پرنوسان ۲۴ساعته = نویز (ATR روزانهٔ کوین‌های داغ می‌تواند ۴–۸٪ باشد؛ حد باید با نوسان سازگار باشد). trendrider 2026: حد ثابت ‎-3.5٪ در تایم‌فریم کوتاه بیشترین win-rate/کمترین drawdown/بهترین profit factor را داشت؛ ‎-1.5٪ مدام بیدار می‌شد.
- **خروج افت (trailing از سقف) ‎-3٪ → ‎-6٪:** trailing تنگ در بازار خُرد زودبیدار می‌شود و سود را می‌کُشد (cryptoriskcalc/blofin)؛ trailing حدود ۱۰ واحد درصد win-rate قربانی می‌دهد و باید عریض‌تر از حد ضرر اولیه باشد — ۲× حد ضرر.
- **حد سود +8٪ → +12٪:** هم‌خوان با خروج عریض‌تر (در نمونهٔ cryptoriskcalc، حد +20٪ با نوسان بالا فقط ۸٪ مارجین‌کال داشت؛ حد سود کوتاه سقف سود را بریده و کارمزد چرخش را زیاد می‌کند).
- **فیلتر پامپ بی‌حجم (جدید):** رایج‌ترین اشتباه خرید برنده‌های روز بدون بررسی حجم است (+124٪ روی حجم کم = تله پامپ/دامپ). در حالت ریسک بازارهایی با حجم ۲۴ساعته زیر کف (`risk.risk_mode_min_quote_volume_usdt` = ۱۰۰٬۰۰۰ USDT، قابل تنظیم) امتیاز ۰ می‌گیرند (`LOW_VOLUME_PUMP`) و هرگز به صدر لیست خرید نمی‌رسند.
- همهٔ مقادیر در config.json/config.py و تب تنظیمات فارسی؛ fallbackهای داخلی کد (`engine.py`) هم هم‌زمان به‌روز شدند تا هیچ مسیر عدد قدیمی را نخواند.

منابع (برای مرور بعدی):
- Wilder, J.W. (1978), *New Concepts in Technical Trading Systems* — تعریف TR/ATR و هموارسازی ۱۴دوره‌ای؛ مبنای «حد باید تابع نوسان باشد».
- chartwhisperer.ca — ATR Volatility Stop Loss Trading Guide: TR=max[(H−L), |H−PrevClose|, |L−PrevClose|]؛ ATR=(PrevATR×13+TR)÷14؛ Chandelier Exit = trailing از سقف با 3×ATR؛ رشد ATR = جهش است نه جهت.
- trendrider.net (2026) — Stop Loss Strategies in Crypto Trading: مقایسهٔ ثابت ‎-3.5٪ / trailing / ATR در تایم‌فریم 15m؛ ثابت بیشترین win-rate و کمترین drawdown؛ trailing ~10pp win-rate می‌دهد.
- cryptoriskcalc.com + blofin.com — Trailing Stop Guide: trailing در روند خوب کار می‌کند و در بازار خرد زودبیدار است؛ استاپ مبتنی بر نوسان (ATR) برای کریپتو ضروری است (نوسان روزانهٔ ~۱۵٪ عادی شده)؛ حد سود +20٪ با نوسان بالا فقط ۸٪ خروج اجباری داشت.

### ۱۴۰۵-۰۶-۲۹ (۳۱) — حالت ریسک: چرخش سریع روی پرسودترین‌های ۲۴ساعته

درخواست: «سود کم می‌دهد» → حالت امن (انتخاب تحلیلی چندعاملی) حالا با یک دکمه به **حالت ریسک** تبدیل می‌شود: در اولویت، پرسودترین توکن‌های ۲۴ساعته را می‌خرد، به‌محض افت می‌فروشد و سرمایه آزادشده را به پرسودترین بعدی می‌برد.

رفتار حالت ریسک (دکمهٔ «حالت ریسک» در هدر — بین سوییچ‌ها زنده):
- **رتبه‌بندی خرید = تغییر ۲۴ساعته:** امتیاز اسکنر در حالت ریسک ۵۰٪ تغییر روز + ۱۵٪ مومنتوم + ۱۵٪ روند + ۲۰٪ قابلیت معامله است؛ برترین‌های روز در صدر کاندیدها (`TOP_24H_MOVER`)
- **فروش فوری روی افت:** حد ضرر تندتر (‎-1.5٪ از خرید، به‌جای ‎-3٪)، حد سود کوتاه‌تر (+8٪، به‌جای +25٪) و **خروج کامل هنگام افت ‎-3٪ از سقفِ قیمت از لحظهٔ خرید** (`EXIT_DROP`) — سقف هر چرخه دنبال می‌شود
- **چرخش سریع:** فاصلهٔ خرید تکراری ۳۰۰ ثانیه (به‌جای ۱۸۰۰)، ورود در همان قیمت لحظه‌ای (بدون pullback)، چرخش سرمایه بعد از حد ضرر **و** فروش افت فعال؛ قفل بعد از حد ضرر حداکثر ۳۰۰ ثانیه
- **تجمیع سرمایه (`RISK_MODE_SWEPT`):** پوزیشن‌های خردِ خریدِ خودِ ربات (زیر حداقل سفارش صرافی، فروش‌نشدنی) از مسیر تبدیل بدون‌حداقل صرافی به تومان برمی‌گردند (حداکثر ۴ عدد در چرخه) — سکه‌های قبلیِ کاربر (avg_entry=0) هرگز لمس نمی‌شوند
- **خرید غیرخرد:** اندازهٔ خرید حداقل ۱٫۲× حداقل سفارش تا بعد از افت کوچک قابل فروش بماند (نه «خرید حداقلی → سوییپ فوری»)
- سفارش FAILED سمت صرافی هم مشمول cooldown شد تا بازار خطاخورده هر چرخه کوبیده نشود

پیاده‌سازی: فلگ `risk.risk_mode` (ماندگار در config.json، اندپوینت `/api/control/risk_mode`، دکمهٔ هدر + badge نارنجی) — scanner/risk/ai/exits آن را در نقطهٔ استفاده می‌خوانند؛ هیچ مقداری جهش نمی‌کند. همهٔ پارامترها (`risk_mode_*`) در تب تنظیمات قابل تغییرند. حالت امن (قفل کل معامله) سرِ جای خودش ماند و بر حالت ریسک اولویت دارد.

دلیل ریشه‌ای «سود کم» که در حین کار پیدا شد: سرمایه به ~۳۷ پوزیشن خرد شکسته بود (اکثراً زیر حداقل سفارش = فروش‌نشدنی)، نقد آزاد کمتر از یک سفارش حداقلی و exposure سقف ۹۷٪ بود — ربات نه می‌توانست بخرد نه بفروشد؛ حالت ریسک با تجمیع + چرخش دقیقاً همین را باز می‌کند.

تأیید زنده: ۵۰/۵۰ تست سبز؛ بعد از فعال‌سازی، ۴ خرید واقعی روی برترین‌های روز (APT/ENA/NEAR/AERO و سپس SUI/CHIPI/…) ثبت شد، یک فروش `EXIT_DROP` روی افت ENA زده شد، نقد آزاد از ۹۴هزار به ~۶۱۰هزار تومان رسید، exposure از ۹۷٪ به ~۸۲٪ افت کرد و پوزیشن‌ها از ۳۷ به ~۲۰ متمرکز شد.

### ۱۴۰۵-۰۶-۲۹ (۳۰) — رفع خرابی اعداد پس از ذخیرهٔ تنظیمات (سقوط به دمو)

باگ: با ذخیرهٔ هر تنظیم بخش صرافی، فرم رمزهای ورود را خالی می‌فرستاد (آن‌ها در سشن‌اند نه config)؛ اعمال درجا آن خالی‌ها را روی cfg می‌نوشت و `make_exchange` با اعتبار خالی به‌جای نوبیتکس **آداپتر دمو** ساخت و وصل کرد — همهٔ قیمت‌ها تقلبی شدند (ارزش کل ۱۸۸ هزار به‌جای ~۳٫۸ میلیون) و چند معاملهٔ کاغذی ثبت شد.

رفع‌ها:
- **حفاظ رمزها:** مقدار خالی هرگز فیلد محرمانهٔ زنده را پاک نمی‌کند؛ رمز واقعاً جدید به سشن هم منعکس می‌شود
- **حفاظ اتصال:** اگر کارخانه بخواهد دمو برگرداند در حالی که نوبیتکس وصل است، اتصال واقعی حفظ و در `failed` گزارش می‌شود — دیگر هیچ ذخیرهٔ تنظیماتی اتصال واقعی را قطع نمی‌کند
- **فرم تنظیمات:** username/password/totp از فرم حذف شدند (مخصوص تب حساب) — با اشتباه تایپی هم پاک نمی‌شوند
- **پاک‌سازی آلودگی:** سفارش‌های قیمتی تقلبی پنجرهٔ دمو (USDT 86k، BTC ۱۴ میلیارد) با اسکریپت هدفمند از دیتابیس حذف شد؛ موجودی واقعی با «همگام‌سازی موجودی» از صرافی بازمیرور شد
- **گِارد جدید خروج:** فروش زیر حداقل ارزش سفارش صرافی (~۲۰۰ هزار تومان) به‌جای REJECTED هر چرخه، ۳۰ دقیقه ساکت می‌ماند (`below_min_until_ts`)؛ خرید جدید این حالت را پاک می‌کند

تأیید زنده بعد از رفع: `real_attached=True`، ۲۳۲ بازار واقعی با کیفیت ۱٫۰، ارزش کل ~۳٫۸۳M و جمعِ کارت سود کل دقیقاً برابر ارزش کل.

### ۱۴۰۵-۰۶-۲۹ (۲۹) — اعمال درجای تنظیمات بدون ری‌استارت

ذخیرهٔ تنظیمات در تب تنظیمات حالا **همهٔ بخش‌ها را بلافاصله روی ربات در حال اجرا اعمال می‌کند** — دیگر نیازی به ری‌استارت نیست:

- **مکانیزم:** همهٔ کامپوننت‌های موتور (collector/executor/scanner) یک شیء `Config` مشترک دارند؛ پس از ذخیره در config.json، هر فیلد با تبدیل نوع به‌درست (bool/int/float/str) روی همان شیء ست می‌شود و از چرخهٔ بعدی بلافاصله مصرف می‌شود
- **`engine.cycle_seconds`** حتی بین چرخه‌ها هم دوباره خوانده می‌شود (حلقهٔ چرخه دیگر interval را یک‌بار برای همیشه نمی‌گیرد)
- **بخش exchange:** اگر mode تغییر کند آداپتر از نو ساخته و متصل می‌شود (`exchange_reattached=true`؛ مثلاً demo→nobitex)؛ اگر فقط مقدارها عوض شوند (مثل divisor)، همان آداپتر درجا به‌روز می‌شود
- **پاسخ API:** `applied_live` فهرست فیلدهای اعمال‌شده، `failed` موارد خطاخورده با دلیل، و `note` پیام نهایی — توست داشبورد همین را نشان می‌دهد («ذخیره و درجا اعمال شد (n فیلد) — بدون نیاز به ری‌استارت»)
- **مخفی‌ها:** مقدار `***` همچنان یعنی «مقدار قبلی بماند»

تست زنده: تغییر `cycle_seconds` 60→75 بلافاصله در status همان پروسه دیده شد؛ `buy_cooldown_s` 1800→2400 و بازگردانی، بدون ری‌استارت.

### ۱۴۰۵-۰۶-۲۹ (۲۸) — کل سرمایه واریزی از آمار واقعی نوبیتکس

«کل سرمایه واریزی» دیگر عدد دستی نیست — از همان داده‌ای محاسبه می‌شود که صفحات `/panel/turnover/deposit` و `/panel/turnover/withdraw` پنل نوبیتکس نشان می‌دهند:

- **منبع:** `POST /users/wallets/deposits/list` (هر دو آرایهٔ deposits و withdraws)
- **فرمول:** جمع واریزی‌های موفق (`status=Succeed`، منهای کارمزد ثبت‌شده) − جمع برداشت‌های انجام‌شده (`status=Done/Sent`)؛ برداشت‌های `Failed` حساب نمی‌شوند چون پول هرگز خارج نشده
- **ارزگذاری:** ریال ÷ divisor تومان؛ USDT و سکه‌ها با نرخ لحظه‌ای بازار به تومان
- **کش:** حداکثر هر ساعت یک‌بار از صرافی می‌خواند (`net_deposit_refresh_s` در config)؛ در هر چرخه اگر پاس صرافی نیاید، آخرین کش یا مقدار دستی نگه داشته می‌شود
- **کارت سود کل:** خط چهارم مبنا را نشان می‌دهد — «از واریزی‌های صرافی: X − برداشت‌ها: Y · n دقیقه پیش» — و دکمهٔ **⟳ بازخوانی از صرافی** (`/api/control/refresh_deposited`) خوانش تازه می‌گیرد
- **عدد دستی هنوز هست:** کلیک روی کارت → مقدار override؛ تا موفق‌شدن بازخوانی بعدی صرافی همان می‌ماند (منبع در `deposited_source` معلوم است: `exchange` یا `manual`)

نمونه زندهٔ همین لحظه: واریز ۱۶٬۲۶۵٬۴۷۰ − برداشت ۱۲٬۵۸۴٬۸۶۵ = **۳٬۶۸۰٬۶۰۵ تومان** خالص سرمایه.

**اصلاح قالب (همان روز):** کارت «سود کل» دقیقاً همین‌طور رندر می‌شود — تیتر درصد، زیرنویس «% جمع و تفریق لحظه‌ای از درصد تمام سود/ضرر از‌هایی که جلوی سود از خرید نوشته می‌شود» (tooltip کارت) و سه خط تمیز «میزان سود سرمایه / کل سرمایه واریزی / جمع» — بدون خط منبع و بدون دکمهٔ بازخوانی؛ خوانش صرافی همیشه خودکار است (حداکثر هر ساعت + کش).

**اصلاح سازگاری (همان روز):** «میزان سود سرمایه» دیگر جمع سودِ بازِ ردیف‌ها نیست — رشد کل حساب (ارزش کل = نقد + موقعیت‌ها + سود/ضرر تحقق‌یافته و کارمزدها) منهای سرمایهٔ واریزی است. با این تغییر همیشه «میزان سود سرمایه + کل سرمایه واریزی = ارزش کل حساب» دقیقاً برقرار است و جمع دیگر از ارزش کل بیشتر نمی‌شود. کنار «میزان سود سرمایه» درصد رشد سرمایه هم نمایش داده می‌شود (نمونه: ‎+۱۳۷٬۹۶۸ (+۳٫۷۵٪)). درصد تیتر «سود کل» طبق تعریف قبلی همان جمع زندهٔ درصدهای «سود از خرید» ردیف‌ها می‌ماند (مخرجش سرمایهٔ در دارایی است، نه واریزی).

### ۱۴۰۵-۰۶-۲۹ (۲۷) — کارت «سود کل» با تفکیک سرمایه واریزی

کارت «سود کل» اکنون سه خط زیرین دارد:

- **میزان سود سرمایه** — سود زندهٔ لحظه‌ای (جمع سود/ضرر از خرید همهٔ ردیف‌ها)
- **کل سرمایه واریزی** — کل تومانی که کاربر داخل ربات گذاشته است؛ با **کلیک روی کارت** قابل تنظیم است (`/api/control/set_deposited`) و در kv_state می‌ماند. بار اول اگر تنظیم نشده باشد، خودش از سرمایهٔ فعلی در دارایی پر می‌شود.
- **جمع** — حاصل جمع دو خط بالا (کل پول حساب: سود + اصل)

نمونه زنده: `سود کل +12.06% | میزان سود سرمایه: +269,588 | کل سرمایه واریزی: 3,000,000 | جمع: 3,269,588` — و «سرمایه در دارایی» قبلی که فقط سکه‌های خریده‌شده را می‌شمرد از این کارت حذف شد (در ردیف‌ها به‌صورت «مبلغ خرید» باقی است).

### ۱۴۰۵-۰۶-۲۹ (۲۶) — سود ۲۴ساعت با مبنای واقعی ۲۴ ساعت قبل + سود کل زنده از ردیف‌ها

**۱. سود ۲۴ساعت همیشه از دادهٔ ۲۴ ساعت پیش:** KPI حالا ارزش حسابِ زنده را با نزدیک‌ترین نقطهٔ تاریخچه به ۲۴ ساعت قبل مقایسه می‌کند و **در زیرنویس اعلام می‌کند مبنا کدام لحظه بوده** («مبنا: ارزش حساب ۲۳ ساعت پیش (17.68$)»). تاریخچهٔ ارزش هم از ۴۰۰ به ۱۸۰۰ نقطه گسترش یافت تا پنجرهٔ ۲۴ ساعت همیشه کامل پوشش داده شود (قبلاً فقط ~۷ ساعت نگه می‌داشت و مبنا واقعی ۲۴ ساعته هرگز موجود نبود).

**۲. سود کل زنده:** KPI «سود کل» دقیقاً از همان اعداد «سود از خرید» ردیف‌های دارایی ساخته می‌شود — جمع (ارزش − سرمایه) همهٔ سکه‌ها، دوباره‌محاسبه‌شده در هر به‌روزرسانی (۲.۵ ثانیه). درصد تیتر = جمع سود ÷ جمع سرمایه (تأیید شد: ۹.۱۷٪ = ۲۸۴,۷۳۱ ت ÷ ۳,۱۰۵,۳۱۳ ت). زیرنویس هم حالا صریح می‌گوید: «زنده — جمع سود از خرید ردیف‌ها».

### ۱۴۰۵-۰۶-۲۹ (۲۵) — پاک‌سازی ستون «حد»: حذف براکت تکراری + نام «حد سود»

- براکت پله `(n)` که بین حد ضرر و حد سود در ستون «حد» تکرار می‌شد حذف شد — شمارنده پله فقط کنار «قیمت حد (n)» نمایش داده می‌شود (و همان کلیک‌پذیر است). ستون حد اکنون فقط دو عدد تمیز دارد: `873 (−۲٪) 1,024 (+۱۱.۴۲٪)`.
- در همه‌ی متن‌ها (توپی ویرایش، دیالوگ یکجا، پیام‌های خطا) «حد سود فروش» به **«حد سود»** و «حد ضرر فروش» به **«حد ضرر»** تغییر کرد.

### ۱۴۰۵-۰۶-۲۹ (۲۴) — براکت پله (n) کلیک‌پذیر شد + تضمین invariant «حد = خرید ⇒ پله ۰»

**۱. کلیک روی براکت (n):** در هر ردیف دارایی، با کلیک روی پرانتز کنار «قیمت حد» می‌توان پله (strike) و قیمت حد را دستی تغییر داد:
- **پله ۰** = حد برابر قیمت خرید (حد سود جدید از همان خرید مسلح می‌شود).
- **پله n>0** = قیمت حد را هم می‌پرسد و حد سود جدید = حد × (۱ + درصد فعلی حد سود).
- حد ضرر هرگز با این ویرایش دست نمی‌خورد (لنگر خرید).

**۲. invariant تضمین شد:** «قیمت حد برابر قیمت خرید» یعنی پله ۰ — نه هیچ عدد دیگری. اگر کاربر پله بالاتر با حدِ برابر خرید بخواهد، خودکار به ۰ اصلاح می‌شود با پیام فارسی؛ پلن‌های قدیمی با شمارنده گم‌شده هم در هر چرخه نرمال می‌شوند (متد `_hadd_stage_of`).

تأیید زنده: API — پله ۲ با حد +۲٪ خرید ✓؛ پله ۳ با حدِ برابر خرید → خودکار پله ۰ با پیام «قیمت حد برابر قیمت خرید است؛ پله روی ۰ تنظیم شد» ✓؛ پله ۰ → حد دقیقاً قیمت خرید ✓. ۳۷/۳۷ تست.

### ۱۴۰۵-۰۶-۲۹ (۲۳) — حذف آیتم تکراری «آخرین خرید» از ردیف دارایی‌ها

زمان آخرین خرید از قبل داخل پرانتز مقابل «سود از خرید» نمایش داده می‌شود؛ آیتم جداگانه «آخرین خرید: (زمان)» تکراری بود و حذف شد. ستون‌های ردیف اکنون: مقدار، مبلغ خرید، ارزش، قیمت، قیمت خرید، قیمت حد (n)، سود از خرید (با زمان آخرین خرید در پرانتز)، سود ۲۴ساعت، حد (ضرر/سود) و عملیات.

### ۱۴۰۵-۰۶-۲۹ (۲۲) — برگرداندن عدد «قیمت خرید» به ردیف دارایی‌ها

در بازطراحی قبلی، ستون عددی «قیمت خرید» به اشتباه حذف شده بود (فقط «آخرین خرید: (زمان نسبی)» مانده بود) — در حالی که مبنای حد ضرر همین قیمت است. حالا هر ردیف هر سه را دارد:

- **قیمت خرید** — عدد واقعی (میانگین سرمایه‌گذاری؛ همان مبنای حد ضرر)
- **قیمت حد (n)** — پله ۰ = آخرین خرید؛ با هر strike `+۱`
- **آخرین خرید** — زمان نسبی در پرانتز

تأیید زنده: BTC (پله ۰): خرید `18,050,000,001` و حد `18,050,000,001 (0)` برابر؛ PUMP (پله ۲): خرید `977` حفظ شده و حد `919 (2)`؛ مرتب‌سازی بر اساس قیمت خرید هم برگشت. ۳۷/۳۷ تست.

### ۱۴۰۵-۰۶-۲۹ (۲۱) — حد ضرر بدون strike + چرخش سرمایه بعد از فروش با حد ضرر

**دو تغییر بر اساس بازخورد کاربر (هدف کلان: رشد ارزش کل حساب):**

**۱. حد ضرر دیگر strike نمی‌خورد** — قبلاً با هر پله سود، حد ضرر هم از حد جدید گرفته می‌شد و بالا می‌رفت؛ نتیجه این بود که بعد از برگشت قیمت، موقعیت خیلی زود با حد ضررِ صعودی فروخته می‌شد (سود داده‌شده برمی‌گشت و سکه می‌رفت). حالا:
- **حد ضرر فروش** برای کل مدت نگهداری از **قیمت خرید** گرفته می‌شود (میانگین خرید) — درصد آن نسبت به قیمت خرید است و هرگز strike نمی‌خورد.
- **حد سود فروش** بر مبنای **قیمت حد** است (پله ۰ = آخرین خرید؛ هر بار رسیدن به حد سود، حد به همان قیمت strike می‌خورد و شمارنده `+۱` می‌شود).
- ویرایش درصدی هم همین‌طور: درصد حد ضرر ← قیمت خرید، درصد حد سود ← قیمت حد (تک‌سکه و «یکجا» هر دو).

**۲. بعد از فروش با حد ضرر، پول بی‌کار نمی‌ماند** — وقتی سکه‌ای با حد ضرر فروخته می‌شود:
- همان بازار تا رسیدن قیمت به strike بعدی (یا سپری‌شدن cooldown چرخش) **از خرید مجدد قفل** می‌شود تا ضرر دوبرابر نشود (`STOP_EXIT_LOCKOUT`).
- در **همان چرخه**، ربات بهترین فرصت امتیازدهی‌شدهٔ بازار را می‌خرد (`STOP_EXIT_ROTATION`) — همهٔ دروازه‌های ریسک (موجودی نقد، سقف موقعیت، لبهٔ کارمزدآگاه) همچنان اعمال می‌شوند.
- با خرید مجدد در آن بازار، پله‌ها از صفر ریست می‌شوند و «قیمت خرید» قبلی حذف می‌شود (خرید جدید = پله ۰).

تأیید زنده: ۳۷/۳۷ تست؛ PUMP: حد ضرر `873 (−۲٪ نسبت به خرید)` و حد سود `1,024 (+۱۱.۴۲٪ نسبت به حد 919)`؛ تست API: ‎−۱٪ حد ضرر روی BTC دقیقاً `avg_entry×۰٫۹۹` شد.

### ۱۴۰۵-۰۶-۲۹ (۲۰) — حذف کلید «قفل سود» + تصحیح پله ۰: قیمت حد = آخرین خرید

**دو تغییر بر اساس بازخورد کاربر:**

**۱. کلید «قفل سود» حذف شد** — دیگر دکمه‌ای روی ردیف‌ها نیست و API `/api/control/profit_lock` پاسخ می‌دهد که بلااستفاده است. رچت قیمت حد اکنون **همیشه فعال** است: هر بار که قیمت به حد سود برسد، شمارنده براکت `+۱` می‌شود، قیمت حد به همان قیمت به‌روز می‌شود، حد ضرر از حد جدید گرفته می‌شود (و هرگز پایین نمی‌آید) و حد سود بعدی از حد تازه محاسبه می‌شود. ترتیب چرخه تضمین می‌کند پیشروی پله **قبل** از بررسی خروج اجرا شود — یعنی فروش با حد سود اتفاق نمی‌افتد؛ خروج فقط با حد ضررِ صعودی است.

**۲. پله ۰ اصلاح شد** — قبلاً اگر پلن `base_price` قدیمی داشت، «قیمت حد» در پله ۰ با آخرین خرید یکی نبود. حالا در پله ۰ قیمت حد **همیشه برابر آخرین قیمت خرید** است (میانگین و مقادیر قدیمی فقط پشتیبان‌اند)؛ در پله ≥۱ قیمت حد = آخرین سطحی که بازار به آن رسیده. هر خرید جدید هم حد را به قیمت همان خرید ریست می‌کند (پله = ۰).

تأیید زنده: ۳۷/۳۷ تست؛ روی داده واقعی BTC/NVDA/LTC/MAGIC/GRAM در پله ۰ دقیقاً `قیمت حد = آخرین خرید` و PUMP پله ۲ و TRX پله ۱ با حد به‌روز؛ بدون هیچ دکمه «قفل سود» در UI.

### ۱۴۰۵-۰۶-۲۹ (۱۹) — «قیمت حد» جدید: مبنای واحد حد ضرر و حد سود با شمارنده پله (n)

**مدل جدید:** به‌جای اینکه همه درصدها از «قیمت خرید» خوانده شوند، یک **قیمت حد** معرفی شد — مرجع واحد هر دو سطح خروج:

- **اولین خرید:** قیمت حد = قیمت همان خرید، براکت `(0)`، حد ضرر ‎−۳٪ و حد سود ‎+۲۵٪ از همین حد.
- **با رسیدن قیمت فعلی به حد سود** (با قفل سود روشن): قیمت حد **به همان قیمت به‌روز می‌شود** و براکت `+1` می‌شود `(1)` — پله بعدی `(2)` و به همین ترتیب. کف حد ضرر از حد جدید گرفته می‌شود و **هرگز پایین نمی‌آید**؛ حد سود جدید هم از حد تازه محاسبه می‌شود (‎+۱۵٪ بالای حد جدید با پیکربندی فعلی).
- **درصدها همیشه از حد:** ویرایش درصدی روی هر سکه یا «یکجا» حالا `حد × (۱ ± درصد/۱۰۰)` حساب می‌کند. مثال زنده: PUMP در پله ۲ → `قیمت حد: 919(2)`، حد ضرر `873 (−۵٫۰۵٪ از حد)`، حد سود `1,024 (+۱۱٫۴۲٪ از حد)`.
- **UI:** ستون «قیمت خرید» به **«قیمت حد (n)»** تغییر کرد (آخرین خرید به‌صورت بازه زمانی کنار سود از خرید مانده). دیالوگ ویرایش حد و دیالوگ «یکجا» هم اکنون مبنای درصد را «قیمت حد» توضیح می‌دهند.
- **سازگاری:** پلن‌های قدیمی و سکه‌های وارداتی صرافی به‌صورت خودکار حد می‌گیرند (backstop در هر چرخه، هر پلنِ بدون حد را از میانگین خرید یا قیمت لحظه‌ای حفاظ می‌کند)؛ کلیدها و API ها بدون تغییر نام کار می‌کنند.

۳۷/۳۷ تست پاس (۵ تست جدید برای مدل حد: ثبت حد در خرید، پیشروی پله، قفل کف، درصدهای مبتنی بر حد) + تست زنده API روی BTCIRT (حد×۰٫۹۵ دقیق).

### ۱۴۰۵-۰۶-۲۹ (۱۸) — بازبینی کامل کد برای بیشینه‌کردن سوددهی (۶ نشتی سود پیدا و بسته شد)

کل خط لوله (AI → ریسک → اجرا → پلن خروج) با داده‌های واقعی دیتابیس (۴۶۲ خرید/فروش زنده، ~۶۴ میلیون تومان گردش) بازخوانی شد. شش نشتی سود پیدا و رفع شد:

**۱. کارمزد صفر در ثبت معاملات زنده (مهم‌ترین)** — reconcile سفارش‌های واقعی فیلد `fee_amount=0` می‌نوشت؛ یعنی «سود کل» ~۰٫۲۵٪ به ازای هر معامله **بیشتر از واقعیت** نشان می‌داد. حالا کارمزد با نرخ تیکر تخمین و ثبت می‌شود — دفتر سود دیگر دروغ نمی‌گوید.

**۲. موقعیت‌های بدون حد ضرر (۲۹۲ هزار تومان!)** — سکه‌هایی که خارج از ربات (خرید دستی در صرافی/همگام‌سازی کیف پول) وارد شدند، هیچ حد ضرری نداشتند: ZRO، BIO، TNSR، CHZ، BEAMX، EGLD. **backstop خودکار** اضافه شد: در هر چرخه، هر سکه‌ای بدون حد ضرر، بلافاصله حد ضرر پیش‌فرض می‌گیرد (از میانگین خرید؛ اگر ثبت نبود از قیمت لحظه‌ای) + قفل سود روشن می‌شود. حالا **هیچ سکه‌ای بی‌حفاظ نیست**.

**۳. خرید مجدد روی ضررده** — top-up خودکار میانگین خرید را مبنای «سود ۲۰٪» می‌گذاشت؛ بعد از افت بازار سکه‌ای که از آخرین خریدِ تو ضررده بود «سودآور» حساب می‌شد و ربات روی آن پول اضافه می‌کرد (doubling down روی بازنده). حالا مبنای top-up همان «قیمت خرید» آخر (last_buy_price) است که داشبورد نشان می‌دهد.

**۴. لبه‌ی تقلبی در فیلتر معاملات** — AI حداقل سود خالص مورد انتظار را با `max(..., 0.003)` به‌زور مثبت می‌کرد؛ یعنی معامله‌هایی که ریاضیاتشان منفی بود (انتظار < کارمزد ۰٫۵٪ رفت‌وبرگشت) به ریسک «سودده» گزارش می‌شدند. حالا عدد واقعی گزارش می‌شود و آستانه رد به ۰٫۰۰۶ (۰٫۶٪ > ۰٫۵٪ کارمزد) رسید — معامله بی‌لبه دیگر اجرا نمی‌شود.

**۵. چرخش بیش از حد (fee bleed)** — cooldown خرید برای هر بازار از ۱۰ دقیقه به **۳۰ دقیقه** رسید (قبلاً تا ۶ بار در ساعت روی همان سکه خرید با کارمزد کامل). و با اصلاح ۳، خریدهای تکراری فقط روی برنده‌های واقعی می‌نشینند.

**۶. نسبت سود/ضرر بهتر** — پیش‌فرض خرید ‎−۲٪/‎+۱۵٪ بود: هر ضرر به +۱۷٪ سود نیاز داشت تا سر به سر شویم. حالا ‎**−۳٪/‎+۲۵٪** (هر ضرر فقط ~۵٫۵ سود لازم دارد) و گام قفل سود **۱۵٪** (بعد از پله ۱، معامله حتی با فعال‌شدن حد ضرر سودده است).

**کشف جانبی مهم:** یک خطای قدیمی (`SNAPSHOT_VALIDATE_FAILED` — امضای تابع اعتبارسنجی به‌روز نشده بود) در لاگ رویدادها دیده می‌شود؛ فقط هشدار بود و جلوی چرخه را نمی‌گیرد، اما در همین بازبینی سالم‌سازی شد. چرخه کامل زنده تست شد: ۳ چرخه پیاپی، backstop روی ۶ سکه بی‌حفاظ مسلح شد، ۳۵/۳۵ تست پاس.

### ۱۴۰۵-۰۶-۲۹ (۱۷) — قفل سود پله‌ای (سطح ۰→۱→۲→۳…) + ستون «حد» و دکمه قفل در دارایی‌های من

**ایده:** دیگر فقط یک حد ضرر ثابت — با رسیدن قیمت به حد سود، سود باید **قفل شود** و موقعیت هرگز به ضرر برنگردد.

**چطور کار می‌کند (قفل سود روشن):**
- لحظه‌ی اول: حد ضرر همان ‎−۲٪ از قیمت خرید و حد سود ‎+۱۵٪ (پیش‌فرض فعلی) — نشان «قفل» با براکت **(۰)** یعنی هنوز هیچ سطحی قفل نشده
- با رسیدن قیمت فعلی به حد سود: **سطح +۱ می‌شود**، کفِ حد ضرر **دقیقاً روی همان سطح قفل می‌شود** (دیگر پایین نمی‌آید) و حد سود جدید **۲۰٪ بالاتر از کف قفل‌شده** مسلح می‌شود — پله‌ی بعدی هم همین‌طور (۱→۲→۳→…)
- نتیجه: بعد از پله ۱، فروش تضمینی روی کفِ قفل‌شده حداقل همان سطح را قفل می‌کند (بدون ضرر)
- خاموش کردن قفل: کف در آخرین سطح قفل‌شده می‌ماند و حد سود ثابت می‌شود — حفاظ از بین نمی‌رود
- از موقعیت بدون حفاظ: با روشن‌کردن قفل، کف اول ۱٪ زیر قیمت لحظه‌ای مسلح می‌شود

**تغییرات داشبورد (دارایی‌های من):**
- ستون‌های «حد ضرر فروش» و «حد سود فروش» در یک ستون **«حد»** ادغام شدند: «حد: 873 (-2٪) 🔒(2) 1,024 (+15٪)» — قفل و براکتِ عدد سطح، کنار حد سود
- دکمه **«قفل سود: روشن/خاموش»** روی هر ردیف — با توضیح فارسی قبل از تغییر
- پله‌ها خودکار در هر چرخه پیش می‌روند و بلافاصله در داشبورد دیده می‌شوند

**فنی:** کلیدهای جدید در exit_plans: `trail` (روشن/خاموش قفل)، `stage` (شمارنده سطح)، `locked_stop` (کف قفل‌شده). API: `POST /api/control/profit_lock {symbol, enabled}`. پیشروی در `engine._advance_profit_locks` قبل از بررسی خروج‌ها اجرا می‌شود. تنظیمات (بخش risk): `profit_lock_enabled`، `profit_lock_step_pct` (گام ‎+۲۰٪)، `profit_lock_max_stage` (۰=نامحدود). تست‌ها: `tests/test_profit_lock.py` — ۴ سناریو؛ کل مجموعه ۳۵/۳۵ پاس.

### ۱۴۰۵-۰۶-۲۹ (۱۶) — فایل start.bat بازسازی شد (قفل آنتی‌ویروس) + نگهبان اجرای همزمان

**مشکل:** دابل‌کلیک روی start.bat خطای دسترسی («can't open / Permission denied») می‌داد. بررسی نشان داد آنتی‌ویروس **ESET** بلافاصله بعد از بازنویسی فایل‌های bat آن‌ها را برای اسکن قفل می‌کند (فایل نه خواندنی بود، نه حذف‌شدنی؛ بعد از چند ثانیه خودش آزاد می‌شود). این رفتار موقتی است و ACL ویندوز سالم بود.

**چه کار شد:**
- start.bat با انتهای خطوط CRLF بازسازی شد و تست زنده‌اش کردیم: اجرای اول سرور و داشبورد را سالم بالا می‌آورد (HTTP 200)
- **نگهبان اجرای همزمان** اضافه شد: اگر یک نسخه از ربات از قبل روی پورت 8787 روشن باشد، دیگر نسخه دوم بی‌سروصدا اجرا نمی‌شود؛ پیام «پورت در حال استفاده است — احتمالاً ربات از قبل روشن است» نمایش داده می‌شود، داشبورد همان نسخه قبلی باز می‌شود و پنجره با مکث بسته می‌شود
- اگر پایتون یا کتابخانه requests نباشد، نصب خودکار انجام می‌شود (بدون نیاز به تنظیم دستی)
- اگر به هر دلیلی سرور با خطا متوقف شود، پنجره بسته نمی‌شود و راهنمای فارسی برای پیدا کردن و بستن پروسه مزاحم نشان داده می‌شود

**اگر دوباره خطای دسترسی دیدید:** فایل معمولاً بعد از چند ثانیه خودش آزاد می‌شود — یک‌بار دیگر تلاش کنید. اگر مدام تکرار شد، در ESET به مسیر Setup → Detection Engine → Exclusions، پوشه پروژه را استثنا کنید و فایل قرنطینه‌شده را از بخش Detections بازیابی (Restore) کنید.

### ۱۴۰۵-۰۶-۲۹ (۱۵) — خطای «حد ضرر فروش باید پایین‌تر از قیمت فعلی باشد» رفع شد

**باگ:** وقتی سکه‌ای که قبلاً خریداری شده بود بیش از ۲٪ زیر قیمت خریدش معامله می‌کرد (مثل W و T)، ثبت حد ضرر ‎−۲٪ رد می‌شد چون عدد به‌دست‌آمده از درصد، **بالاتر از قیمت فعلی بازار** بود (مثلاً خرید ۱۰۰٬۰۰۰، الان ۹۶٬۰۰۰ → حد ضرر ۹۸٬۰۰۰ > ۹۶٬۰۰۰). نتیجه: موقعیت بدون حفاظ می‌ماند. یک علت ثانویه هم بود: تیکر صرافی گاهی واحد اشتباه برمی‌گرداند (۲٬۷۰۰ به‌جای ۲۷۰٬۰۰۰) و گارد را مسموم می‌کرد.

اصلاحات:
- **Clamp به‌جای رد** — اگر سطح درخواستی سمت اشتباه قیمت فعلی بود، دقیقاً روی قیمت فعلی مسلح می‌شود (حفاظ فوری) و درصد واقعی‌شده ذخیره می‌شود؛ پیام فارسی: «چون قیمت فعلی از سطح درخواستی عبور کرده بود، سطح دقیقاً روی قیمت فعلی مسلح شد تا موقعیت بدون حفاظ نماند»
- **Sanity-check تیکر** — قیمت لحظه‌ای فقط وقتی معتبر است که در بازه‌ی ۵ برابر تا یک‌پنجم قیمت خرید باشد؛ وگرنه گارد بدون قیمت فعلی اجرا می‌شود (واردِ درست ثبت می‌شود)
- **پوشش حد سود** — همین منطق برای حد سود فروش هم برقرار است (سطح زیر قیمت فعلی → روی قیمت فعلی مسلح می‌شود)

تایید زنده: WIRT و TIRT که قبلاً با همین خطا رد می‌شدند، حالا ok=True با dist ‎−۰٫۱٪ مسلح می‌شوند؛ ۳۱/۳۱ تست قرارداد پاس.

### ۱۴۰۵-۰۶-۲۹ (۱۴) — حد ضرر/حد سود فروش فوراً بعد از هر خرید، با نام درست بازار

**باگ ریشه‌ای:** صرافی نوبیتکس در چند اندپوینت نام کامل سکه را برمی‌گرداند («PYTH NETWORK»، «Biconomy»، «Defi App» و…)، ولی بات و UI همه‌جا با نماد کوتاه کار می‌کنند (PYTHIRT، BICOIRT). نتیجه: fill و سفارش زیر نام خام ثبت می‌شد، پلن حد ضرر/حد سود زیر کلید اشتباه مسلح می‌شد و باکس «دارایی‌های من» هرگز آن را نشان نمی‌داد (مثل PYTH، W، DEFIAPP).

اصلاحات:
- **کانونی‌سازی در مرز صرافی** — همه‌ی fillها، سفارش‌ها و پلن‌های خروج از این به بعد با نماد کانونی ثبت می‌شوند (`canonical_symbol` در utils؛ نگاشت ~۵۰ نام کامل صرافی به تیکر)
- **تعمیر داده‌های موجود** — ۸۷ fill و ۱۱۵ سفارش قدیمی به نماد کانونی منتقل شدند (scripts/repair_market_names.py، idempotent)
- **پلن‌های ناقص تکمیل شد** — هر ۲۵ موقعیتِ فعال الان هم «حد ضرر فروش ‎-۲٪» و هم «حد سود فروش ‎+۲۰٪» دارند و در دارایی‌های من دیده می‌شوند
- **پلن بعد از فروش پاک می‌شود** — fill فروش پلن را حذف می‌کند تا سطح قدیمی روی موقعیت جدید نماند؛ خرید بعدی دوباره ‎-۲٪/‎+۲۰٪ تازه می‌سازد

### ۱۴۰۵-۰۶-۲۸ (۱۳) — حد ضرر و حد سود پیش‌فرض روی هر خرید

از این به بعد **هر خرید (دستی یا خودکار) به‌صورت خودکار دو سطح خروج می‌گیرد**:

- **حد ضرر فروش ‎-۲٪** از قیمت خرید — در پنل تنظیمات → ریسک، «حد ضرر پیش‌فرض خرید» قابل تغییر است (عدد منفی درصدی؛ ۰ = بازگشت به حالت قبلیِ تطبیقی ATR بین ۲ تا ۶٪)
- **حد سود فروش ‎+۲۰٪** از قیمت خرید — «حد سود پیش‌فرض خرید» در همان بخش؛ ۰ = خاموش

هر دو از قیمت خرید محاسبه می‌شوند و بعد از هر خرید مجدد، با قیمت خرید جدید دوباره مسلح می‌شوند. حالت ATR قبلی هم با تنظیم حد ضرر روی ۰ در دسترس می‌ماند.

### ۱۴۰۵-۰۶-۲۸ (۱۲) — تبدیل خودکار دارایی‌های خرد به تومان (بازار تبدیل نوبیتکس)

**سوییچ به API واقعی «تبدیل موجودی‌های خرد»:** کشف شد که پنل نوبیتکس برای این کار از `POST /users/wallets/convert` استفاده می‌کند — کل موجودی سکه را **بدون کف ۲۵ هزار تومانی** تبدیل می‌کند (تایید زنده: XLM ارزش ~۴ هزار تومان با همین مسیر کامل تبدیل شد در حالی که مسیر get-quote زیر ۲۵ هزار را رد می‌کرد). بات الان دقیقاً از همین مسیر استفاده می‌کند؛ یعنی دیگر هیچ خطای «کف تبدیل نوبیتکس» برای سکه‌های ریز دریافت نمی‌شود.

**فاصله‌گذاری درخواست‌ها:** همه‌ی درخواست‌های POST حداقل ۲٫۵ ثانیه فاصله دارند تا تبدیل‌های دسته‌ای (مثلاً ۱۰ سکه یکجا) خطای «rate limited» نگیرند.

**رفع باگ «کلیک بی‌اثر»:** کلیک روی «تبدیل کن» هیچ اتفاقی نمی‌انداخت — علت: بررسی دکمه‌ی تبدیل **بعد از** دسترسی به `el.dataset` روی عنصر `.stop-edit` انجام می‌شد؛ برای دکمه‌ی تبدیل آن عنصر وجود ندارد، خطای داخل هندلر بی‌صدا مسیر را می‌بست. حالا بررسی دکمه‌ی تبدیل اول از همه انجام می‌شود (تست زنده: کلیک → پنجره باز ✓ → تایید → نتیجه فارسی ✓).

**به‌روزرسانی دیالوگ:** دکمه‌ی «تبدیل کن» دیگر `confirm()` مرورگر را باز نمی‌کند — یک **پنجره‌ی انتخاب** باز می‌شود که همه‌ی دارایی‌های خرد را با **ارزش تومانی واقعی** هرکدام نشان می‌دهد؛ تیک بزنید (یا «انتخاب همه») و با دکمه‌ی سبز تایید کنید — فقط ردیف‌های تیک‌خورده تبدیل می‌شوند. نتیجه‌ی هر سکه (موفق/رد‌شده با دلیل فارسی) در پیام نشان داده می‌شود. **باگ مهم واحد پول هم رفع شد:** مبلغ ارسالی به API تبدیل ریال است نه تومان (×۱۰) — بدون این اصلاح همه‌ی تبدیل‌ها یک‌دهم ارزش واقعی بودند.

**نکته‌ی واقعی حساب:** سکه‌های ریز فعلی (XLM، AAVE، GPS و…) همگی **زیر کف ۲۵٬۰۰۰ تومانی** تبدیل نوبیتکس‌اند؛ تا وقتی با سود/خریدهای بعدی بزرگ‌تر شوند یا ارزش‌شان از کف رد شود، سیستم با پیام فارسی «ارزش X تومان است؛ کف تبدیل نوبیتکس Y تومان است» رد می‌کند — سکه‌های درشت (CGPT، ENA، DOGE و…) اصلاً جزو «خرد» حساب نمی‌شوند.

**مشکل:** سکه‌های باقیمانده‌ی خرد (خرده‌ی خرید و فروش‌ها) در کیف پول بی‌استفاده می‌ماندند و هیچ پولی از آنها به دست نمی‌آمد.

**راه‌حل:** دقیقاً همان مسیر صفحه‌ی «تبدیل» پنل نوبیتکس (`nobitex.ir/panel/balance/convert`)، به‌صورت خودکار:
- **هر چرخه**، دارایی‌هایی که ارزششان زیر «آستانه» است از طریق **بازار تبدیل** نوبیتکس (`exchange/get-quote` → `exchange/create-trade`) به تومان تبدیل می‌شوند.
- **کف واقعی صرافی** رعایت می‌شود: هر سکه کف تبدیل خودش را دارد (بیشترین کف مشاهده‌شده ۲۵٬۰۰۰ تومان) — سکه‌های زیر کف با پیام فارسی «ارزش X تومان است؛ کف تبدیل نوبیتکس Y تومان است» رد می‌شوند تا بی‌دلیل تلاش نشود.
- **سقف ایمنی:** حداکثر «تعداد تبدیل در هر چرخه» (پیش‌فرض ۳) — سکه‌های ارزشمندتر اول.
- بعد از هر تبدیل، کیف پول فوراً همگام می‌شود تا تومانِ آزادشده همان چرخه قابل خرید باشد.
- رویدادهای `DUST_CONVERTED` / `DUST_CONVERT_FAILED` در تاریخچه ثبت می‌شوند.

**استفاده:**
- **خودکار:** پنل تنظیمات → ریسک → «تبدیل خودکار دارایی‌های خرد — آستانه تومان» (۰ = خاموش، پیش‌فرض ۵۰٬۰۰۰ تومان). دو تنظیم دیگر: «سکه‌های مستثنی» و «حداکثر تعداد تبدیل در هر چرخه».
- **دستی:** در باکس «دارایی‌های من» دکمه‌ی فیروزه‌ای **«تبدیل کن»** — همه‌ی سکه‌های زیر آستانه یکجا تبدیل می‌شوند.

**تایید زنده روی حساب واقعی:** قرارداد API کشف و تست شد (پیش‌فاکتور: ۱۳٬۰۰۰٬۰۰۰ ریال → 5.72 USDT با quoteId و انقضا؛ BICO با کف ۲۵۰٬۰۰۰ تومان تایید شد). دکمه‌ی دستی روی حساب واقعی اجرا شد: سکه‌های زیر کف (XLM ارزش ۳٬۹۸۸ تومان، AAVE ۳٬۰۱۲، GPS ۲٬۲۵۹) به‌درستی با پیام فارسی کف رد شدند — یعنی هیچ سفارش تبدیلی بی‌دلیل به صرافی نمی‌رود.

۳۱/۳۱ تست قرارداد پاس؛ سرور روی `http://127.0.0.1:8787` زنده است.

### ۱۴۰۵-۰۶-۲۷ (۱۱) — پول نقد دیگر بلااستفاده نمی‌ماند

**مشکل:** بات سفارش می‌گذاشت ولی پول نقد IRT ساعت‌ها بلااستفاده می‌ماند.

**ریشه:** سفارش‌های خرید ۰٫۲۵٪ زیر قیمت لحظه‌ای ثبت می‌شدند؛ در بازار صعودی هیچ‌وقت پر نمی‌شدند، پول ۱۰ دقیقه قفل می‌ماند، لغو و دوباره زیر قیمتِ بالاترِ جدید ثبت می‌شد — چرخه‌ی بی‌پایان.

**اصلاحات:**
- **خرید در قیمت لحظه‌ای:** «فاصله خرید از قیمت لحظه‌ای» به ۰ تنظیم شد (در پنل تنظیمات قابل تغییر است) — سفارش بلافاصله پر می‌شود.
- **تعقیب قیمت (limit-chase):** در هر چرخه، هر سفارش خریدِ بازی که از قیمت لحظه‌ای عقب افتاده باشد (حداقل ۰٫۱٪) همان لحظه لغو و با قیمت تازه دوباره ثبت می‌شود — منتظر تایم‌اوت ۱۰ دقیقه‌ای نمی‌ماند.
- **منبع دوم قیمت:** نمادهایی که تیکرشان خطا می‌دهد (مثل STELLAR) از آخرین اسنپ‌شات قیمت می‌گیرند.

**تایید زنده:** قفل پول از ۱٬۱۰۳٬۰۳۹ به ۹۸٬۱۰۷ تومان رسید؛ RENDER و DOGECOIN خرید و پر شدند (حد ضرر خودکار مسلح شد)؛ ZEC/NEAR/DYDX هر چرخه با قیمت تازه دوباره ثبت می‌شوند.


هر سری تغییرات در این بخش ثبت می‌شود (جدیدترین در بالا).

### ۱۴۰۵-۰۶-۲۷ (۱۰) — لغو خودکار سفارش‌های پرنشده (آزادسازی تومان بلوکه‌شده)

> **به‌روزرسانی همان روز:** باگ ریشه‌ای پیدا و رفع شد — آداپتور زمان واقعی ثبت سفارش صرافی را دور می‌ریخت و هر سفارش باز را «تازه» جا می‌زد؛ به‌علاوه reaper فقط سفارش‌های دفتر محلی را می‌دید. حالا سن سفارش مستقیم از **زمان واقعی صرافی** خوانده می‌شود (ISO یا اپوک، هر دو) و reaper مستقیم لیست سفارش‌های باز صرافی را چک می‌کند — سفارش‌های ۱۱ ساعته فقط با یک چرخه لغو شدند (تایید زنده ✓). ذخیره‌ی تنظیمات ریسک در پنل حالا **همان لحظه** روی موتور در حال اجرا اعمال می‌شود (بدون ری‌استارت).

- **مشکل:** سفارش خرید ثبت می‌شد ولی اگر تا زمان معیّنی پر نمی‌شد، پولش بلوکه می‌ماند و سفارش‌های جدید با `BELOW_MIN_NOTIONAL` رد می‌شدند.
- **راه‌حل — «سفارش‌خور»:** در هر چرخه، سفارش‌های زنده‌ی خودِ بات که بعد از **۱۰ دقیقه** هنوز پر نشده‌اند به‌صورت خودکار لغو می‌شوند و تومان به کیف پول برمی‌گردد؛ چرخه‌ی بعدی می‌تواند سفارش تازه بفرستد.
- **تنظیمات:** «لغو خودکار سفارش پرنشده بعد از چند دقیقه (آزاد شدن تومان)» در پنل تنظیمات (ریسک). پیش‌فرض ۱۰ دقیقه؛ **۰ = خاموش**.
- سفارش‌های پرجزئی (partial) هم لغو می‌شوند و بخش پرشده حفظ می‌شود؛ رویداد `ORDER_CANCELLED` با دلیل `stale_timeout` در تاریخچه ثبت می‌شود.

### ۱۴۰۵-۰۶-۲۶ (۹) — مبنا برگشت به قیمت خرید + حد سود یکجا

- **مبنای درصد همه‌ی حد‌ها دوباره «قیمت خرید» شد** — هم ادیتور هر ردیف و هم تنظیم یکجا: درصد نسبت به «قیمت خرید» همان سکه در باکس دارایی‌ها حساب می‌شود. (حالت قیمت لحظه‌ای برای بک‌اند با پارامتر `base=current` باقی مانده است.)
- **«قیمت خرید» بعد از هر خرید مجدد به‌روز می‌شود** به آخرین قیمتی که واقعاً پرداخت شده — پس درصد ثابت شما با هر خرید مجدد خودش دوباره از قیمت جدید محاسبه می‌شود (موتور حد ضرر را از قیمت خرید تازه مسلح می‌کند).
- **«حد سود همه (یکجا)» اضافه شد** کنار «حد ضرر همه (یکجا)»: یک درصد مثبت (مثلاً ‎+5) → حد سود فروش هر سکه = قیمت خرید همان سکه × (۱ + درصد).
- اعمال واقعی روی حساب: حد ضرر ‎-2٪ و حد سود ‎+5٪ از قیمت خرید همه‌ی سکه‌ها یکجا نشست (سکه‌هایی که قیمت فعلی‌شان از حد سود پایین‌تر است با پیام فارسی رد می‌شوند — طبیعی است، قیمت هنوز به آن حد نرسیده).

### ۱۴۰۵-۰۶-۲۶ (۸) — رفع دو باگ حد ضرر

- **«حد ضرر همه (یکجا)» که کار نمی‌کرد:** قیمت‌ها فقط از آخرین اسنپ‌شات خوانده می‌شد و اگر اسنپ‌شات خالی/کهنه بود، هیچ سکه‌ای اعمال نمی‌شد. حالا اگر قیمت در اسنپ‌شات نباشد، مستقیم از **تیکر زنده‌ی صرافی** گرفته می‌شود — تست واقعی: هر ۱۲ سکه با ‎-2٪ اعمال شد و حد ضرر هر سکه دقیقاً ۲٪ زیر قیمت لحظه‌ای همان سکه نشست.
- **درصد ردیف‌ها از قیمت خرید حساب می‌شد:** اگر قیمت لحظه‌ای در دسترس نبود، بی‌صدا به مبنای قیمت خرید برمی‌گشت. حالا مبنای قیمت فعلی **الزامی** است و اگر هیچ‌جور قیمت زنده‌ای نباشد، پیام خطای صریح فارسی می‌دهد (دیگر هرگز بی‌صدا از قیمت خرید حساب نمی‌شود). مبنای قیمت خرید فقط با پارامتر صریح `base=entry` در دسترس است.
- اگر هیچ سکه‌ای اعمال نشود، UI حالا پیام «هیچ سکه‌ای اعمال نشد» با دلیل هر سکه نشان می‌دهد.

### ۱۴۰۵-۰۶-۲۶ (۷) — حد ضرر یکجا برای همه‌ی سکه‌ها + مبنای درصد = قیمت لحظه‌ای

- **«حد ضرر همه (یکجا)»** بالای باکس دارایی‌ها اضافه شد: یک درصد منفی (مثلاً ‎-3) وارد می‌کنید و **حد ضرر فروش همه‌ی سکه‌ها یکجا** تنظیم می‌شود — حد ضرر هر سکه = **قیمت لحظه‌ای همان سکه × (۱ − درصد)**. تعداد اعمال‌شده و سکه‌های ردشده (بی‌قیمت لحظه‌ای) در پیام نمایش داده می‌شود. ویرایش تک‌تک سکه‌ها روی ردیف خودشان همچنان ممکن است.
- **مبنای درصد حد ضرر عوض شد:** در ادیتور هر ردیف، درصد حالا نسبت به **قیمت لحظه‌ای فعلی** سکه حساب می‌شود، نه قیمت خرید (مثلاً ‎-3 با قیمت فعلی ۴۰٬۲۵۱ → عدد ۳۹٬۰۴۳ خودکار پر می‌شود). مبنای قدیمی «قیمت خرید» هم با پارامتر `base=entry` برای بک‌اند حفظ شده است.
- **بعد از هر خرید مجدد** (دستی یا خودکار) حد ضرر همان سکه دوباره از قیمت خرید تازه با باند ۲٪~۶٪ (ATR) مسلح می‌شود — درصد یکجای شما تا خرید بعدی روی هر سکه سفر می‌کند.
- تست آفلاین: مبنای قیمت فعلی، اعمال سراسری، مسلح‌سازی مجدد بعد از خرید و مبنای قدیمی همه پاس شدند.

### ۱۴۰۵-۰۶-۲۶ (۶) — مرتب‌سازی ستون‌ها در همه‌ی باکس‌ها

- **همه‌ی جدول‌ها و باکس‌ها** حالا هدرهای قابل کلیک دارند — کلیک روی هر ستون، ردیف‌ها را به‌ترتیب صعودی/نزولی مرتب می‌کند و کلیک دوباره جهت را برعکس می‌کند.
- **ستون نماد: ترتیب الفبایی** (IRT، ARB، XAUT، …). **ستون‌های عددی (قیمت، ارزش، سود، درصد، حجم و…): اولین کلیک = بزرگ‌ترین اول.**
- باکس «دارایی‌های من» هم هدر ستون گرفت (نماد، مقدار، مبلغ خرید، ارزش، قیمت، قیمت خرید، **آخرین خرید**، سود از خرید، سود ۲۴ساعت، حد ضرر، حد سود) — و **انتخاب مرتب‌سازی با هر رفرش ۲/۵ ثانیه‌ای حفظ می‌شود**، مثل بقیه‌ی جدول‌ها.
- مرتب‌سازی «آخرین خرید»: تازه‌ترین خرید اول (کلیک اول) یا قدیمی‌ترین (کلیک دوم)؛ سکه‌هایی که زمان خرید ثبت‌شده‌ای ندارند همیشه ته فهرست می‌نشینند.
- شامل: همه بازارها، کاندیدها، تصمیم‌ها، موتور ریسک، اجراها، موقعیت‌ها، پلن فروش، دارایی‌های صرافی و فیل‌ها.

### ۱۴۰۵-۰۶-۲۶ (۵) — حد ضرر خودکار بعد از هر خرید + خرید مجدد سودده

- **حد ضرر خودکار (بند ۱):** بعد از *هر* خرید — دستی یا خودکار — حد ضرر فروش به‌طور خودکار زیر قیمت همان خرید قرار می‌گیرد. فاصله واقع‌گرایانه بین **۲٪ تا ۶٪** است و نوسان بازار (ATR) تعیین می‌کند در کجای این بازه بیفتد. تنظیم‌پذیر در پنل تنظیمات: «حد ضرر خودکار — کمترین/بیشترین درصد».
- **خرید مجدد سودده (بند ۲):** وقتی سود از خرید یک سکه به **۲۰٪** برسد، بات خودش با پول نقد آزاد به همان موقعیت اضافه می‌کند (مبلغ را موتور ریسک تعیین می‌کند؛ یک بار در روز برای هر سکه). تنظیم: «خرید مجدد خودکار وقتی سود از خرید به این درصد رسید» (۰=خاموش). تست آفلاین: با سقف موقعیت کامل (۸/۸) خرید مجدد سکه‌ی نگه‌داری‌شده تایید شد — سکه‌ی تازه رد می‌شود.
- **قیمت خرید به‌روز (بند ۳):** بعد از خرید جدید، «قیمت خرید» در باکس دارایی‌ها **آخرین قیمت خرید** را نشان می‌دهد و «سود از خرید» و «سود ۲۴ساعت» نسبت به همان خرید تازه از نزدیک صفر حساب می‌شوند — میانگین وزنی واقعی برای P&L و موتور ریسک دست‌نخورده می‌ماند. فروش کامل همه‌چیز را صفر می‌کند تا خرید بعدی از صفر شروع شود.

### ۱۴۰۵-۰۶-۲۶ (۴) — سود کل: درصد به‌عنوان عدد اصلی

- KPI «سود کل» حالا **درصد** را به‌عنوان عدد اصلی نشان می‌دهد (مثلاً +34.87%) و **مبلغ تومانی** به زیرنویس رفت: «مبلغ: +156,022 تومان | سرمایه در دارایی: 447,388 ت».
- محاسبه همان جمع زنده‌ی (ارزش فعلی − مبلغ خرید) همه‌ی دارایی‌ها از زمان خرید است؛ فقط نمایش جابه‌جا شد.

### ۱۴۰۵-۰۶-۲۶ (۳) — سود کل زنده بر پایه‌ی دارایی‌ها + زمان پشت سود از خرید

- **KPI «سود کل» از پایه عوض شد:** حالا مجموع زنده‌ی
  `ارزش فعلی − مبلغ خرید` همه‌ی دارایی‌هاست (جمع سودها منهای ضررها،
  از زمان خرید هر سکه) — هر بار که صفحه رفرش می‌شود با قیمت‌های لحظه‌ای
  محاسبه می‌شود. نمایش: `+143,146 تومان | +32.00%` به‌همراه سرمایه‌ی
  درگیر در دارایی‌ها. (محاسبه‌ی قبلی بر پایه‌ی کل ارزش حساب بود که با
  موجودی نقد و واریزی‌ها قاطی می‌شد.)
- «آخرین خرید (زمان نسبی)» بلافاصله پشت «سود از خرید» نشست —
  `سود از خرید: (۲ ساعت) +6.7% → آخرین خرید: (۲ ساعت) → سود ۲۴ساعت`.

### ۱۴۰۵-۰۶-۲۶ (۲) — top-up خودکار بات + جزئیات کامل آخرین خرید

- **بات خودش پول آزاد را به سکه‌های نگه‌داری‌شده اضافه می‌کند** — دیگر
  فقط خرید اول محدود نیست: وقتی سکه‌ای که دارید همچنان بهترین گزینه‌ی
  رتبه‌بندی AI باشد، بات به‌جای صرفاً نگه‌داشتن، با پول نقد آزاد به
  همان موقعیت اضافه می‌کند (تنظیم `risk.allow_topup` در پنل تنظیمات،
  پیش‌فرض روشن؛ همیشه از صافی‌های موتور ریسک و موجودی واقعی می‌گذرد).
- **جزئیات آخرین خرید با زمان نسبی** داخل برچسب خود سود:
  `سود از خرید (۲ ساعت): +6.6%` — بدون کلمه‌ی «پیش»؛ مقیاس‌ها:
  دقیقه / ساعت / روز / ماه / سال. تاریخ دقیق تهران با نگه‌داشتن ماوس
  (tooltip) دیده می‌شود. موقعیت‌های قدیمی هم یک‌باره از فیل‌های ثبت‌شده
  زمان آخرین خریدشان بازیابی شد.
- **مبلغ خرید تجمعی و قیمت خرید به‌روز:** با هر خرید جدید، مبلغ خرید
  جمع می‌شود و میانگین خرید دوباره محاسبه می‌شود (تست واقعی ARB: پس از
  top-up، مقدار ۲.۷۶۷→۵.۶۳۶، میانگین ۳۳,۹۹۸→۳۴,۷۱۴، مبلغ خرید به‌روز).
- «مبلغ خرید» حالا سرمایه‌ی درگیر فعلی است (مقدار فعلی × میانگین خرید)،
  نه مجموع تاریخی همه‌ی خریدهای قبل از راه‌اندازی بات — تا نسبت سود/ارزش
  درست بماند.

### ۱۴۰۵-۰۶-۲۶ (۱) — دکمه خرید، سود ۲۴ساعت، شفافیت واریز و پاک‌سازی دیتا

- **دکمه «خرید» روی هر سکه در باکس دارایی‌ها** — با کلیک، مبلغ پیشنهادی
  از موجودی نقد (بودجه‌ی ریسک موتور، حداقل سفارش صرافی) پیشنهاد می‌شود؛
  قابل تغییر و تایید، و همان مبلغ از طریق موتور ریسک خریداری و به
  موقعیت اضافه می‌شود. خرید مجدد (top-up) حالا در چرخه‌ی خودکار بات هم
  فعال است (تنظیم `risk.allow_topup` در پنل تنظیمات، پیش‌فرض روشن).
- **جزئیات آخرین خرید در ردیف هر دارایی:** «سود از خرید (۱۲ دقیقه)» —
  تایمر نگهداری با هر خرید جدید از صفر شروع می‌شود؛ «مبلغ خرید»
  تجمعی با هر top-up جمع می‌شود و میانگین خرید به‌روز می‌شود (تست واقعی:
  ARB پس از خرید دوم، ۵.۶۳۶ سکه، میانگین ۳۴,۷۱۴، مبلغ خرید ۵۱۸,۲۱۶ ت).
- **سود ۲۴ساعت جایگزین «سود محقق» شد** — از تاریخچه‌ی ارزش خود حساب
  (نقاط هر دقیقه، ۴۰۰ نقطه) محاسبه می‌شود نه از چارت بازار؛ تا ۲۴ ساعت
  صادقانه «اولین نقطه: X ساعت پیش» می‌گوید.
- **واریز دستی دیگر سود حساب نمی‌شود** — IRT واریزی به حساب نوبیتکس
  به‌عنوان deposit ثبت و از «سود کل» کسر می‌شود (زیر KPI هم مقدارش
  نمایش داده می‌شود). باگ واقعی هم رفع شد: گارد واریز قبل از بازنویسی
  دفتر حساب نمی‌آمد و هیچ‌وقت فعال نمی‌شد.
- **پاک‌سازی خودکار دیتا:** سقف تعداد اسنپ‌شات (تنظیم
  `engine.max_snapshots`، پیش‌فرض ۲۰۰ — قدیمی‌ها خودکار حذف می‌شوند؛
  ۰ = نامحدود) و سقف حجم فایل رویدادها (`engine.events_retention_mb`،
  پیش‌فرض ۲۰MB). هر دو در پنل تنظیمات با برچسب فارسی.
- **رندر باکس دارایی‌ها از بک‌اند** (`holdings` در status): قیمت زنده‌ی
  سکه‌های بیرون از یونیورس هم با کش ۶۰ثانیه‌ای گرفته می‌شود تا سود/ارزش
  هیچ دارایی واقعی «—» نماند.

### ۱۴۰۵-۰۶-۲۵ (۷) — جادار بزرگ‌تر باکس دارایی‌ها بدون تغییر اندازه متن

- **فاصله‌ی بین آیتم‌های هر ردیف کم شد** (گپ ۸px به‌جای ۱۴px و در مانیتور
  بزرگ ۶px) تا کل اطلاعات یک دارایی با دکمه‌ی فروش در همان یک خط بماند.
- **عرض صفحه باز شد:** سقف ۱۴۰۰px به ۱۸۰۰px رسید تا در مانیتورهای بزرگ
  محتوا تا نزدیک گوشه‌ها کشیده شود نه اینکه وسط جمع شود.
- در نمایشگرهای بزرگ، فضای هر خط باکس دارایی‌ها کمی بیشتر می‌شود (پدینگ
  ملایم) — **اندازه‌ی متن همان ۱۳px می‌ماند** و فاصله‌ها جمع است.
- **یکنواخت‌سازی متن باکس:** همه‌ی اجزای هر ردیف (برچسب‌های کم‌رنگ، اعداد
  بولد، درصدها، برچسب‌های حد) روی یک اندازه‌ی ثابت قفل شدند — دیگر هیچ
  قطعه‌ای بزرگ‌تر یا کوچک‌تر از بقیه نیست (فقط دکمه‌ی «فروش» عمداً ۱۲px).
- **اصلاح:** آزمایش line-height ۱.۹/۲.۱ که فاصله‌های عجیب بین آیتم‌های یک
  ردیف می‌ساخت پس گرفته شد — فاصله‌ها دوباره عادی و فشرده‌اند.

### ۱۴۰۵-۰۶-۲۵ (۶) — سود کل درصدی + سود از خرید + فروش واقعی کامل

- **KPI «افت سرمایه» حذف و «سود کل» جای آن نشست:** درصدِ تغییر ارزش کل حساب
  نسبت به نقطه‌ی شروع (اولین همگام‌سازی کیف پول). مثبت سبز، منفی قرمز —
  همان «box سود» با +/- که خواسته بودید.
- **responsive:** در نمایشگرهای بزرگ (۱۶۰۰px و ۱۹۲۰px به بالا) ردیف‌های
  باکس دارایی‌ها بزرگ‌تر و بازتر می‌شوند.
- **«سود از خرید» جایگزین «سود ۲۴ساعته» شد:** درصد نسبت به قیمت خریدِ خودِ
  شما محاسبه می‌شود (نه تغییر بازار ۲۴ساعته) و مدت نگهداری کنارش نوشته
  می‌شود (مثلاً «سود از خرید (۲ روز): +0.32%»).
- **فروش واقعی کامل شد:** سفارش فروش با قیمت بازارِ قابل‌انجام ثبت می‌شود؛
  بعد از پر شدن، سکه‌های باقی‌مانده آزاد، کیف پول همگام و سرمایه به IRT
  (تومان) نشسته و قابل استفاده می‌شود. تست واقعی: فروش PUMP انجام و
  موجودی تومان همان لحظه به‌روز شد.
- باگ خواندن Decimal از float (str جای repr) در `_dec_of` رفع شد.

### ۱۴۰۵-۰۶-۲۵ (۵) — رفع بسته‌شدن ادیتور + فروش کامل با آزادسازی سکه‌های قفل

- **رفع باگ ویرایشگر:** کلیک روی فیلد درصد، فیلد تومانی را blur می‌کرد و
  ادیتور بلافاصله ثبت و بسته می‌شد — عملاً درصد قابل انتخاب نبود. حالا ثبت
  فقط وقتی انجام می‌شود که فوکوس واقعاً از ادیتور خارج شود (Enter، کلیک
  بیرون، Tab)؛ جابه‌جایی بین دو فیلد ادیتور را باز نگه می‌دارد.
- **دکمه «فروش» کامل شد:** قبل از فروش، هر سفارش فروشِ بازِ همین بازار لغو
  می‌شود (سکه‌های قفل‌شده آزاد می‌شوند)، کیف پول همگام می‌شود و بعد کل موجودی
  فروخته و به IRT (تومان) تبدیل می‌شود.

### ۱۴۰۵-۰۶-۲۵ (۴) — ویرایشگر دو فیلدی عدد/درصد با همگام‌سازی زنده

- کلیک روی حد ضرر/حد سود فروش حالا **دو فیلد کنار هم** باز می‌کند: «تومان»
  و «درصد» (پیش‌پرشده با مقدار فعلی پلن).
- **همگام‌سازی زنده دوطرفه:** درصد را بنویسید → عدد تومانی همان لحظه از
  ارزش خرید شما محاسبه می‌شود؛ عدد را بنویسید → درصد همان لحظه به‌روز
  می‌شود. ثبت با Enter (یا کلیک بیرون)، لغو با Escape.
- در ثبت، درصد اولویت دارد (منبع حقیقت)، پس عدد نمایش‌داده‌شده همیشه همان
  چیزی است که دیده‌اید.

### ۱۴۰۵-۰۶-۲۵ (۳) — حد سود فروش + درصد نسبت به ارزش دارایی + مبلغ خرید

- **«حد ضرر خرید» حذف شد** — خرید کار موتور است؛ جایش **«حد سود فروش»**
  نشست: وقتی قیمت به آن برسد (روند صعودی)، ربات قبل از سقوط کندل می‌فروشد.
  عدد آن باید بالاتر از قیمت فعلی باشد.
- **درصد حالا نسبت به ارزش دارایی شماست، نه قیمت بازار:** پایه‌ی درصد،
  `مقدار × قیمت خرید` است (چون مقدار ثابت است، درصد ارزش = درصد قیمت خرید).
  حد ضرر ‎-2 یعنی «وقتی ارزش دارایی‌ام ۲٪ پایین آمد بفروش»؛ حد سود ‎+3 یعنی
  «وقتی ۳٪ سود کردم بفروش». عدد مطلق خودکار از درصد محاسبه و ذخیره می‌شود و
  برعکس هم: عدد بنویسید، درصد پلن به‌روز می‌شود.
- **ستون «مبلغ خرید»** در باکس دارایی‌ها، بین «مقدار» و «ارزش»: ارزش ریالیِ
  خرید اولیه‌ی همان دارایی (مقدار × قیمت خرید).
- کنار هر عدد حد، درصد فعال پلن هم نمایش داده می‌شود؛ با تغییر درصد، عدد و
  با تغییر عدد، درصد خودکار به‌روز می‌شود.

### ۱۴۰۵-۰۶-۲۵ (۲) — حد ضرر خرید/فروش دوگانه + حالت درصدی نسبت به قیمت خرید

- **حد ضرر حالا دوگانه است:** «حد ضرر فروش» (فروش وقتی قیمت پایین می‌آید) و
  «حد ضرر خرید» (سفارش ایستاده خریدِ افت قیمت — وقتی قیمت به آن رسید، ربات
  از طریق موتور ریسک می‌خرد؛ BUY_STOP_TRIGGER).
- **دو حالت ورود در همان فیلد:** عدد ساده = تومان؛ عدد منفی = درصد نسبت به
  **قیمت خرید خودت** (مثلاً ‎-2 یعنی ۲٪ زیر میانگین خریدم). مبلغ مطلق
  حد ضرر خودکار محاسبه و در پلن ذخیره می‌شود (`stop_pct`/`buy_stop_pct`).
- **قیمت خرید** هر دارایی در باکس «دارایی‌های من» نمایش داده می‌شود؛
  بازسازی میانگین ورود حالا از همه معاملاتِ همان سکه (با هر نام بازار:
  ARBIRT/ARBITRUMIRT، GIRT/GRAVITYIRT) استفاده می‌کند — فیلدهای ARB و G که
  «—» بودند حالا پر شده‌اند (ARB ≈ ۱۰۳,۳۹۷ و G = ۱,۰۰۷ تومان).
- `POST /api/control/set_stop` حالا `side` (sell/buy) و `pct` را هم می‌پذیرد؛
  مدیر خروج، تریگر خرید را برای دارایی‌های بدون موقعیت هم چک می‌کند
  (خریدِ افت قیمت حتی وقتی آن سکه را نداری).
- باگ شمارش سود کل: بازسازی ورود قبلاً فقط ۲۰۰ فیل آخر را می‌دید (که پر از
  معاملات دموی قدیمی بود) — حالا پرس‌وجوی بازاری-به-بازاری (`fills_by_base`)
  معاملات واقعی همان سکه را مستقیم می‌خواند.

### ۱۴۰۵-۰۶-۲۵ (۱) — باکس دارایی‌ها به‌جای نمودار BTC + ویرایش حد ضرر

- کارت «نمودار قیمت BTCUSDT» در نمای کلی با **باکس «دارایی‌های من»** جایگزین شد:
  برای هر سکه‌ی کیف پول یک ردیف با مقدار، ارزش تومانی، قیمت فعلی،
  **سود ۲۴ساعته** (از بازار)، **سود کل** (نسبت به میانگین ورود) نمایش داده می‌شود.
- **حد ضرر هر دارایی قابل ویرایش شد:** روی عدد حد ضرر کلیک کنید، عدد جدید را
  وارد و Enter بزنید — از طریق endpoint `/api/control/set_stop` در پلن خروج
  همان سکه ذخیره می‌شود و مدیر خروج (Exit Manager) در چرخه بعد آن را اعمال می‌کند
  (باید پایین‌تر از قیمت فعلی باشد).
- دکمه‌ی **«فروش»** برای هر سکه به باکس اضافه شد (همان فروش فوری کامل موقعیت
  با عبور از موتور ریسک).
- موجودی **IRT (تومان)** — آزاد و قفل‌شده — بالای باکس دارایی‌ها نمایش داده می‌شود.
- کارت «ارزش پرتفوی (زنده)» حذف شد؛ باکس دارایی‌ها اکنون تمام‌عرض است.
- `status` اکنون `exit_plans` را هم برای فرانت‌اند برمی‌گرداند؛ endpoint جدید
  `POST /api/control/set_stop` و متد `TradingEngine.set_stop_loss` اضافه شد.

### ۱۴۰۵-۰۶-۲۴ — رفع خطاهای اجرای معامله واقعی

- `BUY_ORDER_ALREADY_ACTIVE`: همگام‌سازی وضعیت اجراهای قدیمی با صرافی در هر
  چرخه — سفارش‌های لغوشده دیگر بازارها را قفل نمی‌کنند.
- «موجودی نقد (تومان)» اکنون موجودی واقعی IRT را نشان می‌دهد (نه گرد و غبار USDT).
- بخش «خریدهای انجام‌شده و پلن فروش» با حد ضرر/نردبان حد سود و دکمه فروش فوری
  در تب پرتفوی اضافه شد؛ دکمه «لغو سفارش‌های باز ربات» به جدول سفارش‌های واقعی.
- سایز سفارش خرید وقتی از حداقل سفارش نوبیتکس کمتر شود به‌صورت خودکار به یک
  سفارش حداقلی بالا برده می‌شود (قابل تنظیم از تنظیمات فارسی).

### ۱۴۰۵-۰۶-۲۳ — اتصال واقعی به نوبیتکس

- ورود با ایمیل/رمز + کد 2FA (هدر `X-TOTP`)، ذخیره توکن در `data/credentials.json`،
  hot-attach موتور به حساب واقعی بدون ری‌استارت.
- همگام‌سازی موجودی اسپات واقعی، ثبت سفارش لیمیت واقعی، reconcile سفارش‌های باز،
  بازسازی میانگین ورود از معاملات واقعی و پلن خروج خودکار برای سکه‌های خریداری‌شده.
- یکسان‌سازی مقیاس قیمت‌ها روی تومان (ticker/orderbook/candles) و تبدیل ریال→تومان
  هنگام ثبت سفارش؛ فرمت `clientOrderId` سازگار با نوبیتکس.
- برطرف‌شدن `MAX_OPEN_POSITIONS_REACHED` (شمارش فقط معاملات خود ربات) و
  `BELOW_MIN_NOTIONAL` (بوت‌استرپ سایز برای حساب‌های کوچک).
