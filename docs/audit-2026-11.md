# Audit 2026-11 — findings, fixes, verification

Scope: the whole Python repository (`nobitex_bot/`, `scripts/`, `tests/`,
`run.py`, `sync_rtc.py`, the dashboard HTML). Every finding below was
reproduced from the code (or from a failing test that already existed in the
repository) before it was changed. Nothing here is a claim about profit or
about behaviour on the live exchange.

Method:

* read the execution path (`engine.py → ai.py → risk.py → execution.py →
  nobitex_api.py`) and the dashboard handlers in `web.py`;
* static analysis: `python -m compileall` and `python -m pyflakes`
  (pyflakes is the only linter installed on this machine; ruff/pytest are
  not);
* full unittest suite, then targeted modules per fix;
* the existing test suite was treated as the specification: three of its
  tests were already failing before any edit, and each failure was a real
  product defect (below).

## Defects found and fixed

| # | Sev | Where | Root cause | Fix |
|---|-----|-------|------------|-----|
| 1 | P1 | `nobitex_bot/ai.py` `HeuristicAI.decide` | `gate_notes` was appended to inside the multi-timeframe (analysis) block but only created *after* it. With `analysis.enabled = true` — the configuration the project recommends — every candidate carrying an analysis verdict raised `NameError: name 'gate_notes' is not defined`, so the whole analysis branch (allow/deny + veto codes) never completed. | `gate_notes = []` is created before the analysis block; the later re-assignment was removed. Regression: `tests/test_audit_fixes.py::TestAnalysisBranchNotes`. |
| 2 | P1 | `nobitex_bot/nobitex_api.py` `place_limit_order` | An HTTP 200 whose payload had no `order` object produced `order_id=""`, `status="OPEN"`. The engine then stored a phantom order that could never be reconciled with the exchange, and the market stayed "free" for another order. | A missing order id now raises `NobitexError("ORDER_UNCONFIRMED", …)` instead of pretending success. Regression: `TestUnconfirmedOrderReply`. |
| 3 | P1 | `nobitex_bot/risk.py` duplicate-buy guard | Only EXECUTION rows were consulted. An order adopted from the exchange after a lost submit response (`reconcile_real_orders` writes `exch_*` rows) has no execution row, so a second automatic BUY could be sent while the first was still resting. | The guard now also blocks when the order ledger has a NEW/PENDING/OPEN/ACTIVE/SUBMITTED/PARTIAL BUY for the same market. Manual clicks keep their documented override. Regression: `TestRestingOrderBlocksDuplicateBuy` (3 cases). |
| 4 | P2 | `nobitex_bot/engine.py` `_convert_dust_holdings` | In `trade_quote_markets = "usdt"` (or `"irt"`) the destination was forced to the active side even for a coin bought on the *other* side. Automatic runs then tried a cross-market transfer; a coin whose own section was switched off was not reported as such, and the manual button hit the exchange minimum on the wrong leg and converted nothing. (Two tests already failed: `test_quote_gate.TestDustConvertHonoursSelector`.) | The coin's own section is checked first (auto pass blocks with «بخش … خاموش است»), and a destination on the other side is refused for the automatic pass / redirected to the coin's own section for the manual pass, unless the markets are explicitly linked. |
| 5 | P3 | `nobitex_bot/web.py` `do_POST` | `/api/dust_preview` read `parsed.query`, a name that only exists in `do_GET`; a POST raised `NameError` → HTTP 500. | Parse the request line with `urlparse(self.path).query`. |
| 6 | P3 | `nobitex_bot/engine.py` status payload | `"executions"` was written twice into the same dict. | Removed the duplicate key. |
| 7 | P3 | `nobitex_bot/web/index.html` holdings box | The holdings card still rendered a «۲۴ساعت» chip and its `ch24*` helpers, contradicting the recorded requirement that this box shows only «سود از خرید» (`test_portfolio_v2` was failing). | The chip and its helpers were removed from `holdingsBox`; the dedicated «پرتفوی نوبیتکس» tab keeps the 24h column. |

Pre-existing failing tests now passing: `test_holdings_24h_column_is_gone_profit_from_purchase_stays`,
`test_auto_convert_skips_the_off_section`, `test_manual_convert_button_still_converts`.

### Follow-up tightening (fresh-eyes review of the fixes)

* Fix #3 originally scanned `storage.orders(limit=200)` — the newest 200 rows of
  *all* orders — so a resting BUY older than that window was still invisible.
  `Storage.active_orders(market, side)` now runs one indexed query for exactly
  the statuses that commit money (`ACTIVE_ORDER_STATUSES`, one definition used
  by both the query and the caller). The guard is also no longer wrapped in
  `try/except: pass`: a failing ledger read stops the evaluation instead of
  silently allowing the duplicate order.
* `Storage.upsert_candles` stores a whole OHLCV window with one `executemany`
  (the old single-row method committed per bar and now delegates to it). The
  `(symbol, timeframe, timestamp)` key keeps re-fetches idempotent.
* The collector now persists the 30m candles it already downloads for the AI
  (`CANDLE_STORE_FAILED` event on error, never breaking a cycle). This is what
  makes the `candles` table grow from normal operation instead of only from the
  backfill script.

## Not changed (deliberately)

* Dead locals reported by pyflakes (`hold_s`, `sp2`, `step`, `quote`,
  `usdtirt`, `res`, `chased`, `opened`, `cash_ratio`, `st_map`,
  `breakout_st`) and unused imports in modules this pass did not otherwise
  touch (`analysis`, `demo_market`, `events`, `features`, `validation`,
  `web`). They are unused values/names, not wrong values; removing them
  changes no behaviour and would only enlarge the diff. `chased` in
  `_chase_stale_orders` is the one worth a follow-up: the chase loop builds
  the list but never reports it to the caller. The unused imports in the
  touched modules (`risk.ExecutionStatus`, `collector.new_id`,
  `collector.validate_market`, `web.threading`) were removed, so pyflakes on
  this pass's files reports only the pre-existing `cash_ratio` local.
* Order/price unit conversions (`Rial`↔`Toman`, USDT isolation) — inspected
  and consistent with the documented boundary rule; already covered by
  `test_price_units`.
* Database schema and `data/` — untouched. No migration was needed, no
  history was rewritten, no database file was copied into `RTC/`.

## Remaining, requires a real account / separate work

* No live order was placed and no exchange endpoint was called with
  credentials during this audit. The IRT-vs-USDT sell path, partial fills,
  404/429 handling and balance reconciliation are covered only by unit tests
  with mocked replies (plus the adapter's own read-only `NOBITEX_READ_ONLY`
  lock).
* No profitability claim is made. The backtest below replays one stored
  window with the harness's fixed exits and costs; it is not walk-forward and
  not out-of-sample. See its own caveats.
* The dashboard was not exercised in a browser. The HTML is covered by the
  static assertions in `tests/test_portfolio_v2.py`, not by a click-through.
* `_chase_stale_orders` still discards its `chased` list (no user-visible
  report of a re-priced order).
* The real `config.json` was not started: it currently has
  `live_trading: true`, so launching the engine would place real orders.
  Startup/first-cycle smoke checks were therefore run through the tests'
  temporary configs only.

## Backtest on stored real candles (2026-11-23)

Data was fetched from the public OHLC endpoint only (`scripts/fetch_candles.py`,
no login, no wallet, no order) into `data/trading_bot.db`:

```text
12 markets x {1h, 4h} x 500 bars = 12,000 rows (all new)
1h span 2026-11-02T17:30Z .. 2026-11-23T12:30Z   (~21 days)
4h span 2026-09-01T08:30Z .. 2026-11-23T12:30Z   (~83 days)
markets: BLUR, BTC, ETH, MMT, PROM, PUMP, TRX, USDT, XAUT, XRP, ZEC, ZIL (all …IRT)
```

The public candle endpoint returns at most 500 bars per request, so a longer
window needs a paging loop (not implemented) or the collector's own history.

Command (identical for `--timeframe 4h`):

```text
python -m nobitex_bot.backtest --db data/trading_bot.db --timeframe 1h \
    --symbols BLURIRT,BTCIRT,ETHIRT,MMTIRT,PROMIRT,PUMPIRT,TRXIRT,USDTIRT,\
XAUTIRT,XRPIRT,ZECIRT,ZILIRT --spread-pct 0.2 --json reports/backtest-1h-spread02.json
```

Costs: 0.25% fee/side, 0.10% slippage/side, 0.2% spread charged once;
slots=2, max_hold=24 bars, pipeline defaults (max extension 2.5 ATR, min p_up
0.55).

| timeframe | arm | trades | win % | avg net % | total net % | PF | max DD % |
|---|---|---|---|---|---|---|---|
| 1h | change_24h | 97 | 23.71 | -1.4833 | -143.88 | 0.477 | -156.31 |
| 1h | change_24h+veto | 13 | 38.46 | -1.3705 | -17.82 | 0.610 | -25.25 |
| 1h | net_edge | 82 | 32.93 | -0.9837 | -80.67 | 0.545 | -108.74 |
| 1h | net_edge+veto | 13 | 38.46 | -1.3705 | -17.82 | 0.610 | -25.25 |
| 4h | change_24h | 112 | 25.89 | -1.5372 | -172.17 | 0.573 | -215.22 |
| 4h | change_24h+veto | 31 | 35.48 | +0.1013 | +3.14 | 1.037 | -36.53 |
| 4h | net_edge | 93 | 30.11 | -0.6223 | -57.87 | 0.792 | -135.47 |
| 4h | net_edge+veto | 32 | 37.50 | +0.2490 | +7.97 | 1.095 | -25.89 |

Without the 0.2% spread the 4h veto arms read +29.87% (PF 1.36) and +18.37%
(PF 1.25); the spread is what separates "promising" from "flat". What the
sample supports:

* On this window the 24h-change ranking alone loses money in every
  configuration; the Phase-2 entry vetoes remove most of the trades and turn
  the 4h result from clearly negative to roughly break-even (+3% and +8% over
  83 days, 31-32 trades, drawdown -26% to -37%).
* The vetoed samples are small and the 1h timeframe stays negative, so this is
  **not** evidence that the bot is profitable. It is evidence that the entry
  veto is the component worth keeping and that the current exits still bleed
  fees on short holds (stop rate 60-68%, target rate 19-29%).
* `max_drawdown_pct` is a sum of per-trade net percentages, not compounded
  equity — it overstates the account-level drawdown.
