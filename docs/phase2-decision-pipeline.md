# فاز ۲ — خط لولهٔ تصمیم واحد

وضعیت: **طراحی + پیاده‌سازی ماژول، بدون اتصال به موتور.**
`nobitex_bot/pipeline.py` هیچ سفارشی نمی‌فرستد، حجمی تعیین نمی‌کند و
`engine.py` آن را import نمی‌کند؛ پس رفتار معاملات واقعی و paper تغییری
نکرده است. اندازه‌گیری سوددهی کار فاز ۳ است و در این فاز هیچ ادعایی دربارهٔ
سود مطرح نشده.

---

## ۱) قرارداد

یک ورودی، یک خروجی، یک صاحب تصمیم:

```
Evidence  ──►  DecisionPipeline.evaluate()  ──►  Decision(action = BUY|AVOID)
                    │
                    ├─ rank() → (buyable مرتب بر net edge, rejected با دلایل)
                    └─ best() → تنها بهترین BUY یا None
```

- `Evidence` (frozen): همهٔ چیزی که تصمیم **اجازه دارد** ببیند.
- `Policy` (frozen): آستانه‌ها؛ پیش‌فرض‌ها محافظه‌کارانه‌اند، نه بهینه‌شده.
- `Decision`: شامل `vetoes`، `net_edge_pct`، `cost_pct`، `target_pct`،
  `stop_pct`، `p_up`، و **کپی کامل Evidence** برای بازپخش.

همهٔ درصدها در این ماژول **درصد** هستند (`0.25` یعنی ۰٫۲۵٪)، نه کسر. موتور
هر دو قرارداد را قاطی می‌کند و همین منبع باگ‌های واحد بوده است.

## ۲) رتبه‌بندی بر بازده انتظاری خالص

```
cost      = 2×fee + 2×slippage + spread            (رفت‌وبرگشت، درصد)
upside    = min(ATR×3.2 , فاصلهٔ مقاومت , پیش‌بینی)  ≥ 0
downside  = max(ATR×1.2 , 2×cost)
net_edge  = p_up × upside − (1 − p_up) × downside − cost
```

نکته‌های طراحی:

- **هزینه یک‌بار و روی کل انتظار** حساب می‌شود، چون رفت‌وبرگشت در هر دو
  حالت (سود و ضرر) پرداخت می‌شود.
- **سقف واقعی، تارگت را کوچک می‌کند**: مقاومتی که ۰٫۹٪ بالاتر است، تارگت
  را به ۰٫۹٪ می‌برد؛ وگرنه هر معامله روی کاغذ سودآور به‌نظر می‌رسد.
- **رتبه فقط از `net_edge` می‌آید.** تغییر ۲۴ساعته، امتیاز اسکنر و
  `growth_score` هیچ نقشی در ترتیب ندارند (فقط در Evidence ثبت می‌شوند).

## ۳) وتوی مکان ورود — غیرقابل خاموش کردن

`entry_location_veto(evidence, policy)` **هیچ پارامتر `top_gainer` ندارد**.
این ساده‌ترین تضمین ساختاری است: پرچم رتبه وجود ندارد که بتواند آن را
relax کند. قواعد:

| کد | شرط |
| --- | --- |
| `ENTRY_LOCATION_UNKNOWN` | `extension_atr is None` — نبود داده = عدم خرید (fail closed) |
| `ENTRY_TOO_EXTENDED` | `extension_atr > 2.5` |
| `TOO_CLOSE_TO_RESISTANCE` | فاصلهٔ مقاومت `< 0.7%` |

بقیهٔ وتوها (سخت، هرگز میانگین نمی‌شوند): `NO_PRICE_DATA`،
`DATA_QUALITY_LOW`، `LIQUIDITY_UNTRADABLE`، `LIQUIDITY_SCORE_LOW`،
`SPREAD_TOO_WIDE` (سقف = `max(1.5%, 0.5×ATR)`)، `STRUCTURE_DOWNTREND`،
`P_UP_BELOW_MIN`، `NET_EDGE_BELOW_MIN`.

هیچ وتویی «امتیاز منفی» نیست که با یک امتیاز خوب جبران شود؛ وجود یکی از
آن‌ها کافی است برای `AVOID`.

## ۴) این ماژول چه چیزی را در موتور فعلی جایگزین می‌کند

| مسیر فعلی تولید BUY | وضعیت پیشنهادی |
| --- | --- |
| `ai.heuristic.decide` (BUY) | فقط `Evidence` می‌سازد؛ اکشن از pipeline |
| `analysis.decide(allow_buy)` | منبع `p_up`/`expected_move`/`extension` و بقیهٔ Evidence |
| `ai.buy_best` (ساخت BUY اجباری) | **حذف**؛ جایش `pipeline.best()` که اگر BUY نباشد `None` می‌دهد |
| `_synthesize_buy_plan` | حذف به‌عنوان تولیدکنندهٔ تصمیم؛ فقط ساخت پلن اجرایی از Decision |
| `_rotation_buy_after_stop` | همان pipeline، با Evidence بازارهای آزاد |
| `_ladder_topup_decisions` / `_profit_topup_decisions` | افزودن روی موقعیت موجود، جدا از ورود اولیه (خارج از دامنهٔ این ماژول) |

نتیجهٔ ساختاری: یک نقطه در کل برنامه می‌تواند `BUY` بدهد و همان نقطه
`top_gainer` را نمی‌خواند.

## ۵) نگاشت Evidence از دادهٔ موجود

| فیلد | منبع فعلی |
| --- | --- |
| `atr_pct`, `extension_atr`, `structure`, `dist_resistance_pct` | `analysis.analyze_frame` / `score_components` |
| `p_up`, `expected_move_pct` | `forecast.project` (احتمال، نه کالیبره — بند ۶) |
| `spread_pct`, `change_24h`, `liquidity` | اسنپ‌شات `collector` |
| `data_quality` | `features`/`collector` |
| `fee_pct`, `slippage_pct` | `fee.taker_rate`، `risk.max_slippage` |

**غایب و لازم در فاز بعد:** VWAP روزانه (برای «چقدر بالای میانگین حجمی
هستم»)، عمق دفتر سفارش در سطح قیمت (برای هزینهٔ واقعی)، و نوسان رژیم.

## ۶) محدودیت‌های صریح

1. `p_up` از `forecast.py` می‌آید که **کالیبره نشده** است. تا فاز کالیبراسیون،
   `net_edge` یک معیار **رتبه‌بندی نسبی** است، نه پیش‌بینی سود.
2. آستانه‌های `Policy` از داده به دست نیامده‌اند؛ قواعد «کارمزد را برای
   حرکتی که قبلاً انجام شده نپرداز» هستند.
3. اتصال به موتور نیازمند حذف مسیرهای «خرید اجباری» است؛ تا آن زمان این
   ماژول فقط در تست و بک‌تست اجرا می‌شود.
4. تست‌ها فقط رفتار قرارداد را ثابت می‌کنند (`tests/test_pipeline.py`)، نه
   سوددهی.

## ۷) گام بعد (فاز ۳)

هارنس بک‌تست روی کندل‌های ذخیره‌شده: برای هر کندل بسته، `Evidence` ساخته
شود، `pipeline.rank` اجرا شود، و نتیجه با کارمزد/اسلیپیج واقعی همان بازار
مقایسه شود — شامل walk-forward و مقایسهٔ «رتبه بر اساس تغییر ۲۴ساعته» با
«رتبه بر اساس بازده انتظاری خالص». تا آن عدد، هیچ تغییری در مسیر معاملات
واقعی مجاز نیست.
